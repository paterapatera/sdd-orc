# タスクの書き方

完全モードの `tasks.ts` と、軽量モードの `spec.ts`（`tasks`）で共通の書き方。
型の定義は `docs/sdd/schema/tasks.ts` にある。

## 粒度と順序

- **1タスク＝1コミット**で進められる粒度にする。経緯を追えて、途中で一部だけ戻せるようにするため。
- 細かくしすぎない。目安は完全モードで3〜10件。設定ファイルを1つ足すだけのような小さな作業は、関係するタスクにまとめる。
- タスクは上から順に実施する。オブジェクトに書いた順序がそのまま実施の順序になる。
- 軽量モードは1〜3件が目安。4件以上になるなら、完全モードへの切り替えを検討する。

## 種類（kind）

| kind | 内容 |
|---|---|
| `test` | テストを追加・変更する。`verifies` に確かめる対象を書く |
| `impl` | 機能を実装する |
| `refactor` | 振る舞いを変えずに構造を直す |
| `docs` | ドキュメントを更新する |
| `chore` | 設定、依存関係など |

## refs と verifies

- `refs`: そのタスクが実現する要件のID（`FR`、`NFR`、`INV`）やコンポーネント名。1件以上。
- `verifies`: テストで確かめる対象のID（`AC`、`INV`、`NFR`）。`kind: "test"` のタスクにだけ書く。

verify は次を確かめる。

- すべての受け入れ条件（`AC`）と変えてはいけない振る舞い（`INV`）が、どれかのテストタスクの `verifies` に含まれている（漏れはエラー）
- すべての非機能要件（`NFR`）が、どれかのテストタスクの `verifies` に含まれている（漏れは警告）
- すべての機能要件（`FR`）が、どれかのタスクの `refs` に含まれている（漏れはエラー）

## 受け入れ条件のテストの書き方

- **テストは、受け入れ条件の `when` を実際に実行し、`then` を観測する。** ファイルに文字列が書かれているかを調べるだけのテスト
  （「README に〇〇が含まれる」「設定ファイルに〇〇がある」）は、受け入れ条件のテストにしない。
- 品質ゲート（`deno task gate`）で実行されない（スキップされる）テストを、`verifies` の根拠にしない。
- **テストの中から、品質ゲート（`deno task gate`）、`docker compose`、依存関係の導入（`composer install`、`bun install` など）を呼ばない。**
  品質ゲートがテストを実行し、そのテストが品質ゲートを呼ぶと、無限に再帰して止まる。
- テストは、対応する実装と同じタスクか、その直後のタスクに置く。すべてのテストを最後にまとめない
  （各タスクのコミットで品質ゲートを通すため）。

## プロジェクト全体の非機能要件を確かめるタスク

要件の `nfrReview` で baseline にしたカテゴリに `docs/sdd/nfr.ts` の基準（`BNFR-xxx`）があれば、
その基準を確かめるテストタスクを作り、`verifies` に `BNFR-xxx` を書く（例: 主要画面の表示時間を計測する）。
このissueで確かめない場合は、要件の `nfrReview` の `waived` に理由が書かれている（verify が確かめる）。

## 受け入れテストの準備のタスク

人が確かめる受け入れ条件（`verifiedBy: "human"`）が、特定のデータやアカウントを前提にしている場合
（ログインした利用者、100件のデータなど）は、それを用意するタスクを作る。

- **開発用のシーダー（またはコマンド）を必ず作る。** 本番の初期データとは別のクラスにするか、環境で分ける。
  テストの中だけでデータを作るのでは、人が受け入れテストで使えない。
- 件数が受け入れ条件の前提になっている場合（101件、201件など）は、その件数をそのまま作れるようにする（実行するたびに同じ状態になるように）。
- テスト用のアカウントは、ID とパスワードを決めて作る（人に登録させない）。
- 用意のしかたは、sdd-impl が完了時に `acceptanceGuide` の `data` と `accounts` に書く。

## E2E テストのタスク

`docs/sdd/config.ts` の `ui` が true（画面がある案件）なら、人が確かめる受け入れ条件（`verifiedBy: "human"`）を
E2E テストでも確かめるタスクを作る（`kind: "e2e"`、`verifies` にその受け入れ条件を書く。verify が確かめる）。
人の受け入れテストより先に、画面の崩れや遷移の誤りに気づくため。
画面の見た目が変わる場合は、スクリーンショットの比較も入れる（E2E のツールに機能があれば）。

## テストの順序

- **バグの修正**: 最初のタスクを「再現テストを書いて、失敗することを確かめる」にする（verify が確かめる）。
  修正のタスクで、そのテストが通るようにする。
- **テストが無い既存のコードを変更する**: 変更の前に「現状の振る舞いを固定するテスト」を追加するタスクを置く。
  変えてはいけない振る舞い（`INV`）を確かめるテストになることが多い。
- 新しい機能は、受け入れ条件のテストを実装の前か直後に置く。どちらにするかはプロジェクトの規約に合わせる。

## 状態（status）とコミット

- 作成時は、すべて `status: "todo"` にする。
- 着手したら `"doing"`、完了したら `"done"` にし、その変更をタスクのコミットに含める。
- **コミットのハッシュは spec に書かない。** コミットメッセージを `<type>(<ID>): <タスクID> <タスクのタイトル>`
  （`docs/sdd/guides/commits.md`）にすれば、道具（next、finish-report、HTML）が自動で対応を求める。

## 説明（description）の書き方

- 何をどこに作るかを、実装する人（AI）が迷わない程度に具体的に書く。
- ファイルのパス、関数名、テストの観点を含める。
- 設計（design.ts）や spec の方針と矛盾させない。
