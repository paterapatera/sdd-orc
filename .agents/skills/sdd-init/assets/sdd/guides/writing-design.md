# 設計の書き方

完全モードの `design.ts` の書き方。型の定義は `docs/sdd/schema/design.ts` にある。

## 基本の考え方

- **恒久ドキュメントに従う。** `docs/sdd/architecture.ts`、`conventions.ts`、`nfr.ts`、`adr/` の決定に反する設計をしない。
  **accepted の ADR と食い違う設計（例: ADR で PostgreSQL と決めたのに、テストだけ SQLite にする）が必要な場合は、必ず質問する。**
  ADR は人と合意した技術選定なので、AIだけで覆さない。覆すことになったら、新しい ADR を作る（decisions に `adr: true`）。
- **既存の作法を優先する。** `docs/sdd/conventions.ts` と既存のコードの書き方に合わせる。より良いと思うやり方があっても、
  新しいライブラリや新しいパターンを持ち込むなら、decisions に `adr: true` で理由と代替案を書く。
- **コードを正とする。** `docs/sdd/architecture.ts` とコードが食い違っていたら、コードに合わせて設計し、
  食い違いを `risks` に書いてユーザーに伝える（architecture.ts は sdd-finish で直す）。
- **要件に無いものを作らない。** 将来のための拡張や、頼まれていない改善は入れない。必要だと思ったらユーザーに提案する。
- **判断できないことは推測で決めない。** 下の「質問するもの・しないもの」に従い、決められない選択は
  `docs/sdd/guides/asking-questions.md` の手順で**1件ずつ**質問する。

## 質問するもの・しないもの

設計の内容を人にレビューしてもらうことはしないので、人の判断が要る選択は、設計を書く前に質問して決める。
ただし、質問は最小限にする。要件・既存コード・規約（conventions.ts）・ADR のどれかで決まるものは質問しない。

### 質問するもの（要件などから決められず、次のどれかに当たるもの）

| 種類 | 例 |
|---|---|
| 利用者や外部から見える形が変わる | 受け入れ条件に無い画面の構成（表かカードか、見出し、ナビゲーション）、文言、操作の後の遷移先、既存の画面の削除、外部に公開するAPIの形（URL、項目名、エラーの返し方） |
| 画面の部品やデザインの決まりに無いもの | `conventions.ts` の画面の部品やデザイントークンに無い部品・色・スタイルを使う、新しいUIライブラリを足す |
| 既存のデータや運用に影響する | 既存データの移行方法、削除の扱い（物理削除か論理削除か）、保存期間、バッチの実行時刻 |
| 新しい依存を持ち込む | 新しいライブラリ、外部サービス、ミドルウェアの採用。**`adr: true` になる判断は、必ず質問する**（AIだけで決めない） |
| 費用や性能のトレードオフがある | キャッシュを入れるか、同期処理か非同期処理か（非機能要件で決まっていない場合） |
| 後方互換の扱い | 既存のインターフェースを変えるか、新しいものを並べるか（変えてはいけない振る舞いで決まっていない場合） |
| 他の人の作業と取り決めが要る | 他のissueと共有するインターフェースや共通ファイルの変更 |

- **利用者から見えることを決めたら、要件に戻す。** 画面の構成、文言、遷移先などを質問で決めた場合は、
  `docs/sdd/guides/review-feedback.md` の手順で要件の受け入れ条件にも加える（人が受け入れテストで確かめられるようにするため）。
  要件の変更になるので、ユーザーの了承を得る。
- issue がツールの選定方法を指定している場合（例:「propose-quality-tools で選定する」）は、その方法を実行してから質問する。

### 質問しないもの（AIが決める）

- 既存のコードや規約に同じ種類の実装があり、それに合わせれば決まるもの（クラスの分け方、命名、ファイルの置き場所）
- 利用者や外部から見えない内部の実装の詳細（関数の分け方、内部のデータ構造）
- 要件・受け入れ条件・非機能要件・変えてはいけない振る舞いから決まるもの

迷う場合は、「この選択を後から変えるのが高くつくか」「利用者や他の人に影響するか」で判断する。どちらかに当たるなら質問する。

## 各項目

### overview、asIs、toBe

- `overview`: 設計の要点を2〜3文で。
- `asIs`: 変更する部分が**今どうなっているか**。コードを読んで書く。新しく作る場合は「新規作成」。
- `toBe`: 変更後にどうなるか。asIs との差が分かるように書く。

### components

- 責務がはっきり分かれる単位（クラス、モジュール、サービスなど）にする。細かくしすぎない（関数ごとには分けない）。
- 名前は、コード上の名前と一致させる（既存のものは実際の名前、新しいものは作る予定の名前）。
- `kind: "modified"` のものは `asIs`（現状）を必ず書く。
- `files` には対応するファイルを書く。**すべて `impact` に含める**（verify が確かめる）。
- テストのための補助（テスト用のクラス、テストのファイル）はコンポーネントにしない。ファイルは `impact` にだけ書く。

### dependencies

- 「from が to を使う」関係を書く。HTMLの構成図になる。
- 既存のコンポーネントとの関係も、今回の変更に関わるものは書く。

### interfaces

- 公開する関数、クラス、HTTP API、イベントなどを、**対象プロジェクトの言語で**書く（`signature`）。
- `change` に `new`（新規）、`modified`（変更）、`removed`（削除）を書く。
- 既存のインターフェースを変更・削除する場合は、`compatibility` に**呼び出し元への影響と互換の扱い**を書く（型で必須）。
  呼び出し元を検索して件数と場所を確かめ、「旧シグネチャを残して非推奨にする」「呼び出し元もすべて直す」などを決める。
- 他の人のissueがこのインターフェースを使う予定なら（新規案件でよくある）、先に取り決めて変えないようにする。
  逆に他の人のissueのインターフェースを使う場合は、そのブランチの design.ts を読む:
  ```sh
  git show origin/<ブランチ名>:docs/specs/<その人のID>/design.ts
  ```

### dataModels

- テーブル、型、スキーマなどを、対象プロジェクトの言語やDDLで書く。
- 既存のデータモデルを変える場合は `kind: "modified"` とし、`migration` に**既存データの移行方法**
  （マイグレーション、既存の値の扱い、巻き戻し方）を書く（型で必須）。

### errorHandling

- 要件の異常系それぞれに、どう対処するかを書き、`refs` に対応する要件・受け入れ条件のIDを書く。
  **異常系の受け入れ条件（`kind: "error"`）と、EARSの `unwanted` の要件は、すべてどれかのエラー処理に対応させる**（verify が確かめる）。
- 外部との通信、入力の検証、永続化の失敗など、要件に書かれていない異常にも対処を決める（`refs` は省いてよい）。

### impact

- 作成・変更・削除するファイルを、リポジトリのルートからの相対パスで**漏らさず**書く。
- 他のブランチとの衝突の確認（conflicts）と、実装の範囲の確認（sdd-impl）に使う。
  ここに無いファイルを実装中に変える必要が出たら、先に設計を直すことになる。
- 新規案件では、共通の型、マイグレーション、ルーティングやDIの登録箇所など、**他の人と衝突しやすい共有ファイル**を特に漏らさない。

### decisions

- 設計の途中で選択肢があったものを書く。代替案と、採用しなかった理由も書く。
- 次の場合は `adr: true` にする（sdd-finish で `docs/sdd/adr/` に記録する）。
  - 新しいライブラリを導入する
  - 新しいパターンや作法を導入する（今後の実装も従うもの）
  - 構成に関わる判断（モジュールの分け方、データの持ち方など）

### traceability

- すべての機能要件（FR）と非機能要件（NFR）について、それを実現するコンポーネントを1つ以上書く。漏れると型エラーになる。
- 変えてはいけない振る舞い（INV）は traceability には書かない（テストタスクで確かめる）。

### nfrStrategy と invariantStrategy

- `nfrStrategy`: 非機能要件ごとに、**どう実現するか**を書く（例:「主キーでの検索1回で済ませる」「結果を5分キャッシュする」）。
  traceability はコンポーネントを挙げるだけなので、手段はここに書く。全件必須（型で強制される）。
- `invariantStrategy`: 変えてはいけない振る舞いごとに、**設計でどう守るか**を書く
  （例:「応答の組み立て部分には手を入れない」「旧APIを残し、新しいAPIを並べる」）。全件必須（型で強制される）。
- sdd-impl の `next` は、タスクがこれらの要件に関わるときに、実現方法・守り方を表示する。

### checklist（設計のチェックリスト）

設計を書き終えたら、次の観点を1つずつ点検し、結果を `checklist` に書く（全項目が必須。型で強制される）。
設計は人がレビューしないので、この点検が設計の抜けを見つける主な手段になる。結果はHTMLに表示される。

| 項目 | 点検すること |
|---|---|
| `conventions` 既存の作法 | どの既存実装に合わせたか（ファイル名を挙げる）。新しいやり方を持ち込んでいないか |
| `security` セキュリティ | 認可（誰が操作できるか）、入力の検証、秘密情報の扱い、ログに個人情報を出さないか |
| `dataIntegrity` データの整合性 | トランザクションの範囲、同時に更新された場合、途中で失敗した場合 |
| `performance` 性能 | N+1、インデックス、大量データ、繰り返し呼ばれる処理 |
| `observability` ログと調査 | 障害時に原因を調べられるか（何をどのレベルでログに出すか） |
| `testability` テストのしやすさ | 依存（時刻、外部サービス、DB）を差し替えられるか、テストの置き場所 |
| `rollback` 戻し方 | リリースで失敗したときの戻し方（マイグレーションの巻き戻し、機能の切り替え） |
| `sharedFiles` 共有ファイル | 他の人と衝突しやすい共有ファイル（共通の型、ルーティング、DIの登録、マイグレーション）の変更を最小にしたか |

- `result: "considered"` の場合、`note` には「どのコンポーネント・設計判断・エラー処理に反映したか」を書く。
- `result: "notApplicable"` の場合、`note` には関係しない理由を書く。
- 点検の結果、設計の不足が見つかったら直す。判断できない選択が見つかったら、1件ずつ質問する。

### conventionsCompliance（手で守る規約の守り方）

`docs/sdd/conventions.ts` の規約のうち、品質ゲートで強制していないもの（`enforcedBy: "manual"`）は、
ツールでは検出されないので、設計で守り方を決めて書く（verify が全件あるかを確かめる）。

- 書き方: 「〇〇を△△に置く」「新しいモジュールを足すので、Tailwind の content と ESLint の対象に `Modules/*` のパターンで含める」のように、
  この設計で具体的に何をするかを書く。
- 関係しない規約は「該当しない: 理由」と書く。
- 品質ゲートで強制している規約（`enforcedBy: "gate"`）は書かなくてよい。

### ADR の漏れ

依存関係の定義（`package.json`、`pyproject.toml` など）を変える設計なのに、decisions に `adr: true` のものが無いと、
完了時（finish-report）にエラーになる。新しい依存を入れるときは、必ず選定の理由と代替案を decisions に書き、`adr: true` にする。

### risks

- 既存のインターフェースの変更による影響、性能の懸念、architecture.ts との食い違いなど、レビューで見てほしい点を書く。
