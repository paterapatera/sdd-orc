# 質問のしかた（要件定義と設計）

要件定義（sdd-req、sdd-quick）と設計（sdd-design）で、推測で決められないことをユーザーに聞くときの手順。

## 1件ずつ聞く

**質問は1件ずつ聞き、回答を受け取ってから次の質問を考える。** まとめて聞かない。
回答の内容によって、次に聞くべきことが変わったり、聞く必要が無くなったりするためである。

## 質問ツールを使う

使っているツールに構造化された質問の機能（Cursor の AskQuestion など、選択肢を選んで答えられるもの）があれば、**必ずそれを使う**。
文章だけで質問しない（ユーザーは選択形式で答えたい）。

- **1回の呼び出しに入れる質問は1問だけ**にする。質問ツールが複数の質問をまとめて出せても、まとめない。
- 選択肢には、推奨するものに「（推奨）」を付ける。自由に書ける選択肢（その他）も残す。
- 選択肢の利点・欠点は、質問の本文（prompt）か選択肢の説明に書く。選択肢の名前（ラベル）だけにしない。
- 例外: sdd-start と sdd-finish の確認ポイント、sdd-init の事務的な確認は、互いに依存しないので1回にまとめてよい。

## 手順

1. 聞くべきことを洗い出す（ユーザーには見せない、自分用の一覧）。
2. その中から、**回答が他の質問に最も影響するもの**を1件選んで聞く。
   目安: 範囲や方針に関わるもの → 主な振る舞い → 細部（表示の形式、境界値、エラーの扱い）の順。
3. 回答を受け取ったら、次を行う。
   - 回答を spec（requirements.ts、spec.ts、または design.ts の decisions）に反映する
   - 残りの一覧を見直す。回答で決まったものは消し、前提が変わったものは聞き方を変え、新しく必要になったものは加える
4. 一覧が空になるまで2と3を繰り返す。
5. 一覧が空になったら、スキルの手順に戻る（要件定義なら、要件全体の確認に進む）。

## 1件の質問の形

次を1つの返答にまとめ、質問を示したら返答を終える。

- 何を決めたいか（1文）
- なぜ issue・要件・コード・規約などから決められないか（1〜2文）
- 選択肢（2〜3個）と、**それぞれの利点・欠点**（選択肢の名前だけにしない）
- 推奨する選択肢と、その理由
- 選択肢が言語・フレームワーク・ライブラリの版を含む場合は、**提案する前に現在の最新版を調べる**（公式サイト、パッケージの登録先）。
  覚えている版で推奨しない
- 残りの質問のおおよその件数（例:「このほかに2件ほど確認したいことがあります」）。見通しを伝えるため

## 守ること

- 1つの返答に複数の質問を入れない。「ついでに」別のことを聞かない。
- 回答が曖昧で決めきれない場合は、同じ点を聞き直す（次の質問に進まない）。
- ユーザーが「任せる」と答えた場合は推奨の選択肢で決め、そのことを spec に書く（要件なら `assumptions`、設計なら decisions の `context`）。
- 質問が無ければ、質問せずに進む。質問のための質問をしない。
