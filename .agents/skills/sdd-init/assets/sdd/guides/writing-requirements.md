# 要件の書き方

完全モードの `requirements.ts` と、軽量モードの `spec.ts`（`expected` と `invariants`）で共通の書き方。
型の定義は `docs/sdd/schema/requirements.ts` にある。

## 機能要件: EARSで規則を書き、Given/When/Thenで具体例を書く

- EARSで、全体に通じる**規則**を1つ書く。
- 受け入れ条件（Given/When/Then）で、その規則を確かめる**具体例**を書く。

### EARSの型の選び方

| 型 | 使う場面 | 書き方の例 | HTMLでの文章 |
|---|---|---|---|
| `ubiquitous` | 常に成り立つ | response: 「パスワードをハッシュ化して保存しなければならない」 | システムはパスワードをハッシュ化して保存しなければならない。 |
| `event` | 何かが起きたとき | trigger: 「利用者が保存ボタンを押した」 | 利用者が保存ボタンを押したとき、システムは… |
| `state` | ある状態の間 | state: 「メンテナンス中である」 | メンテナンス中である間、システムは… |
| `optional` | 機能や設定が有効な場合 | feature: 「二要素認証が有効な」 | 二要素認証が有効な場合、システムは… |
| `unwanted` | 異常な状況 | condition: 「外部APIが5秒以内に応答しない」 | もし外部APIが5秒以内に応答しないならば、システムは… |
| `complex` | 状態＋出来事 | state: 「ログインしている」、trigger: 「セッションが切れた」 | ログインしている間、セッションが切れたとき、システムは… |

各項目は、上の文章にそのままつながる形で書く。

- `response` は「〜なければならない」で終える（verify が警告する）。動詞は正しく活用する
  （「返さなければならない」「表示しなければならない」。「返しなければならない」は誤り）。
- `trigger` は過去形で終える（「押した」「受信した」）。
- `state` は状態で終える（「ログインしている」「メンテナンス中である」）。
- `feature` は「〜が有効な」「〜を契約している」などで終える。
- `subject` は、主語が「システム」でない場合だけ書く（例: 「バッチ処理」「管理画面」）。

HTMLで組み立てた文章が日本語として自然に読めるかを、必ず確かめる。

### 1つの要件には1つの振る舞いだけを書く

「〜し、かつ〜しなければならない」のように複数の振る舞いをまとめない。分けて別の要件にする。

### 実装の詳細は要件に書かない

DBの列の制約（NOT NULL）、マイグレーションの方法、クラスやファイルの構成などは、要件ではなく設計（design.ts）に書く。
要件には、利用者や外部から見た振る舞いだけを書く。

### 曖昧な言葉を使わない

次の言葉は、テストできる形に言い換える。

| 使わない | 言い換えの例 |
|---|---|
| 適切に、正しく、きちんと | 何をもって適切かを具体的に書く |
| 高速に、すばやく | 目標値を書き、非機能要件にする |
| など、等、ほか | 対象をすべて列挙する |
| または同等、相当 | 何をもって同等とするかを書く。決められなければ未確定の点にする |
| A または B（期待する結果の中） | 結果を1つに決める。条件によって変わるなら、受け入れ条件を分ける |
| 可能な限り、なるべく | 必須か任意かを決める（`priority`） |
| 使いやすい、分かりやすい | 確かめ方を決める。決められなければ未確定の点にする |

### 受け入れ条件（Given/When/Then）

- `given`: 前提となる状態。具体的な値を使う（「失敗回数が4回である」）。
- `when`: 1つの操作や出来事だけを書く。
- `then`: 外から観察できる結果を書く。内部の実装の詳細は書かない。
- `verifiedBy`: 確かめ方を書く。
  - `human`: 人が受け入れテストで確かめる。**`then` は、人が画面を見て・操作して分かる形で書く**
    （「『アカウントがロックされています』と表示される」「トップページに移動する」）。
    HTTPステータスやヘッダ、ログ、DBの値は人には確かめにくいので、human の `then` には書かない。
  - `automated`: 自動テストだけで確かめる。HTTPステータス、ログの出力、
    人が再現しにくい状況（15分の経過、1万件のデータ、外部サービスの障害）など。
    品質ゲートやツールそのものの成否（gate が通る、lint が失敗する）は受け入れ条件にしない（下の「基盤issueの受け入れ条件」）。
  - 人が確かめる受け入れ条件は、**受け入れテストで確かめる価値のある振る舞いに絞る**。人の負担を増やさないため、
    同じことを確かめる受け入れ条件を重ねない。
- 各受け入れ条件に種類（`kind`）を付ける: `normal`（正常系）、`boundary`（境界値: 0件、上限ちょうど、ちょうど5回目など）、`error`（異常系: 不正な入力、権限が無い、外部の失敗など）。
- 1つの機能要件に、**正常系を1件以上**つける。**境界値と異常系も1件以上**つけるのが原則で、つけない場合は
  `notApplicable.boundary` / `notApplicable.error` に理由を書く（verify が確かめる）。
  「思いつかなかった」は理由にならない。境界となる値や、失敗する状況が本当に無いことを書く。
- **検査を通すための水増しをしない。** 境界値・異常系の受け入れ条件は、その要件の振る舞いの境界や失敗を確かめるものにする。
  悪い例:
  - 「テストが1本だけ存在する → その1本が通る」（要件の振る舞いの境界ではない）
  - 「Deno が無い環境 → deno が見つからないと表示される」（ツールそのものの振る舞いで、要件と関係が無い）
  - 「README と composer.json の版が一致する」を別の受け入れ条件で2回確かめる（重複）
  本当に境界や異常が無い要件は、`notApplicable` に理由を書くのが正しい。
- 人は受け入れテストだけを行うので、**受け入れ条件の漏れは、そのまま品質の漏れになる**。

### 基盤issueの受け入れ条件

基盤issue（新規案件で、機能の前に土台を作るissue）では、環境やツールそのものを試す受け入れ条件を作りすぎない
（試行で、テストの中から docker や品質ゲートを起動し、無限に再帰して止まった）。次の形を基本にする。

| 確かめること | 確かめ方 |
|---|---|
| アプリが起動し、最初の画面が表示される | human（acceptanceGuide の手順で起動して画面を見る）と E2E のスモークテスト1件 |
| 品質ゲートが通る | 受け入れ条件にしない。sdd-impl と finish-report が `deno task gate --full` を実行して確かめる |
| 層やモジュールの規則が守られている | 受け入れ条件にしない。規約を gate で強制する（アーキテクチャテストや Deptrac など） |
| 画面の土台（UIの部品、デザイントークン、レイアウト）が使える | human（最初の画面で見た目を確かめる）と E2E のスクリーンショット |

- ポートの競合、マイグレーションの失敗のような、環境の異常系は `notApplicable` にしてよい（理由を書く）。
- 「README の手順どおりに動く」は、acceptanceGuide を `deno task acceptance` で実行して確かめるので、受け入れ条件にしない。

## 非機能要件

- `docs/sdd/nfr.ts`（プロジェクト全体の基準）との**差分だけ**を書く。基準をそのまま満たせばよいなら書かない。
- 書かなかったことと検討しなかったことを区別するため、`nfrReview` に IPA の6つのカテゴリすべての扱いを書く（型で強制される）。
  - `baseline`: 基準のままでよい。nfr.ts にそのカテゴリの基準が無い場合も、このissueで追加の要求が無ければ baseline にする。
    nfr.ts にそのカテゴリの基準（`BNFR-xxx`）がある場合は、tasks でその基準を確かめる（verify が確かめる）。
    このissueに関係しない基準は `waived` に理由を書く（例: `waived: { "BNFR-002": "画面を変えないため" }`）
  - `added`: 非機能要件を追加・上書きした（`ids` に NFR-xxx）
  - `notApplicable`: このissueには**関係しない**（`reason` に理由）。関係するのに「基準が無いから」という理由で使わない。
    例: 認証、権限、利用者のデータを扱うissueでは、セキュリティは関係する（baseline か added にする）
  - 追加した非機能要件は、必ずそのカテゴリの `added` に挙げる（verify が確かめる）。
- 基準を変える場合は `overrides` に基準のID（`BNFR-xxx`）を書く。
- 「何を測るか」「目標値」「条件」「確かめ方」をすべて具体的に書く。測れないものは書けない。
- カテゴリは IPA「非機能要求グレード」の大項目から選ぶ。

## 変えてはいけない振る舞い（INV）

既存のコードを変更するときに、壊してはいけない振る舞いを書く。既存案件で一番事故が起きやすい部分である。

探し方:

1. 変更するコードを呼び出している箇所（呼び出し元）を調べる。
2. 公開API（HTTP、ライブラリの公開関数、CLI）の入出力の形式を調べる。
3. 保存されているデータの形式（DB、ファイル、キャッシュ）を調べる。

各項目の `verification` には、どう確かめるかを書く（「既存の〜のテストが変更なしで通る」「〜の応答を比較する」）。
確かめるテストが無ければ、タスクで「現状の振る舞いを固定するテスト」を追加する。

該当するものが無い場合は `invariants: {}` とし、`noInvariantsReason` に理由を書く（verify が確かめる）。
例:「新規作成で、既存のコードや保存データに触れないため」。

## issue の受け入れ条件との対応（issueCoverage）

issue.md の「受け入れ条件」の箇条書きを、1項目ずつ**そのまま** `source` に写し、それを満たす要件のIDを `coveredBy` に書く。
要件にしない項目は、`excluded` に理由を書く（対象外にした、別issueにしたなど）。
verify は、issue.md の箇条書きがすべて `source` にあるかを確かめる（issue の要望の取りこぼしを防ぐ）。
issue.md に受け入れ条件が無い（「未記載」）場合は `[]` にする。

## 十分性のチェックリスト（checklist）

要件全体の確認を頼む前に、次の観点を1つずつ点検し、結果を `checklist` に書く（全項目が必須。型で強制される）。
結果はHTMLの「十分性の確認」に表示され、人が要件を確認するときの手がかりになる。

| 項目 | 点検すること |
|---|---|
| `actors` 利用者の種類と権限 | 誰が使うか。種類によって振る舞いが変わるか（管理者、一般、未ログイン）。権限が無い場合の受け入れ条件はあるか |
| `dataStates` データの状態 | 0件、1件、上限ちょうど、上限超え、重複、削除済み・無効なデータのとき、どうなるか |
| `inputValidation` 入力の検証 | 必須、形式、長さ、範囲。不正な入力の受け入れ条件はあるか。**URLのクエリやパスの値も入力に含める** |
| `errorFeedback` 失敗時の伝え方 | 失敗したとき、利用者に何をどう伝えるか（文言、画面、応答）。受け入れ条件で決めたか |
| `existingData` 既存への影響 | 既存のデータや利用者に影響するか（移行、互換、既存の画面の変化） |
| `consistency` 矛盾と用語 | 要件同士が矛盾していないか。同じものを別の言葉で呼んでいないか |
| `outOfScope` 対象外の明示 | 誤解されやすい周辺の機能を、対象外として明示したか |

- `result: "considered"` の場合、`note` には「どの要件・受け入れ条件で扱ったか」を書く（例:「0件のときの表示を AC-005 で決めた」）。
- `result: "notApplicable"` の場合、`note` には関係しない理由を書く。
- 点検の結果、足りない受け入れ条件が見つかったら追加する。決められないことが見つかったら `openQuestions` に書き、質問する。

## 分からないことは推測で埋めない

- issueに書かれておらず、コードからも判断できないことは、`openQuestions`（未確定の点）に書き、ユーザーに質問する。
- **利用者から見える振る舞いは、issue に明記されていなければ、既存のコードに既定の動きがあっても質問する。**
  既存のコードの動きは、今回の要望に合っているとは限らない。例:
  - 表示する文言やラベル（0件のときの文言、ステータスの表記）
  - 並び順、1ページの件数
  - 操作の後の遷移先（ログイン後、登録後）
  - 既存の画面や機能を残すか、置き換えるか、削除するか
  - 不正な入力への対応（URLのクエリやパスの値も入力に含める。例: `page=0`、負の値、数字でない値）
- 要件全体の確認を頼む前に、`assumptions`（前提）を見直す。**利用者から見える振る舞いに関わる前提は、確認の前に1件ずつ質問する。**
  前提に残すのは、利用者から見えない技術的な前提だけにする。
- 質問は `docs/sdd/guides/asking-questions.md` に従い、**1件ずつ**聞く（回答によって次の質問が変わるため）。選択肢と推奨を添える。
- 回答をもらったら、要件に反映して `openQuestions` から消し、残りの未確定の点を見直してから次を聞く。

## IDの振り方

- 3桁のゼロ埋め（`FR-001`、`AC-001`、`INV-001`、`NFR-001`）。
- `AC` の番号は、issueの中で要件をまたいで通し番号にする。
- 一度振ったIDは振り直さない。削除した場合は欠番のままにする（レビューでIDを使ってやり取りするため）。
