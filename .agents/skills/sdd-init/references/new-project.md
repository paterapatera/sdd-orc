# 新規案件での恒久ドキュメントの作り方

新規案件にはまだコードが無い。リーダーと対話しながら、全員のAIが共通の前提にする内容を決める。
ここで決めずに issue のフローを始めると、issue ごとにばらばらの前提で設計されてしまう。

## 1. 対話で決める

次の順に質問する。質問ツールがあれば使い、回答によって次の質問が変わるので1問ずつ聞く。
ユーザーが決めていない項目は、選択肢と推奨を示してよいが、決めるのはユーザーである。
選択肢に言語・フレームワーク・ライブラリの版が含まれる場合は、提案する前に現在の最新版を調べる。

1. **システムの概要**: 何をするシステムか、誰が使うか、規模感（利用者数、データ量）
2. **技術スタック**: 言語、フレームワーク、DB、インフラ、主要なライブラリ（版も）
3. **構成の方針**: モジュールの分け方、層の構成と依存のルール、ディレクトリの規約
4. **画面とデザインの方針**（画面がある場合）: 次を**すべて**、1問ずつ決める（試行で、デザイントークンとレイアウトを聞き漏らした）。
   - スターターキットや雛形を使うか（例: Laravel Breeze）。使う場合、どの画面や機能（認証、プロフィールなど）を残すか
   - UIのコンポーネントの仕組み（例: shadcn/ui、MUI、Mantine、自作。shadcn/ui のようにコードをリポジトリに取り込むものか、パッケージとして使うものか）
   - デザインシステム（色、文字の大きさ、余白、角の丸みなどの決まり＝デザイントークン）。既存のガイドラインやブランドの色があるか
   - CSS の書き方（例: Tailwind CSS、CSS Modules）。コンポーネントの仕組みと合うものにする
   - アイコン（例: lucide）、フォント
   - レイアウトの骨組み（ヘッダー、ナビゲーション、ページの幅）
   - 対応する画面の幅（PCだけか、スマートフォンも含めるか）、ダークモードの要否
   - アクセシビリティの目標（例: WCAG 2.2 AA）
5. **規約**: 命名、エラー処理、ログ、テストの書き方と置き場所、画面の部品の使い方（4で決めた部品とトークン以外を使わない、など）
6. **ツールの選定**: `references/tooling.md` の手順で、品質ツール（propose-quality-tools を自分で実行する）、テストのツール（E2E を含む）、
   規約を強制するツールを選定し、1つの提案として確認してもらう。**ユーザーに propose-quality-tools の実行を頼まない。**
7. **非機能要件**: IPA「非機能要求グレード」の大項目ごとに、目標値があるかを聞く
   - 可用性、性能・拡張性、運用・保守性、移行性、セキュリティ、システム環境・エコロジー
   - 目標値が決まっていない項目は書かない（推測の値を入れない）

## 2. 書く

- `docs/sdd/architecture.ts`: 上の1〜3の内容（4のライブラリは技術スタックに含める）。
  - `basedOn` には `git rev-parse HEAD` の結果を入れる。コミットがまだ無ければ `"none"` とし、
    基盤issueの完了時（sdd-finish）に更新する。
  - `modules` には、基盤issueで作る予定のモジュールを書く。
- `docs/sdd/conventions.ts`: 上の4〜6の内容（画面の部品とデザイントークンの使い方、採用したツールと、その使い方）。
  各規約に、ツールで強制しているか（`enforcedBy`）を書く。
- `docs/sdd/nfr.ts`: 上の7のうち、目標値が決まったものだけ。
- `docs/sdd/config.ts` の `commands`: まだツールが無いので空のままにする（基盤issueで登録する）。
- `docs/sdd/adr/ADR-0001.ts` 〜: 技術選定ごとに1件ずつ（UIのコンポーネントの仕組み、CSS、品質ツール、テストのツールの選定も含む）。
  理由と、検討した代替案をユーザーに聞いて書く（「なぜこのフレームワークにしたか」が半年後に分かるように）。

## 3. 基盤issueを案内する

**基盤issue**とは、新規案件で機能の開発を始める前に、全員がその上で開発できる土台（雛形、共通の部品、品質ツールとテストの土台、
画面の土台など）を作るためのissueである。機能はまだ作らない。

何も無い状態から複数人が同時に始めると、全員がディレクトリ構成や共通モジュールを作ろうとして衝突する。
そこで、並行開発を始める前に1人で片付ける基盤issueの文面を作り、ユーザーに渡す。
ユーザーはそれを issueトラッカーに登録する。

基盤issueに含める内容の例:

- プロジェクトの雛形とディレクトリ構成（architecture.ts の modules に沿う）
- 共通の型、共通のエラー処理、ログ
- 画面の土台（画面がある場合）: 4で決めたものを**実際に導入する**（UIのコンポーネントの仕組みの初期化と基本部品の追加、
  デザイントークンの定義、フォントとアイコンの導入、レイアウトの骨組み）。設定ファイルを置くだけにしない
  （試行で、shadcn/ui の設定ファイルだけを置き、部品もトークンも入っていなかった）。
- 規約の強制: `references/tooling.md` の提案で gate にすると決めた規約について、そのツールと設定を導入し、`conventions.ts` を gate に変える
- DB接続とマイグレーションの仕組み
- 品質ゲート: propose-quality-tools の提案どおりにツールを導入し、`docs/sdd/config.ts` の `commands` に
  `format`、`check`、`test` を登録する（`deno task --config docs/sdd/deno.json gate` が通る状態）
- テストの土台（単体・結合テストが1件動き、画面があるなら E2E テストが1件動く状態。`commands` に `e2e` も登録する）
- CI（使う場合）

あわせて、次を伝える。

- 基盤issueは1人で担当し、マージしてから機能issueの並行開発を始める。
- 基盤issueも sdd-start から通常のフロー（完全モード）で進める。sdd-init の続きとして直接実装して main にコミットしない。
- 基盤issueの作成は、`forge` を登録していれば了承を得てCLIで行ってよい。
