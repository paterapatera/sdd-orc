# ツールの選定（品質、テスト、規約の強制）

人はコードレビューを行わないので、コードの品質と画面の正しさは、ツールで担保するしかない。
sdd-init では、技術スタックと画面とデザインの方針が決まったら**ユーザーに頼まれなくても**、次の3つを選定して1つの提案にまとめ、確認してもらう。

1. 品質ツール（フォーマッタ、lint、型チェック、境界ルールなど）
2. テストのツール（単体・結合、E2E）
3. 規約を強制するツール（手で守るしかない規約を、品質ゲートで検出できるようにする）

試行では、品質ツールの選定をユーザーが指示するまで行わず、E2E のツールも無かったため、画面の崩れに受け入れテストまで気づけなかった。

## 0. 前提をそろえる

- 言語ごとに、規模（S / M / L）を聞く（`.agents/skills/propose-quality-tools/SKILL.md` の規模の定義を示す）。推測で決めない。
- 画面があるか（Web の画面、CLI だけ、API だけ）を確かめる。E2E の要否と方式が変わる。
- 既存案件では、既存のツール（`package.json`、`composer.json`、`pyproject.toml`、CI の設定など）を調べる。既存のものを優先し、差分を提案する。

## 1. 品質ツール

`.agents/skills/propose-quality-tools/SKILL.md` を読み、その手順で、**言語ごとに**提案を作る（ユーザーに `/propose-quality-tools` の実行を頼まない）。
既存のツールがあれば、その差分の提案（re-propose-diff）になる。

## 2. テストのツール

propose-quality-tools はテストのツールを扱わないので、ここで選ぶ。役割ごとに1つずつ選び、重ねない。

| 役割 | 目的 | 選び方 |
|---|---|---|
| 単体・結合テスト | 関数やクラス、API の振る舞いを確かめる | その言語・フレームワークの標準的なものを選ぶ（既存があればそれ） |
| E2E テスト | 利用者と同じ操作（画面を開く、入力する、押す）をして、表示と遷移を確かめる。**画面があるなら必須** | ブラウザを操作できるもの。言語やフレームワークに依存しにくいものを優先する |
| 画面の見た目の確認 | スタイルの崩れ（CSS が読み込まれない、レイアウトが崩れる）を検出する | E2E のツールでスクリーンショットを比べる機能があれば、それを使う（別のツールを足さない） |
| アクセシビリティ（任意） | 画面の基本的なアクセシビリティの問題を検出する | E2E のツールに組み込めるものを選ぶ |

既定の候補（**提案する前に、公式の資料で現在の版と使い方を確かめる**。覚えている版で推奨しない）:

| 技術スタック | 単体・結合 | E2E |
|---|---|---|
| TypeScript / JavaScript（フロントエンド） | Vitest（コンポーネントには Testing Library） | Playwright |
| PHP / Laravel | Pest または PHPUnit（既存に合わせる） | Playwright（Laravel Dusk は PHP だけで書ける代わりに、ブラウザの扱いが限られる） |
| Python | pytest | Playwright（pytest-playwright） |
| Go | go test | Playwright |
| Java / Kotlin | JUnit 5 | Playwright |
| Rust | cargo test（または cargo-nextest） | Playwright |

E2E を品質ゲートに入れるときの決まり:

- `docs/sdd/config.ts` の `commands.e2e` に登録する。タスクごとの品質ゲートには含まれず、`deno task gate --full` で実行される
  （sdd-impl の完了時と sdd-finish の開始時）。
- アプリの起動（Docker、開発サーバー）、テスト用のデータとアカウントの用意も、E2E のコマンドの中で行えるようにする
  （人が手順を覚えていなくても、コマンド1つで実行できるように）。
- 人が確かめる受け入れ条件（`verifiedBy: "human"`）は、E2E テストでも確かめる。人の受け入れテストより先に、AIが画面の誤りに気づけるようにするため。

## 3. 規約を強制するツール

規約（`conventions.ts`）を書いたら、手で守るしかないもの（`enforcedBy: "manual"`）を1件ずつ見て、ツールで強制できないかを検討する。
試行では、ツールで強制されている規約だけが確実に守られた。

| 規約の種類 | 強制のしかたの例 |
|---|---|
| レイヤーやモジュールの依存の向き | PHP: Deptrac、PHPat、Pest のアーキテクチャテスト / TypeScript: dependency-cruiser、eslint-plugin-boundaries / Java: ArchUnit / Python: import-linter |
| ファイルやディレクトリの置き場所、命名 | ls-lint、または置き場所を確かめるテスト（アーキテクチャテスト） |
| 特定の書き方の禁止・必須（例: Domain で特定のクラスを使わない、ページは特定の場所からだけ描画する） | Semgrep、ast-grep（言語をまたいでパターンで検査できる）、または lint の独自ルール |
| 画面の部品とデザイントークンの統一（例: 決めたコンポーネントだけを使う、トークン以外の色や余白を直接書かない） | lint の独自ルールやプラグイン（Tailwind の任意の値の禁止、特定のUIライブラリの読み込みの禁止など）、stylelint、Semgrep。画面の崩れは E2E のスクリーンショットの比較で検出する |
| パッケージマネージャーの統一（例: Bun だけを使う） | 他のツールのロックファイル（`package-lock.json` など）があれば失敗する検査を、品質ゲートに入れる |
| 設定の漏れ（例: 新しいモジュールを Tailwind や lint の対象に入れ忘れる） | 設定にモジュール名を1つずつ書かず、`Modules/*` のようなパターンで書く。書けない場合は、設定とディレクトリを突き合わせるテストを書く |
| コミットメッセージの形式 | commitlint など（SDD のタスクのコミットは、finish-report が形式を確かめる） |

- 強制できるものは、規約の `enforcedBy` を `"gate"` にし、`tool` にツールと設定ファイルを書く。
- 強制できないもの（設計の判断に関わるものなど）は `"manual"` のまま残す。設計の `conventionsCompliance` で守り方を書かせる。
- 強制のためにツールを増やしすぎない。1つのツール（Semgrep やアーキテクチャテストなど）で複数の規約を強制できるなら、それを選ぶ。

## 4. 提案の形

3つをまとめて、1つの提案として**本文に**示し、そのうえで質問ツールでは「採用」か「修正」かだけを聞く。
提案の中身を質問ツールの短い文に詰め込まない（試行で、要約しか示されず、ユーザーが propose-quality-tools を自分で実行し直した）。
品質ツールの部分は、propose-quality-tools の出力の形式（採用、不採用、設定スケッチ、スクリプト）をそのまま含める。

**主な設定値の表を必ず含める。** 試行で、PHPStan が提案に無い level 5 で導入され、ユーザーが気づかなかった。

| ツール | 設定 | 値（規模に応じた推奨） |
|---|---|---|
| 例: PHPStan / Larastan | level | max |
| 例: TypeScript | strict など | strict: true、noUncheckedIndexedAccess: true … |
| 例: 複雑度の lint | しきい値 | … |

```
# ツールの提案

## 品質ツール（<言語>、規模 <S|M|L>）
<propose-quality-tools の出力の要点: 採用するツール、不採用とその理由>

## テストのツール
| 役割 | ツール | 理由 | 不採用にした候補 |

## 規約を強制するツール
| 規約 | 強制のしかた（ツールと設定） | gate にできない場合の理由 |

## 品質ゲートのコマンド（config.ts の commands）
format / check / test / e2e のコマンドの案
```

採用が決まったら、次を行う。

- **提案した設定値より弱くしない。** 導入で問題が出ても、レベルを下げたり対象を絞ったりせずに直す。
  どうしても緩めるなら、ユーザーに質問して理由を記録する（finish-report が、緩めた変更を検出する）。

- 採用したツールと使い方を `conventions.ts` に、選定の理由を ADR に記録する。
- 新規案件: ツールの導入と `commands` の登録を基盤issueに含める（`references/new-project.md`）。
- 既存案件: 導入は別のissueで行うよう勧める（既存のコードに大量の指摘が出ることが多いため）。今あるコマンドは `commands` に登録する。
