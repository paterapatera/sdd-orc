# 既存案件での恒久ドキュメントの作り方

既存案件では、正しい情報源はコードそのものである。コードと既存の資料を解析して恒久ドキュメントを作る。

**全部を最初から書き起こさない。** 大きなコードベースを一度に網羅しようとすると、質が落ち、古くなるのも早い。
最初は大まかに作り、sdd-finish のたびに、触った部分を詳しくしていく。

## 1. 材料を集める

- README、`docs/` などリポジトリ内の資料
- リポジトリの外にある資料（Wiki、Confluence、RedmineのWikiなど）があるかをユーザーに聞く。
  あれば、内容をファイルに書き出してパスで渡してもらう。
- 依存関係の定義: `package.json`、`pyproject.toml`、`requirements.txt`、`Cargo.toml`、`go.mod`、`pom.xml`、`build.gradle` など
- ディレクトリ構成（上位3階層程度。`node_modules`、`vendor`、`target`、`.venv` などは除く）
- エントリポイント（main、サーバーの起動処理、CLIの定義など）
- テストの置き場所と書き方
- フォーマッタ、リンタ、型チェッカーの設定
- CIの設定
- 最近よく変更されている場所:
  ```sh
  git log --since=6.months --name-only --format= | cut -d/ -f1-2 | sort | uniq -c | sort -rn | head -20
  ```

## 2. 書く

### architecture.ts

- `basedOn` には `git rev-parse HEAD` の結果（完全なハッシュ）を入れる。
  sdd-start はこのコミットからの差分を見て、構成が古くなっていないかを判定する。
- `stack`: 依存関係の定義から、主要なものだけを版付きで書く。
- `modules`: 責務がはっきりしている上位のディレクトリ単位で書く。細かく分けすぎない。
- `layers`: コード上で依存の方向が一貫している場合だけ書く。一貫していなければ書かずに、`notes` に現状を書く。

### conventions.ts

- **複数のファイルで一貫して守られている**ものだけを規約として書く。1か所でしか見られないものは書かない。
- 各項目の `source` に、根拠となるファイルのパスを書く。
- フォーマッタやリンタで強制されている内容は書き写さず、「〜の設定に従う」とだけ書き、`source` に設定ファイルを書く。
- 目安は5〜15件。

### nfr.ts

- 資料やコードで**確かめられた事実だけ**を書く（対応するランタイムの版、SLAの記載など）。
- 目標値が分からない項目は書かず、ユーザーへの質問として挙げる。値を推測して埋めない。

### 画面とデザインの方針（画面がある場合）

- 今使っているUIのコンポーネントの仕組み、CSS の書き方、デザイントークン（Tailwind の設定、CSS 変数など）、アイコン、
  レイアウトの骨組みを、コードと設定から調べる。
- 一貫して使われているものを規約の案にし、ユーザーへの質問に含めて確認してもらう。
  一貫していなければ（画面ごとに書き方が違うなど）、どれに寄せるかをユーザーに聞く。

### ツールの選定と品質ゲート（config.ts の commands）

`references/tooling.md` の手順で、品質ツール、テストのツール（E2E を含む）、規約を強制するツールを、既存のものとの差分として提案する。

- 既存のフォーマッタ、lint、型チェック、テストのコマンドを、`package.json` の scripts、`Makefile`、CIの設定などから探し、
  `commands` の案（`format`、`check`、`test`。まとめた check が無ければ `lint`、`typecheck`）を作る。
  案はユーザーへの質問に含めて確認してもらう。
- 品質ツールが無い、または足りない場合は、propose-quality-tools で差分の提案（re-propose-diff）を作ってユーザーに示す。
  導入は、このPRに含めず別のissueで行うよう勧める（既存のコードに大量の指摘が出ることが多いため）。

### adr/

- 過去の判断をさかのぼってADRにすることはしない。
- 既存の資料に判断の理由がはっきり書かれている場合だけ、ユーザーに確認したうえで記録してよい。

## 3. 確認する

作った内容の要約と、分からなかった点の質問をユーザーに示す。
回答をもらったら反映し、型チェックを通す。

## 4. 途中からの導入について伝える

- specは作業ブランチの中にだけ置き、main には入らない。SDDを使わないメンバーへの影響は `docs/sdd/` が増えることだけ。
- 導入後は、まず1〜2人が完全モードで中規模のissueを試すことを勧める。軽量モード（sdd-quick）は、完全モードで作った機能の後の修正に使う。
- すでに作業中のissueは、SDDを使わずに完了させる。
