# sdd-quick

軽量モードのspec（`docs/specs/<ID>/spec.ts`）を作る。完全モードの要件・設計・タスクを1ファイルにまとめたもの。
軽量モードは、主に完全モードで作った機能の後の修正（バグの修正、小さな仕様変更）に使う。

このスキルのファイル:

- `assets/spec-template.ts`: `spec.ts` のひな形

対象リポジトリの手引き（書く前に必ず読む）:

- `docs/sdd/guides/writing-requirements.md`: 期待する動作（EARS、Given/When/Then）と変えてはいけない振る舞いの書き方
- `docs/sdd/guides/writing-tasks.md`: タスクの書き方
- `docs/sdd/guides/asking-questions.md`: 質問のしかた（1件ずつ聞く）
- `docs/sdd/guides/review-feedback.md`: 指摘を受けたときの手順

`docs/sdd/deno.json` のタスクは、リポジトリのルートで `deno task --config docs/sdd/deno.json <タスク名>` として実行する。
以下では `deno task <タスク名>` と略す。

## 確認ポイント

ユーザーの回答を待つのは、次の場合だけ。質問を示して返答を終え、回答を受け取ってから先に進む。

1. **期待する動作と受け入れ条件の確認（必須）**: spec.ts を書く前に確認してもらう。
   決まっていないこと（出力の形式、エラー時の扱いなど）があれば、先に `docs/sdd/guides/asking-questions.md` に従い
   **1件ずつ**質問し、すべて決まってから、期待する動作・受け入れ条件の案・変えてはいけない振る舞いをまとめて示して確認してもらう。
   人は受け入れテストだけを行うので、受け入れ条件は人と合意した基準でなければならない。
   issue に受け入れ条件が明記されていて曖昧さが無い場合も、spec に書く形で示して確認してもらう。
2. **完全モードへの切り替え**: 手順2の条件に当たったとき。

質問ツール（Cursor の AskQuestion など）があれば使い、1回の呼び出しに1問だけ入れる。
利用者から見える振る舞いで issue に明記されていないものは、既存のコードに既定の動きがあっても質問する。
スキルを呼び出したこと（`/sdd-quick`）は、確認ポイントへの回答ではない。
確認の後は止まらずに最後まで進め、行ったことを最後に報告する。

## 1. 前提を確認する

1. `deno task current` で issue の ID とモードを特定する。
2. `docs/specs/<ID>/issue.md` の「モード」が軽量モードであることを確かめる。
   - issue.md が無い → sdd-start を案内して止まる。
   - 完全モードになっている → sdd-req を案内して止まる。
3. 完全モードのファイル（`requirements.ts` など）があれば、混在になるので止まってユーザーに確認する。
4. `spec.ts` がすでにあれば、作り直すのではなく、手直しとして扱う。

## 2. 調べる

1. `issue.md` と `attachments/` を読む。
2. `docs/sdd/architecture.ts`、`conventions.ts`、`nfr.ts` を読む（あれば）。
3. コードを調べる。
   - **バグの修正**: 症状が出る箇所から処理をたどり、**根本原因**を特定する。症状をふさぐだけの修正方針にしない。
     根本原因は、根拠となるファイルと行をあわせて示せるところまで確かめる。
     コードを読んでも確定できなければ、推測で書かずに確認ポイント1でユーザーに伝え、どう進めるかを相談する。
   - **小さな変更**: 変更する箇所と、その呼び出し元を調べる。
   - どちらの場合も、変更するコードの呼び出し元、公開API、保存データの形式を調べ、変えてはいけない振る舞いを洗い出す。
4. 既存のテストの有無と置き場所を確かめる。

### 完全モードへの切り替え

調べた結果、次のどれかに当てはまったら、確認ポイント2として完全モードへの切り替えを提案する。

- 公開APIやDBのスキーマを変更する必要がある
- 複数のモジュールにまたがる
- 依存ライブラリを追加する必要がある
- タスクが4件以上になる

切り替えることになったら、`issue.md` の「モード」を完全モードに直してコミットし、sdd-req を案内する。
それまでに調べた内容は、要件を作るときに使えるよう報告に含める。

## 3. 確認ポイント1: 期待する動作と受け入れ条件を確認してもらう

1. 決まっていないこと（出力の形式、エラー時の扱いなど）があれば、`docs/sdd/guides/asking-questions.md` の手順で
   **1件ずつ**質問する。回答のたびに残りの質問を見直し、すべて決まるまで繰り返す。
2. すべて決まったら、次を示して回答を待つ。
   - 期待する動作（EARSの文章の形で）と、受け入れ条件の案（Given/When/Then、具体的な値で。境界値と異常系も）
   - 変えてはいけない振る舞い
   - バグの修正なら、根本原因とその根拠
   - 質問への回答で決まったこと

## 4. spec.ts を書く

回答を反映して、`assets/spec-template.ts` をもとに `docs/specs/<ID>/spec.ts` を書く。手引きに従う。

- `kind`: バグの修正は `"bugfix"`（`cause` が必須）、それ以外は `"change"`（`cause` を削除する）。
- `expected`: 確認ポイント1で合意した期待する動作と受け入れ条件。**合意していない受け入れ条件を足さない。**
- `invariants`: 変えてはいけない振る舞い。無ければ `{}` にし、`noInvariantsReason` に理由を書く。
- 受け入れ条件には種類（正常系・境界値・異常系）を付け、境界値・異常系が無い場合は `notApplicable` に理由を書く。
- 受け入れ条件と変えてはいけない振る舞いには確かめ方（`verifiedBy`）を付ける。人が確かめるもの（human）は、画面で分かる形で書く。
- `issueCoverage`: issue.md の受け入れ条件の各項目と、期待する動作の対応。
- `conventionsCompliance`: 手で守る規約（`conventions.ts` の `enforcedBy: "manual"`）ごとの守り方（関係しなければ「該当しない: 理由」）。
- `checklist`: 十分性のチェックリスト（`docs/sdd/guides/writing-requirements.md`）。確認ポイント1の前に点検しておき、
  見つかった不足は受け入れ条件の案に含める。
- `impact`: 変更・作成・削除するファイル。衝突の確認と実装の範囲に使うので漏らさない。
- `tasks`: 1〜3件。バグの修正では最初のタスクを再現テストにする。

書いたら、次を実行し、エラーが無くなるまで直す。警告は内容を確かめ、直さない場合は理由を報告に含める。

```sh
deno task check <ID>
deno task verify <ID>
```

## 5. 衝突を確かめる

```sh
deno task conflicts --issue <ID>
```

`[重なり]` があれば、どのブランチの作業と重なるかを報告に含め、担当者との調整を勧める。作業は止めない。

## 6. HTMLを生成して、コミットして push する

1. `deno task render <ID>` でHTMLを生成する。
2. `docs/specs/<ID>/` をコミットする。コミットメッセージは `docs(<ID>): specを作成（軽量モード）`。
3. `git push -u origin <ブランチ名>` で push する（他の人の衝突チェックに見えるようにするため）。リモートが無ければ省く。

## 7. 報告する

作った spec の要点、生成したHTMLのパス、衝突の確認結果を報告し、次の工程として sdd-impl を案内する。
