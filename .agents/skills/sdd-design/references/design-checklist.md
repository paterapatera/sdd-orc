# 設計の観点

requirements.md と既存コードを読んだら、次の観点で設計を組み立て、決まっていない点を洗い出す。
質問は上から順に（戻しにくいものから）行う。

## 1. 技術スタックと既存の慣習

- 使っている言語、フレームワーク、ライブラリ、フォルダ構成は何か。根拠のファイル（依存関係の定義、設定ファイル）を確かめたか。
- 似た機能がすでにあるか。あれば、その作り方（層の分け方、命名、エラー処理）に合わせる。
- 既存コードがない場合は、技術スタックの選定を技術判断として質問し、ADRにする。実装を始めるのに必要な基盤（初期設定、DBの接続、テストの設定）を、コンポーネントとして書いたか。
- 新しいライブラリを入れる必要があるか。既存のライブラリで足りないか。
- 選ぶライブラリや方式の制約（上限の単位が文字かバイトか、既定の動き、切り捨てや丸めの有無）を確かめたか。要件の数値と合っているか。
- 他のissueの機能（ログインなど）を前提にしているか。要件の文や受け入れ条件の「前提」も見たか。前提にしているなら、記入ルールの「他の機能との関係」で本当の依存か条件付きの前提かを判断したか。
- 本当の依存なら、その機能が既存コードにあるか、依存先が approved か。
- 条件付きの前提なら、状態を読み取る仕組みを技術判断にしてADRにしたか。後から作る機能の画面や操作まで作っていないか。
- 依存先がまだ実装されていないなら、依存先の design.md を読んだか。依存先のファイルを変えるコンポーネントを `（変更）` にしたか。依存先の design.md にしか書かれていない、他の機能にも影響する決め事を、ADRにしたか。

## 2. コンポーネントの分け方

- 要件ごとに、どのコンポーネントが実現するかが決まっているか。
- 1つのコンポーネントに、関係の薄い役割が混ざっていないか。
- 既存のコンポーネントを変更するか、新しく作るかを、既存の構成に合わせて決めたか。

## 3. 入出力と検証

- コンポーネント同士の入出力（関数の型、APIのメソッドとパスと入出力、画面の表示項目と操作）が決まっているか。
- 入力の検証をどこで行うか（画面、API、サービス、DBの制約）。複数で行う場合、どれが正とするか。
- 検証エラーを、どの形で呼び出し元や利用者に返すか。既存の返し方に合わせているか。
- APIなら、成功とエラーの種類（検証エラー、未ログイン、権限なし、重複、見つからない）ごとのHTTPステータスと応答の形が決まっているか。
- 画面なら、成功したときとエラーのときに、何が表示されて入力欄がどうなるかが決まっているか。
- 関数の戻り値が、非同期の処理（DB、外部サービス）なら `Promise` になっているか。失敗の種類ごとにエラーの型が決まっているか。
- 複数の入力エラーが同時にあるとき、すべて返すのか、最初の1件だけか、どの順で判定するのかが決まっているか。
- 他の機能と同じでなければならないルール（メールアドレスの正規化、文字数の数え方、エラーの形）を、共通の関数を呼ぶ形で守っているか。どのコンポーネントがその処理を行うかが1つに決まっているか（例: 小文字化を検証と保存のどちらで行うか）。
- 並び順を決めるとき、最後に一意な列を加えて並びを決め切ったか。文字列の並びの照合順序を、要件の解釈として決めたか。
- 入出力に書いた値（エラーの code など）が、どれも決めておく振る舞いで使われているか。使われない値が残っていないか。
- 要件の言葉を実装に落とすときに、意味が複数に分かれないか（文字数の数え方、全角と半角、空白の範囲、日付の境界、端数の扱い、「一般的な形式」）。分かれるなら、記入ルールの「要件の解釈」の条件を満たすかどうかで、技術判断にするか要件の問題にするかを決める。

## 4. データ

- 永続化するデータの追加・変更（テーブル、列、型、NULL、一意、初期値、索引）が決まっているか。主キーの形式や値の範囲の守り方が「または」のまま残っていないか。
- 列の文字数の上限と、アプリの検証の数え方が一致しているか。
- 要件にないデータ（将来のための列など）を足していないか。
- 「同じもの」を判定する要件があるなら、それをDBの一意制約で守るか、処理の中で確かめるか。
- 利用者ごとにデータを分ける必要があるなら、その分け方（所有者の列など）が決まっているか。
- 外部キーで参照先を消したときの動きを、対象外の機能（アカウントの削除など）のために先に決めていないか。

## 5. 異常系と同時実行

- 外部サービスやDBの呼び出しが失敗したとき、どうするか（やり直す、エラーを返す）。
- 同時に操作されたときに、データが壊れたり重複したりしないか。
- 途中で失敗したとき、途中までの変更を残すか、取り消すか（トランザクションの範囲）。

## 6. 権限とセキュリティ

- 権限の確認をどこで行うか。画面で隠すだけでなく、APIやサービスでも拒否しているか。
- 利用者の入力をそのまま表示・実行していないか（スクリプトの埋め込み、SQLの組み立て）。
- 利用者が指定できる遷移先（ログイン後の戻り先など）を、文字列の前方一致で検証していないか。`/\evil.example` のように、ブラウザが外部のサイトとして扱う文字列がある。URLとして解釈してオリジンを比べるか、許可するパスを列挙する。
- 個人情報や秘密の値を、ログやエラーメッセージに出していないか。
- 失敗の理由を区別しない要件（例: 未登録とパスワード違いで同じメッセージ）があるとき、応答時間などでも区別できないようにしているか。
- ログイン状態などをセッションに保存するなら、有効期限、Cookie の属性（httpOnly、secure、sameSite）、暗号化の鍵の管理が決まっているか。他の機能にも影響するので、ADRになっているか。
- 開発やテストのための仕組み（仮の認証、テスト用のデータ投入口、テスト専用の関数など）が、本番で有効にならないよう仕組みで防いでいるか。その仕組みが具体的に書かれているか。

## 7. 非機能

- 種別が `非機能` の要件と、制約・前提の数値（件数、応答時間）を、どのコンポーネントがどう満たすか決まっているか。
- 最大の件数で動かしたときに、時間やメモリが足りるか。

## 8. 移行・リリース

- 既存データの移行が必要か（新しい必須の列に入れる値など）。
- 既存の利用者、他の機能、他システムとの互換性が崩れないか。
- リリースの順番（DBの変更を先に行うなど）に注意が要るか。依存先の実装がマージされてから実装する必要があるか。
- 本番で新しく必要になる設定（環境変数、秘密鍵、外部サービスの設定）があるか。
- 要件が他の機能の振る舞いを置き換える場合、その機能の既存のテストをどう書き換えるかが決まっているか。

## 9. テスト

- 既存のテストの書き方（種類、道具、置き場所、実行方法）を確かめたか。
- すべての受け入れ条件に、記入ルールの「検証方法の選び方」に沿って検証方法を決めたか。同じ種類の受け入れ条件をすべてE2Eにしていないか。
- テストデータ（受け入れ条件の「前提」）をどう用意するか。当日の日付やログイン状態のように作りにくい前提を、どう作るか。そのための差し替えの口が入出力にあるか。
- 前提の作り方が、テストの種類ごとに成り立つか。E2Eのログイン状態を、テストのプロセスの中の関数で作ろうとしていないか。
- 応答時間のテストは、測る環境（本番と同じビルドか）と区間が決まっているか。
- 画面にだけある表示（0件のときのメッセージなど）の受け入れ条件を、画面より下のコンポーネントのテストだけで確かめたことにしていないか。
- 手動確認の環境は実在するか。
- 「受け入れ条件との対応」の検証方法と、「テスト方針」に書いたテストの種類が一致しているか。

## セルフレビューで必ず確認すること

- requirements.md のすべての要件が、どれかのコンポーネントの `対応する要件` に載っているか。
- すべての受け入れ条件が「受け入れ条件との対応」に載っていて、その検証方法で「結果」を確かめられるか。
- 設計が、要件や受け入れ条件に書かれていない業務ルール（値の範囲、権限、データの範囲、出力の形式など）を新しく決めていないか。決めていれば、要件の問題として扱う。
- 「決めておく振る舞い」のすべてに根拠が付いていて、根拠の要件の文だけで成り立つか。要件の言葉を具体化した部分が、根拠なしで書かれていないか。
- 「決めておく振る舞い」が、requirements.md の要件と矛盾していないか。
- 「入出力」が、エラーの種類ごとの返し方まで書かれていて、「〜を表す応答」のような書き方で止まっていないか。
- 技術判断の選択肢に、他のissueで決めることが混ざっていないか。
- 技術判断の「決定」が、選択肢のどれかと一致しているか。
- 要件の言葉を具体化した技術判断に `種類: 要件の解釈` が付いていて、特殊な入力にだけ影響するものになっているか。
- 「既存コードの調査」に書いたパスが、実際にあるか。書いた慣習が、そのファイルで確かめられるか。
- 実装中に「設計で決めることと、実装に任せること」の1〜3に当たる選択が残っていないか。残っていれば技術判断として追加する。
- 既存の慣習に従った判断に、根拠のパスが書かれているか。根拠が、実装後に削除される他の機能の design.md や、この設計で新しく作るファイルになっていないか。根拠のファイルで、実際に同じ選び方をしているか。
- テストのための関数や設定に、「本番では呼ばない」のような注意書きではなく、本番で使えなくする仕組みが書かれているか。
- 「リスク」や技術判断の理由に書いた「整合する」「問題ない」を、要件の最大値を制約の単位に換算して確かめたか。
- 要件や設計が、他の機能の要件の文や受け入れ条件の「結果」と合わなくなるのに、requirements.md の「既存仕様への影響」の「変更」に載っていない、ということがないか。他の機能のコンポーネントを `（変更）` にした場合は、その機能の要件の文を読み直す。
- 他の機能にも影響する判断が、ADRになっているか。
- 同じ論点の技術判断が2つ以上ないか。

## 質問の作り方

- 1回に1問だけ聞く。
- 選択肢は2〜4個。推奨する選択肢を先頭に置き、「（推奨）」と付ける。推奨の理由を短く添える。
- 質問文に、決める必要がある理由を1文添える。技術的な言葉には短い説明を付ける。
- 既存コード、ADR、requirements.md から判断できることは質問しない。
- 顧客の判断が必要な論点は、設計の質問にしない。要件の問題として扱う。

## 質問の例

> CSVの作り方を決める必要があります。注文は最大で月5万件あり、作り方によって応答時間とメモリの使い方が変わるためです。
>
> 1. 1件ずつ読み出して書き出す（推奨: 件数が増えてもメモリの使用量が一定のため）
> 2. 全件をメモリで作ってから返す（実装は簡単だが、件数が増えると遅くなる）
