# 独立したレビューの依頼文

セルフレビューのあとに、設計を書いた文脈を持たないレビュー役に design.md を読ませる。
サブエージェントを起動できる環境では、次の依頼文の `<...>` を埋めて渡す。
サブエージェントを起動できない場合は、会話の経緯を使わず、ここに挙げたファイルだけを読み直して、同じ観点で自分でレビューする。

## 依頼文

```text
あなたは設計レビューの担当です。次の設計を、実装前に直すべき問題がないかという観点でレビューしてください。
ファイルは読むだけにし、編集しないでください。

- 設計: <docs/specs/<feature>/design.md のパス>
- 要件: <docs/specs/<feature>/requirements.md のパス>（front matter、スコープ、用語、要件、受け入れ条件、制約・前提、既存仕様への影響だけを読む）
- 記入ルール: <このスキルの references/writing-rules.md のパス>
- 設計の観点: <このスキルの references/design-checklist.md のパス>
- 依存先の設計と要件: <depends_on の依存先の design.md と requirements.md のパス。なければ「なし」>
- ADR: <docs/adr/ の accepted と proposed のファイルのパス>
- 既存コード: <「既存コードの調査」に書かれたパス>

次の観点で、実際に問題になる具体的な入力や手順を挙げて指摘してください。一般論だけの指摘はしないでください。

1. 要件との食い違い: 要件や受け入れ条件と合わない振る舞い、要件にない業務ルール、他の機能の要件の文と合わなくなる変更。
2. セキュリティ: 認証・権限の抜け、利用者が指定できる値（遷移先、ID、ファイル名など）の検証のすり抜け、応答の違い（本文や時間）から分かってしまう情報、テスト用の仕組みが本番で有効になる経路。
3. データ: 並びやページ分割が1つに決まらない、照合順序や文字の数え方の違い、制約と検証の食い違い、消したときの動き、同時に操作したときの重複や不整合。
4. ライブラリや方式の制約: 上限の単位（文字かバイトか）、切り捨て、既定の動き。設計やADRに「整合する」とある箇所は、要件の最大値を換算して確かめる。
5. テスト: 受け入れ条件の「結果」を、その検証方法で本当に確かめられるか。前提（ログイン状態、データ）を、その種類のテストで本当に作れるか。応答時間を測る環境が決まっているか。
6. 実装で迷う点: 実装する人が選ばなければならないことが残っていないか（どのコンポーネントが行うか、エラーの返し方、値の範囲）。

結果は次の形式で返してください。問題がない観点は「なし」と書いてください。

- <観点の番号> <重大度: 高 | 中 | 低> <design.md の該当箇所（見出しやコンポーネントID、D-xx）>: <問題> / <問題になる入力や手順の例> / <直し方の案>
```

## 指摘の扱い

- 指摘を1件ずつ確かめる。レビュー役の指摘が誤っている場合もあるので、design.md と要件を読み直して判断する。
- 正しい指摘は、次のどれかで扱う。
  - 設計の中で直せて、選択肢がない（直し方が1つに決まる）: 本文を直す。
  - 選択肢がある: 技術判断に `open` で追加し、「3. 質問」で聞く。
  - 要件の問題に当たる: 「要件の問題が見つかったとき」に進む。
- 誤りと判断した指摘は、理由を1文で添えて、セルフレビューの報告に載せる。
