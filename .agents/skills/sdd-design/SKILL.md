# sdd-design

完全モードの設計（`docs/specs/<ID>/design.ts`）を作る。
設計の内容そのものを人にレビューしてもらうことはしない。設計の妥当性は、型チェック・検証・品質ゲートで担保する。
ただし、**要件・既存コード・規約・ADRのどれからも決められない設計上の選択**は、推測で決めずに質問する。

このスキルのファイル:

- `assets/design-template.ts`: `design.ts` のひな形

対象リポジトリの手引き（書く前に必ず読む）:

- `docs/sdd/guides/writing-design.md`: 設計の書き方（質問するもの・しないものの基準を含む）
- `docs/sdd/guides/asking-questions.md`: 質問のしかた（1件ずつ聞く）
- `docs/sdd/guides/review-feedback.md`: 要件を変える必要が出たときの手順

`docs/sdd/deno.json` のタスクは、リポジトリのルートで `deno task --config docs/sdd/deno.json <タスク名>` として実行する。
以下では `deno task <タスク名>` と略す。

## 確認ポイントと止まる条件

ユーザーの回答を待つのは、次の場合**だけ**。質問を示して返答を終え、回答を受け取ってから先に進む。
それ以外は止まらずに進め、判断した内容を最後の報告に含める。

1. **要件などから判断できない設計上の選択がある**（手順3）: 設計を書く前に、`docs/sdd/guides/asking-questions.md` に従い
   **1件ずつ**質問する。回答によって次に聞くべきことが変わるため、まとめて聞かない。
   何を質問し、何を質問しないかは `docs/sdd/guides/writing-design.md` の「質問するもの・しないもの」に従う。
   判断できない選択が無ければ、質問せずに進む。
2. **要件・受け入れ条件・変えてはいけない振る舞いを変えないと設計できない**（矛盾、漏れ、実現できない）。
   状況と、要件をどう変えるかの案を示して返答を終える。受け入れ条件は人と合意した基準なので、AIの判断では変えない。
3. **開始時の前提を満たさない**（手順1）。

スキルを呼び出したこと（`/sdd-design`）は、確認ポイントへの回答ではない。

**「質問はありません」と判断する前に、次を確かめる**（試行では、これらを質問せずに決めてしまった）。

- 受け入れ条件に無い、利用者から見えることを決めていないか（画面の構成、文言、遷移先、既存の画面の削除）
- `adr: true` になる判断（新しいライブラリ、ツール、ミドルウェア、構成の方針）をしていないか。**これは必ず質問する**
- issue がツールの選定方法を指定していないか（例: propose-quality-tools で選定する）。指定があれば、それを実行してから質問する
- accepted の ADR、`conventions.ts`、`architecture.ts` と食い違う設計をしていないか。**ADR や規約と食い違う場合は必ず質問する**
  （質問して決めたら、decisions に `deviates` と `decidedBy: "user"` で書く。verify が確かめる）
- 既存の機能や画面を有効にする・つなぐ判断をしていないか（例: 雛形にあるアカウント登録の画面を使えるようにする）。
  利用者に見える機能が増えるので、必ず質問する

## 1. 前提を確認する

**要件の確認に「OK」と答えずに sdd-design が呼ばれた場合**は、要件の了承とみなす。requirements.ts が未コミットなら、
`docs(<ID>): 要件を作成` としてコミットし、push してから進める。

1. `deno task current` で issue の ID とモードを特定する。完全モードでなければ止まる。
2. `docs/specs/<ID>/requirements.ts` があり、`deno task verify <ID>` のエラーが無く、`openQuestions` が空であることを確かめる。
   満たさなければ sdd-req を案内して止まる。
3. `design.ts` がすでにあれば、作り直すのではなく、手直しとして扱う。

## 2. 調べる

1. `requirements.ts` と `issue.md` を読む。
2. `docs/sdd/architecture.ts`、`conventions.ts`、`nfr.ts`、`adr/` を読む。
3. コードを調べる。
   - 変更する部分の現状（As-Is）。関係するクラス、関数、テーブル、画面
   - 変更する部分の呼び出し元と、そこへの影響
   - 同じ種類の既存の実装（新しく作るものは、既存の作り方に合わせる）
   - 既存のテストの置き場所と書き方
   - architecture.ts とコードの食い違い（あればコードを正とし、`risks` に書く）
4. 他のブランチの作業を確かめる。
   ```sh
   deno task conflicts
   ```
   他の人のissueのインターフェースを使う場合（新規案件でよくある）は、そのブランチの design.ts を読む。
   ```sh
   git show origin/<ブランチ名>:docs/specs/<その人のID>/design.ts
   ```

## 3. 判断できない設計上の選択を質問する

手順2で調べた結果から、設計上の選択肢を洗い出し、要件・既存コード・規約（conventions.ts）・ADR のどれかで決まるものは、それに従って決める。
どれからも決められず、`docs/sdd/guides/writing-design.md` の「質問するもの」に当たる選択が残った場合は、
`docs/sdd/guides/asking-questions.md` の手順で、**1件ずつ**質問する。

1. 他の選択に最も影響するもの（例: データの持ち方 → それを使う処理の方式）を1件選び、選択肢と推奨を添えて聞く。返答を終えて回答を待つ。
2. 回答で決まったことを控える（design.ts を書くときに decisions に書く。`context` に質問の経緯、`decision` に回答）。
   新しいライブラリやパターンの導入に当たるなら `adr: true` にする。
3. 残りの選択を見直す。回答で決まったものは消し、前提が変わったものは聞き方を変え、新しく必要になったものは加える。
4. 残りが無くなるまで1〜3を繰り返す。

**質問がすべて終わるまで、design.ts を書かない・コミットしない。**

利用者から見えることを質問で決めた場合は、`docs/sdd/guides/review-feedback.md` の手順で要件の受け入れ条件にも加える
（要件の変更なので、加える内容を示してユーザーの了承を得る。了承を得たら requirements.ts を直し、check と verify を通す）。

## 4. 設計を書く

`assets/design-template.ts` をもとに `docs/specs/<ID>/design.ts` を書く。手引きに従う。

- 既存の作法を優先する。新しいライブラリやパターンを導入するときは、decisions に `adr: true` で理由と代替案を書く。
- 要件に無いものを作らない。
- `impact` は、作成・変更・削除するファイルを漏らさず書く。コンポーネントの `files` はすべて impact に含める。
- `traceability` には、すべての機能要件と非機能要件について、実現するコンポーネントを書く（漏れると型エラーになる）。
- `errorHandling` の `refs` で、異常系の受け入れ条件と EARS の unwanted の要件を、すべてどれかのエラー処理に対応させる。
- `nfrStrategy` に非機能要件ごとの実現方法を、`invariantStrategy` に変えてはいけない振る舞いごとの守り方を書く。
- 既存のインターフェースの変更・削除には `compatibility`、既存のデータモデルの変更には `migration` を書く。
- `conventionsCompliance` に、手で守る規約（`conventions.ts` の `enforcedBy: "manual"`）ごとの守り方を書く（verify が全件あるかを確かめる）。
  守らない（使わない、見送る）なら、それは守り方ではなく逸脱なので、質問して decisions に書く（verify が逸脱の言い回しを検出する）。
- decisions には、誰が決めたか（`decidedBy`）を書く。質問して決めたものは `"user"`、AIが決めたものは `"ai"`。
  `adr: true` の判断は `"user"` でなければならない（verify が確かめる）。
- テストのための補助（テスト用のクラスやファイル）はコンポーネントにしない。ファイルは impact にだけ書く。
- 書き終えたら、`docs/sdd/guides/writing-design.md` の「設計のチェックリスト」で点検し、`checklist` を書く。
  点検で見つかった不足は設計に反映する。判断できない選択が見つかったら、手順3に戻って1件ずつ質問する。

書いたら、次を実行し、エラーが無くなるまで直す。警告は内容を確かめ、直さない場合は理由を報告に含める。

```sh
deno task check <ID>
deno task verify <ID>
```

## 5. 衝突を確かめる

```sh
deno task conflicts --issue <ID>
```

`[重なり]` があれば、重ならない設計にできないかを検討する（共有ファイルの変更を最小にする、別のファイルに分けるなど）。
避けられない重なりは報告に含め、担当者との調整を勧める。作業は止めない。

## 6. HTMLを生成して、コミットして push する

1. `deno task render <ID>` でHTMLを生成する。
2. `docs/specs/<ID>/design.ts` をコミットする。コミットメッセージは `docs(<ID>): 設計を作成`。
3. push する（リモートが無ければ省く）。

## 7. 報告する

設計の要点（コンポーネント、主なインターフェース、データモデルの変更、ADRにする設計判断、質問して決めたこと）、
設計のチェックリストで `notApplicable` にした観点とその理由、衝突の確認結果、
risks、HTMLのパスを報告し、次の工程として sdd-tasks を案内する。
