# sdd-design: 設計

承認済みの `docs/specs/<feature>/requirements.md` から `docs/specs/<feature>/design.md` を作り、ユーザーへの質問で技術判断を決めて、設計を確定（`status: approved`）させる。
設計を確認するのはユーザー（開発者）だけで、顧客は確認しない。

## やらないこと

- 書き込みを伴うgit操作（ブランチ作成、コミット、プッシュ、PR作成、マージ）。ユーザーが手動で行う。
- requirements.md の編集。要件の問題が見つかったら、設計を止めてユーザーに報告する（「要件の問題が見つかったとき」）。
- 実装、タスクの分解。ステップ4（tasks）とステップ5（実装）で扱う。
- 読んで確かめていないファイル、関数、ライブラリを前提にすること。
- 既存の慣習がない技術判断を、ユーザーに聞かずに決めること。

## 参照ファイル

- テンプレート: [templates/design.md](templates/design.md)、ADR: [templates/adr.md](templates/adr.md)
- 記入ルール（決めることの線引き、見出し、技術判断、ADR）: [references/writing-rules.md](references/writing-rules.md)
- 設計の観点と優先順: [references/design-checklist.md](references/design-checklist.md)
- 記入例: [references/example.md](references/example.md)（sdd-req の記入例 `42-order-csv-export` に対応する設計）
- 独立したレビューの依頼文: [references/review-prompt.md](references/review-prompt.md)
- 検証スクリプト: `python3 <このスキルのディレクトリ>/scripts/validate_design.py <design.md> [--target approved]`

作業を始める前に、テンプレートと記入ルールを必ず読む。

## 手順

### 対象の決定

1回の実行で扱う feature は1つだけにする。複数の design.md をまとめて作らない。質問は1問ずつ行い、実装PRも feature ごとに分かれるため。

1. ユーザーが feature（ディレクトリ名、issue番号、ファイル）を指定していれば、それを対象にする。
2. 指定がなければ、`docs/specs/*/` を調べ、requirements.md が `approved` で、design.md がないか `approved` でない feature を一覧にする。各行に feature 名と design.md の状態（なし、drafting、clarifying）を書く。
3. 一覧から1つを、選択肢形式でユーザーに選んでもらう。候補が1つだけでも、推測で決めずに選んでもらう。候補がなければ、その旨と、requirements.md が approved でない feature があればその一覧を伝えて終わる。
4. 対象の feature を「0. 状況の判定」に進める。

### 0. 状況の判定

- design.md がない → 「1. 準備」
- `status: drafting` → 「2. 調査と初稿」の続き
- `status: clarifying` → 「3. 質問」
- `status: approved` で、設計の変更を依頼された → 変更内容を技術判断として記録し、`status: clarifying` に戻して「3. 質問」へ進む。
- どれにも当てはまらない → ユーザーに何をしたいか確認する。

### 1. 準備

1. requirements.md の `status` が `approved` であることを確かめる。そうでなければ止まり、sdd-req で承認を済ませるよう伝える。
2. requirements.md の `depends_on` にある依存先が approved であることを確かめる。approved でない依存先があれば止まり、ユーザーに伝える。依存先がまだ実装されていない場合は、依存先の design.md を読み、記入ルールの「依存先がまだ実装されていないとき」に従う。依存先の design.md が approved でなければ止まり、先に依存先を設計するよう伝える。
3. requirements.md のうち、front matter、スコープ、用語、要件、受け入れ条件、制約・前提、既存仕様への影響を読む。顧客への確認事項と質問ログは読まない。
4. 他のissueの機能が必要になっていないかを確かめる。見る場所は、制約・前提、スコープの対象外、各要件の文と受け入れ条件の「前提」（例: 「ログイン済みである」という前提は、ログイン機能が作る状態）。
   - その機能が既存コードか `docs/capabilities/` にあれば、それを前提に進める。
   - なければ、記入ルールの「他の機能との関係」に従って、「本当の依存」か「条件付きの前提」かを判断する。判断に迷う場合は、その判断を選択肢にしてユーザーに質問する。
   - 本当の依存で、`depends_on` に載っていない、または依存先が approved でない場合は止まり、「要件の問題が見つかったとき」と同じ形でユーザーに報告する。仮の実装（スタブ）で先に進めるかどうかを、設計の中で決めない。
   - 条件付きの前提なら止まらない。状態を読み取る仕組みを技術判断として `open` で登録し、「2. 調査と初稿」へ進む。
5. `docs/adr/`（accepted のもの）、`docs/decisions/`（accepted のもの）、`docs/glossary.md`、影響する業務領域の `docs/capabilities/<業務領域>.md` があれば読む。
6. テンプレートをもとに `docs/specs/<feature>/design.md` を作る（`status: drafting`）。

### 2. 調査と初稿

1. 既存コードを調べる。
   - 技術スタック（依存関係の定義、設定ファイル）、フォルダ構成、似た機能の作り方、エラー処理、権限の確かめ方、テストの書き方を確かめる。
   - 要件ごとに、関係する既存のファイルを探して読む。
   - 読んで確かめたことを「既存コードの調査」に書く。
2. 設計の観点に沿って、方針、変更内容、データ、移行・リリース、受け入れ条件との対応、テスト方針を書く。
   - 「設計で決めることと、実装に任せること」の1〜3に当たる選択ごとに、次のように扱う。
   - 既存の慣習や accepted のADRで決まる: 質問せずに従い、設計の中身に影響するものは技術判断に `決定者: 既存の慣習` と `根拠` を書く。
   - 慣習がなく、選択肢が複数ある: 技術判断に `open` で登録し、本文の該当箇所に `[要確認: D-xx]` を置く。
   - 要件の言葉が複数の意味に分かれ、記入ルールの「要件の解釈」の2つの条件を満たす: 技術判断に `種類: 要件の解釈` を付けて `open` で登録し、ユーザーに質問する。同じ言葉の解釈が他の機能ですでに決まっている場合だけ、記入ルールの例外に従って既存の慣習で決める。
   - 顧客の判断が必要、または「要件の解釈」の条件を満たさない: 設計では決めない。「要件の問題が見つかったとき」に進む。
   - ライブラリや方式を選ぶときは、その制約（上限の単位、既定の動き）を確かめ、要件の数値と合うかを確かめる。
   - `決めておく振る舞い` を書くたびに、行末の根拠に何を書けるかを確かめる。要件IDも `D-xx` も書けない振る舞いは、本文に書かずに技術判断にする。
3. 既存コードがない（新規のプロジェクトの）場合は、次のようにする。
   - 技術スタックの選定を、最初の技術判断として `open` で登録する。ADRにする。
   - 技術スタックが決まったら、実装を始めるのに必要な基盤（初期設定、DBの接続、テストの設定など）を `対応する要件: なし（基盤）` のコンポーネントとして書く。
4. `status: clarifying` にして「3. 質問」へ進む。

### 3. 質問（1回に1問）

1. `open` の技術判断から、設計の観点の優先順（戻しにくいもの）に従って1問選ぶ。
2. 選択肢形式で質問する。選択肢形式の質問ツールがあれば使い、なければ番号付きの選択肢をテキストで示す。
   - 選択肢は2〜4個。推奨する選択肢を先頭に置き「（推奨）」と付け、理由を短く添える。
   - 質問文には、なぜそれを決める必要があるかを1文添える。技術的な言葉には短い説明を付ける。
   - 「要件の解釈」の質問では、選択肢ごとに、結果が変わる入力の例を示す（例: 「全角の Ａ を a と同じにする: `ＵＳＥＲ@example.com` は `user@example.com` と重複になる」）。
3. 回答を反映する。
   - 技術判断を `decided` にし、`決定`、`理由`、`決定者: ユーザー` を書く。`決定` には選んだ選択肢をそのまま書く。選択肢にない答えなら、先に選択肢へ書き足す。
   - 本文の `[要確認: D-xx]` を消して決定内容を反映し、`（根拠: D-xx）` を付ける。
   - 他の機能にも影響する判断なら、ADRにするかをユーザーに質問する。ADRにする場合は、テンプレートから `docs/adr/<id>.md` を `status: proposed` で作り、技術判断に `ADR: する（adr:<id>）` と書く。
4. 回答と他の技術判断・本文との組み合わせを見直す。矛盾や、新たに決める必要が出た点があれば、技術判断に `open` で追加する。前提が変わった技術判断は、新しく作らずに既存のものを `open` に戻して聞き直す。
5. `open` が残っていれば 3-1 に戻る。なくなれば「4. セルフレビュー」へ進む。

ユーザーが途中で中断しても、状態はファイルに残る。次回は「0. 状況の判定」から再開する。

### 4. セルフレビュー

1. 設計の観点を上から順にすべて見直し、観点ごとに「design.md のどこで扱ったか」を確認する。扱っていない観点で決める必要があるものは、技術判断に `open` で追加する。
2. 設計の観点の「セルフレビューで必ず確認すること」を1つずつ確かめる。
3. `決めておく振る舞い` を1行ずつ読み、根拠の要件の文に書かれていることだけで成り立つかを確かめる。要件の言葉を具体化している部分（数え方、文字の種類、空白の範囲、境界の値など）があれば、それが `種類: 要件の解釈` の技術判断で決まっているか、要件の問題として報告済みかを確かめる。どちらでもなければ、技術判断に追加するか、「要件の問題が見つかったとき」に進む。
4. `入出力` を1行ずつ読み、呼び出す側がそれだけで実装できるか（非同期かどうか、エラーの種類ごとの型と返し方、複数のエラーの返し方まで書かれているか）を確かめる。
5. 選んだライブラリや方式の制約（上限の単位など）が、要件の数値と合っているかを、要件の最大値を制約の単位に換算して確かめる。この設計、依存先の設計、ADRに書かれた「整合する」も換算し直す。合わない場合は、技術判断に `open` で追加する。ADRが原因なら、そのADRを置き換える新しいADRを提案する。
   - 他の機能と同じでなければならないルールが、共通の関数やADRではなく、文章の「揃える」だけで守られていないかも確かめる。
6. `--target approved` で検証スクリプトを実行する。ADRが proposed であることによるエラー以外は、直して再実行する。
7. 独立したレビューを行う。[references/review-prompt.md](references/review-prompt.md) の依頼文で、設計を書いた文脈を持たないレビュー役（サブエージェント）に design.md を読ませ、「指摘の扱い」に従って1件ずつ扱う。本文を直した場合は、6 からやり直す。
8. `open` を追加した場合は「3. 質問」に戻る。
9. 確認結果を、次の形式でユーザーに報告する。省略しない。

```markdown
#### 観点ごとの確認
- 技術スタックと既存の慣習: ...
（設計の観点の9項目すべて）

#### 要件と受け入れ条件の対応
- 要件: 7件すべてコンポーネントに対応済み
- 受け入れ条件: 12件すべて検証方法を決定済み（単体 5、結合 6、手動 1）

#### 既存の慣習に従って決めたこと
- D-02 権限の確認はAPIのミドルウェアで行う（根拠: src/middleware/requireRole.ts）

#### 要件の解釈（実装PRの本文に載せる）
- D-04 read-book.title-length の「100文字」: 絵文字は1文字と数える（特殊な入力だけに影響し、受け入れ条件の結果は変わらない）
（ない場合は「なし」）

#### 要件の問題として報告したもの
- D-06 order-export.csv-columns の「一般的な形式」: 普通の入力で結果が変わるため、sdd-req に戻す
（ない場合は「なし」）

#### 選んだライブラリや方式の制約
- bcrypt: 72バイトまで。要件の上限は72文字のため、日本語を含むと超える。D-07 で対策を決定
（ない場合は「なし」）

#### 要件に書かれていない振る舞い
- なし（見つかった場合は、要件の問題として報告する）

#### 独立したレビューの指摘と対応
- 高 D-03 returnTo の検証が前方一致で、`/\evil.example` を通す: 許可する戻り先を列挙する形に直した
- 低 リスク の記述: 誤り（理由: 8文字未満の判定は照合の前で、アカウントの有無は漏れない）
（指摘がない場合は「なし」）
```

### 5. 承認

1. ユーザーに、design.md の確認と承認を依頼する。修正の依頼があれば、技術判断として記録して反映し、必要なら「3. 質問」に戻る。
2. 依存先がまだ実装されていない場合は、依存先の design.md を読み直す。作業中のブランチにあれば、`git fetch` のあと `git show <ブランチ>:<パス>` で読む。前提にしたコンポーネントの場所や入出力が変わっていれば、影響する技術判断を `open` に戻して「3. 質問」に戻る。
3. 承認されたら、この feature で作ったADRを `status: accepted` にする。
4. `--target approved` で検証スクリプトを実行し、エラーがなくなるまで直す。
5. `status: approved` にする。
6. ユーザーに、次はステップ4（sdd-tasks でタスクを作る）であることを伝える。design.md は実装PRに含める。「対象の決定」の2と同じ条件で残りの feature を調べ、次に設計できる feature があれば一覧で伝える。
7. `種類: 要件の解釈` の技術判断がある場合は、実装PRの本文に載せる一覧の案を出力する。顧客向けに、要件IDと決めた解釈を平易な日本語で1行ずつ書く。

## 要件の問題が見つかったとき

「記入ルール」の「要件の問題として扱うもの」に当たる場合は、設計で決めずに止まる。

1. design.md の該当箇所に `[要確認: D-xx]` を置き、技術判断に `open` で登録する。`選択肢` には、考えられる解釈や対応（例: 「`user+tag@example.com` を受け付ける / 受け付けない」）を書く。要件が直るまで `open` のままにする。
2. ユーザーに次を報告する。
   - 問題のある要件ID、受け入れ条件ID、または制約・前提の記述。
   - 何が問題か（矛盾、実現できない理由、要件にない業務ルール、普通の入力で結果が変わる複数の意味の言葉、本当の依存に当たる機能がない、または未承認）。
   - 考えられる対応の選択肢。
   - 問題が複数ある場合は、まとめて1回で報告する（sdd-req での顧客確認を1回で済ませるため）。
3. ユーザーが sdd-req で要件を直し、顧客の再確認を経て requirements.md が再び approved になったら、「0. 状況の判定」から再開する。requirements.md の変更に合わせて、影響する技術判断と本文を見直す。
