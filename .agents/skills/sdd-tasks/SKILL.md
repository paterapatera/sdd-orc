# sdd-tasks

完全モードの実装タスク（`docs/specs/<ID>/tasks.ts`）を作る。**人の確認は挟まず、止まらずに進める。**

このスキルのファイル:

- `assets/tasks-template.ts`: `tasks.ts` のひな形

対象リポジトリの手引き（書く前に必ず読む）:

- `docs/sdd/guides/writing-tasks.md`: タスクの書き方

`docs/sdd/deno.json` のタスクは、リポジトリのルートで `deno task --config docs/sdd/deno.json <タスク名>` として実行する。
以下では `deno task <タスク名>` と略す。

## 止まる条件

途中でユーザーの判断を待つのは、次の場合**だけ**。それ以外は止まらずに進め、判断した内容を最後の報告に含める。

1. **要件・受け入れ条件・変えてはいけない振る舞いを変えないとタスクにできない**（テストできない受け入れ条件など）。
2. **開始時の前提を満たさない**（手順1）。

設計の見直しが必要になった場合は、止まらずに design.ts を直す（`docs/sdd/guides/review-feedback.md` の手順2と4）。

## 1. 前提を確認する

1. `deno task current` で issue の ID とモードを特定する。完全モードでなければ止まる。
2. `requirements.ts` と `design.ts` があり、`deno task verify <ID>` のエラーが無いことを確かめる。
   満たさなければ、足りない工程（sdd-req、sdd-design）を案内して止まる。
3. `tasks.ts` がすでにあれば、手直しとして扱う。完了した（`status: "done"`）タスクは消さず、IDも振り直さない。

## 2. 調べる

1. `requirements.ts`、`design.ts` を読む。
2. `docs/sdd/conventions.ts` のテストの規約（テストを実装の前に書くか後に書くか、置き場所、書き方）を読む。
3. `docs/sdd/config.ts` の `commands`（品質ゲート）を確かめる。
4. 変更するコードに既存のテストがあるかを調べる（無ければ、現状の振る舞いを固定するテストのタスクが要る）。

## 3. タスクを書く

`assets/tasks-template.ts` をもとに `docs/specs/<ID>/tasks.ts` を書く。手引きに従う。

順序の目安:

1. 変えてはいけない振る舞い（INV）を固定するテスト（既存のテストで確かめられない場合）
2. コンポーネントの実装。**使われる側から先に**作る（design.ts の dependencies で `to` の側が先）
3. 受け入れ条件（AC）のテスト。実装の前に書くか後に書くかは、conventions.ts の規約に合わせる
4. 非機能要件（NFR）の計測
5. ドキュメントの更新（必要な場合）

守ること:

- 粒度の目安は3〜10件。小さな作業（設定ファイルを1つ足すなど）は、関係するタスクにまとめる。
- **受け入れ条件のテストは、`when` を実行して `then` を観測するものにする。** ファイルの文字列を調べるだけのテストにしない。
  品質ゲートでスキップされるテストを `verifies` の根拠にしない。
- テストは対応する実装と同じタスクか直後に置く（すべてのテストを最後にまとめない）。
- 要件の `nfrReview` で baseline にしたカテゴリに `docs/sdd/nfr.ts` の基準があれば、それを確かめるテストタスクを作る
  （`verifies` に `BNFR-xxx`。要件の `waived` に理由があるものは除く）。
- `config.ts` の `ui` が true なら、人が確かめる受け入れ条件を E2E テストでも確かめるタスク（`kind: "e2e"`）を作る（verify が確かめる）。
- テストの中から、品質ゲート、`docker compose`、依存関係の導入を呼ばない（無限の再帰や停止の原因になる）。
- 人が確かめる受け入れ条件（`verifiedBy: "human"`）がデータやアカウントを前提にしているなら、開発用のシーダー（またはコマンド）を作るタスクを作る
  （開発用のシーダーやコマンド。本番用の初期データには混ぜない）。

- 1タスク＝1コミットの粒度にする。各タスクの完了時に品質ゲート（`deno task gate`）が通る状態を保てる順序にする。
- すべての受け入れ条件と変えてはいけない振る舞いを、どれかのテストタスクの `verifies` に含める（漏れると verify のエラーになる）。
- `description` には、作る・変えるファイル、関数名、テストの観点を具体的に書く。sdd-impl はこれを読んで止まらずに実装する。

書いたら、次を実行し、エラーが無くなるまで直す。警告は内容を確かめ、直さない場合は理由を報告に含める。

```sh
deno task check <ID>
deno task verify <ID>
```

## 4. HTMLを生成して、コミットして push する

1. `deno task render <ID>` でHTMLを生成する。
2. `docs/specs/<ID>/tasks.ts` をコミットする（design.ts を直した場合は、それも含める）。コミットメッセージは `docs(<ID>): タスクを作成`。
3. push する（リモートが無ければ省く）。

## 5. 報告する

タスクの一覧（ID、種類、タイトル）、design.ts を直した場合はその内容、HTMLのパスを報告し、次の工程として sdd-impl を案内する。
