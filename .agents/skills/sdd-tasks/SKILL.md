# sdd-tasks: タスクの分解

承認済みの `docs/specs/<feature>/design.md` から `docs/specs/<feature>/tasks.md` を作る。
タスクは設計から機械的に決まるものとし、ユーザーの承認は待たない。検証スクリプトを通ったら `status: ready` にして、ステップ5（実装）に進めるようにする。

## やらないこと

- 書き込みを伴うgit操作（ブランチ作成、コミット、プッシュ、PR作成、マージ）。ユーザーが手動で行う。
- design.md と requirements.md の編集。設計の不足が見つかったら止まり、sdd-design に戻す（「設計の不足が見つかったとき」）。
- 設計にない判断を、タスクの中で決めること（新しいコンポーネント、入出力、振る舞い、ライブラリ）。
- 実装。ステップ5で扱う。

## 参照ファイル

- テンプレート: [templates/tasks.md](templates/tasks.md)
- 記入ルール: [references/writing-rules.md](references/writing-rules.md)
- 記入例: [references/example.md](references/example.md)（sdd-design の記入例 `42-order-csv-export` に対応するタスク）
- 検証スクリプト: `python3 <このスキルのディレクトリ>/scripts/validate_tasks.py <tasks.md> [--target ready]`

作業を始める前に、テンプレートと記入ルールを必ず読む。

## 手順

### 対象の決定

1回の実行で扱う feature は1つだけにする。

1. ユーザーが feature（ディレクトリ名、issue番号、ファイル）を指定していれば、それを対象にする。
2. 指定がなければ、`docs/specs/*/` を調べ、design.md が `approved` で、tasks.md がないか `ready` でない feature を一覧にする。各行に feature 名と tasks.md の状態（なし、drafting）を書く。
3. 一覧から1つを、選択肢形式でユーザーに選んでもらう。候補が1つだけでも、推測で決めずに選んでもらう。候補がなければ、その旨と、design.md が approved でない feature があればその一覧を伝えて終わる。

### 0. 状況の判定

- tasks.md がない → 「1. 準備」
- `status: drafting` → 「2. タスクの作成」の続き
- `status: ready` で、design.md が変わった、または作り直しを依頼された → tasks.md を作り直す（`status: drafting` に戻して「1. 準備」から）。`状態: done` のタスクがある場合は、作り直す前にユーザーに確認する。
- どれにも当てはまらない → ユーザーに何をしたいか確認する。

### 1. 準備

1. design.md の `status` が `approved` であることを確かめる。そうでなければ止まり、sdd-design で承認を済ませるよう伝える。
2. design.md の、方針、変更内容、データ、移行・リリース、受け入れ条件との対応、テスト方針、技術判断の `決定` を読む。
3. requirements.md の受け入れ条件（前提、操作、結果）を読む。テストで確かめる内容に使う。
4. テストの実行コマンドを、design.md のテスト方針と既存コード（package.json の scripts など）で確かめる。
5. テンプレートをもとに `docs/specs/<feature>/tasks.md` を作る（`status: drafting`）。

### 2. タスクの作成

記入ルールに従って、次の順に書く。

1. design.md の「変更内容」のコンポーネントを、1つにつき1タスクにする。
2. コンポーネント同士の依存（入出力を呼ぶ側と呼ばれる側、基盤とそれを使うもの）を調べ、依存の少ない順に並べて `T-01` から番号を付ける。
3. タスクごとに、「テストを書く」を先に決める。
   - 受け入れ条件は、design.md の「受け入れ条件との対応」の検証方法のまま、1つのタスクに載せる。複数のコンポーネントを通すテストは、必要なコンポーネントがすべてそろうタスクに置く。
   - 「決めておく振る舞い」ごとに、それを確かめるテストを書く。テストで確かめられない振る舞いは「レビューで確かめる」に書く。
4. 「守る技術判断」「実装する」「完了条件」を書く。「データ」と「移行・リリース」の項目は、それが必要になるタスクの「実装する」に入れる。
5. 途中で設計の不足に当たったら、書き進めずに「設計の不足が見つかったとき」に進む。

### 3. 検証

1. `--target ready` で検証スクリプトを実行し、エラーがなくなるまで直す。警告は1件ずつ確かめ、直すか、直さない理由をユーザーへの報告に書く。
2. 記入ルールの「セルフレビューで必ず確認すること」を1つずつ確かめる。
3. `status: ready` にする。
4. ユーザーに次を報告する。承認は求めない。
   - タスクの一覧（番号、コンポーネント、依存、受け入れ条件の数）。
   - 直さなかった警告と、その理由。
   - 次はステップ5（sdd-impl で実装する）であること。design.md に「依存先の実装PRがマージされてから実装する」とある場合は、そのことも伝える。

## 設計の不足が見つかったとき

次に当たる場合は、タスクで補わずに止まる。

- テストの実行コマンド、テストの置き場所、テストデータの用意の仕方が、design.md にも既存コードにもない。
- 受け入れ条件の「前提」を、その検証方法のテストで作る方法が決まっていない。
- 「決めておく振る舞い」や入出力が、実装する人に選択を残している。
- コンポーネント同士の依存が循環していて、順番を決められない。
- 「データ」や「移行・リリース」の項目を、どのコンポーネントが扱うかが決まらない。

1. tasks.md は `status: drafting` のままにする。
2. ユーザーに、不足している箇所（design.md の見出し、コンポーネントID、受け入れ条件ID）、何が決まっていないか、考えられる対応を報告する。複数ある場合はまとめて1回で報告する。
3. ユーザーが sdd-design で設計を直し、design.md が再び approved になったら、「0. 状況の判定」から再開する。
