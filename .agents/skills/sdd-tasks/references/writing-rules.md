# tasks.md 記入ルール

## 目次

- 基本方針
- YAML front matter
- タスクの見出しと並び
- 各項目の書き方
- テストを書く
- 後続スキルが読む範囲
- セルフレビューで必ず確認すること

## 基本方針

- 読み手は、ステップ5（実装）を行うAIと、進み具合を見るユーザー。
- tasks.md は design.md を実装の順番に並べ直したもの。設計にない判断を足さない。
- 1行に1文。表は使わない。
- 入出力や振る舞いの中身は書き写さない。design.md のコンポーネントIDで参照する。
- タスクの中では、テストを先に書き、失敗することを確かめてから実装する。

## YAML front matter

```yaml
feature: 42-order-csv-export   # design.md と同じ feature 名。ディレクトリ名と一致させる
status: ready                  # drafting | ready
```

| status | 意味 | 次に進む条件 |
|---|---|---|
| drafting | 作成中、または設計の不足で止まっている | `--target ready` の検証を通過した |
| ready | 実装を始められる | ステップ5（実装）に進める。ユーザーの承認は要らない |

## タスクの見出しと並び

- 見出しは `## T-<2桁の番号> <コンポーネントID> <コンポーネント名>（新規 | 変更 | 削除）`。コンポーネントIDと種類は design.md と同じにする。
- design.md の「変更内容」のコンポーネント1つにつき、タスクを1つ作る。1つのコンポーネントを複数のタスクに分けたり、複数のコンポーネントを1つのタスクにまとめたりしない。
- 番号は `T-01` からの連番。依存の少ない順（基盤、データを読み書きするもの、それを使う処理、API、画面の順が目安）に並べる。
- 依存先のタスクは、必ず前に置く。

## 各項目の書き方

```markdown
## T-03 orders-export-api CSV出力のAPI（変更）

- 依存: T-01, T-02
- 場所: src/orders/ordersRouter.ts
- 守る技術判断: D-02
- テストを書く:
  - 自動テスト（結合） tests/orders/export.test.ts: 経理ロールで期間を指定すると、完了とキャンセルの注文がCSVで返る（根拠: order-export.csv-download.ac1）
  - 自動テスト（結合） tests/orders/export.test.ts: 経理ロールがないと403が返る（根拠: auth.accounting-role, D-02）
- 実装する: design.md の orders-export-api の入出力と決めておく振る舞い
- 完了条件: `npm test` で上のテストが通り、既存のテストも通る
- 状態: todo
```

- `依存`、`場所`、`守る技術判断`、`テストを書く`、`実装する`、`完了条件`、`状態` は必須。
- `依存`: このタスクの前に終わっている必要があるタスクを、カンマ区切りで書く。ない場合は `なし`。このコンポーネントが入出力を呼ぶコンポーネントと、このタスクのテストが通るのに必要なコンポーネントのタスクを書く。
- `場所`: design.md のそのコンポーネントの `場所` をそのまま書く。
- `守る技術判断`: そのコンポーネントの `決めておく振る舞い` の根拠にある `D-xx`、`adr:<id>`、`decision:<id>` をすべて書く。ほかに守るものがあれば足してよい。ない場合は `なし`。
- `実装する`: `design.md の <コンポーネントID> の入出力と決めておく振る舞い` と書く。design.md の「データ」や「移行・リリース」の項目をこのタスクで扱う場合は、続けて書く（例: 「design.md の「データ」の orders テーブルの索引を、マイグレーションで追加する」）。
- `完了条件`: テストの実行コマンドをバッククォートで囲んで書き、「上のテストが通り、既存のテストも通る」と続ける。E2Eなど別のコマンドが要る場合は、すべて書く。
- `状態`: 作るときは `todo`。ステップ5が、タスクを終えたら `done` にする。
- 任意の項目:
  - `レビューで確かめる: <確かめること>（根拠: ...）`: テストで確かめられない振る舞い（例: 全件をメモリに載せない）を書く。複数行書ける。
  - `手動確認: <受け入れ条件ID>: <確かめること>`: design.md で検証方法が `手動確認` の受け入れ条件を書く。複数行書ける。

## テストを書く

- 1行に1つのテストの観点を、`  - <検証方法> <テストファイルのパス>: <確かめること>（根拠: <ID>, ...）` の形で書く。
- 検証方法は `自動テスト（単体）`、`自動テスト（結合）`、`自動テスト（E2E）` のいずれか。
- テストファイルのパスは、design.md のテスト方針と既存のテストの置き場所に合わせる。
- 根拠に書けるのは、受け入れ条件ID、要件ID、`D-xx`、`adr:<id>`、`decision:<id>`。
- design.md の「受け入れ条件との対応」にあるすべての受け入れ条件を、どれか1つのタスクに、同じ検証方法で載せる。`確かめること` には、受け入れ条件の前提、操作、結果を短く書く。
- 受け入れ条件を置くタスクは、「受け入れ条件との対応」に並んだコンポーネントのタスクがすべて、そのタスク自身か、その依存先（たどった先も含む）になっているタスクにする。
- `決めておく振る舞い` ごとに、その根拠のIDを根拠に書いたテストを、少なくとも1行書く。受け入れ条件のテストで確かめられる場合は、その行の根拠に振る舞いの根拠も足す。
- テストのためだけの仕組み（テスト用のデータ投入口、テスト用の設定など）は、design.md のテスト方針に書かれたものだけを使う。
- テストがないタスク（削除だけのタスクなど）は、`- テストを書く: なし（<理由>）` と書く。

## 後続スキルが読む範囲

ステップ5（実装）は、`status: ready` の tasks.md を上から順に読み、`状態: todo` のタスクを1つずつ行う。
タスクを行うときは、そのタスクの項目と、design.md の該当するコンポーネント、「守る技術判断」の決定を読む。

## セルフレビューで必ず確認すること

- design.md のすべてのコンポーネントが、ちょうど1つのタスクになっているか。
- すべての受け入れ条件が、design.md と同じ検証方法で、どれか1つのタスクに載っているか。
- 受け入れ条件のテストを置いたタスクで、そのテストが通るのに必要なコンポーネントがすべてそろっているか。
- すべての `決めておく振る舞い` に、確かめるテストか「レビューで確かめる」があるか。
- design.md の「データ」と「移行・リリース」の項目が、どれかのタスクの「実装する」に入っているか。
- テストの前提（ログイン状態、テストデータ、現在時刻など）の作り方が、design.md のテスト方針にあるものだけになっているか。
- 設計にないコンポーネント、入出力、振る舞い、ライブラリを足していないか。
