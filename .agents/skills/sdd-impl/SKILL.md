# sdd-impl

specのタスクを上から順に、1タスク＝1コミットで、**すべて完了するまで止まらずに**実装する。

- 人のコードレビューは行わない。コードの品質は品質ゲート（`deno task gate`: フォーマッタ → check → テスト）で担保する。
- 人は、実装の完了後に受け入れテストだけを行う。受け入れテストを頼む前に、AIが実際に動かして確かめ、準備を整える。

対象リポジトリの手引き:

- `docs/sdd/guides/writing-tasks.md`: タスクの状態と、受け入れ条件のテストの書き方
- `docs/sdd/guides/review-feedback.md`: specを直すときの手順

`docs/sdd/deno.json` のタスクは、リポジトリのルートで `deno task --config docs/sdd/deno.json <タスク名>` として実行する。
以下では `deno task <タスク名>` と略す。

## 止まる条件

途中でユーザーの判断を待つのは、次の場合**だけ**。それ以外は止まらずに進め、判断した内容を最後の報告に含める。

1. **要件・受け入れ条件・変えてはいけない振る舞いの変更が必要になった**（矛盾、漏れ、実現できない）。
   受け入れ条件は人が受け入れテストで確かめる基準なので、AIの判断では変えない。
2. **accepted の ADR と食い違う実装が必要になった**（例: ADR で PostgreSQL と決めたのに、テストを SQLite で動かす必要がある）。
   ADR は人と合意した技術選定なので、AIの判断では覆さない。食い違いの内容と、ADR を変える案・実装を変える案を示す。
3. **品質ゲートを緩める必要が出た**（除外を足す、PHPStan などのレベルを下げる、テストを外す）。緩めずに直せないか調べたうえで、
   理由と案を示す。ユーザーが了承したら、design.ts の decisions に `relaxesQualityGate`（ファイル）と `decidedBy: "user"` で書く。
4. **環境の問題で先に進めない**（依存関係の取得に認証が要る、必要なサービスが無いなど）。
5. **開始時の前提を満たさない**（手順1）。

止まるときは、状況、原因、選択肢を示して返答を終える。

## 守ること（試行で崩れた点）

- **1タスクずつ進める。** 次のタスクに着手する前に、今のタスクの品質ゲートを通してコミットする。
  複数のタスクをまとめて実装してから、後でコミットを分けることはしない。作業ツリーに次のタスクの変更を残さない。
- **サブエージェントにタスクをまとめて任せない。** 使う場合も1タスクずつ順に任せ、完了を待ってから次に進む。
  自分とサブエージェントが同時にファイルを変更したり、コミットしたりしない。
- **コミットメッセージは `<type>(<ID>): <タスクID> <タスクのタイトル>`**（`docs/sdd/guides/commits.md`）にする。
  ユーザーのルールが Conventional Commits を求めていても、この形式はそれを満たす。コミットのハッシュは spec に書かない（道具が自動で求める）。
- `git commit --amend`、`--allow-empty`、`--no-verify` は使わない。タスクの内容が他のタスクに含まれてしまった場合は、
  空のコミットを作らず、tasks.ts でタスクを統合する（`docs/sdd/guides/review-feedback.md` の手順2と4）。
- **specと違う実装を、specを直さずに進めない。**
- **時間のかかるコマンドを待ち続けない。** 開発サーバーや監視（watch）は、バックグラウンドで起動するか、`deno task acceptance` に任せる。
  コマンドには上限時間を決めて実行する。同じコマンドが2回止まったら、再実行せずに原因を調べる
  （試行で、テストが品質ゲートを呼び、無限に再帰して止まった）。
- **品質ゲートを緩めて通さない**（止まる条件3）。finish-report が、除外の追加やレベルの引き下げを検出する。
- **E2E テストを削除しない。** テストを減らす相談を受けても、画面がある案件の E2E は残す（`config.ts` の `ui` が true なら必須）。
- 実装中に、ADR になる判断（新しい依存、構成の方針）や、規約・ADR からの逸脱が必要になったら、design.ts を直すだけでなく止まって質問する（止まる条件2）。

## 1. 前提を確かめる（ここで問題があれば、実装を始めずに止まる）

1. `deno task current` で issue の ID とモードを特定する。
2. `deno task verify <ID>` のエラーが無いことを確かめる。
3. `git status --porcelain` で作業ツリーを確かめる。
   - **変更が無い**: 最初から、または前回の続きから始める（`deno task next <ID>` で次のタスクが分かる）。
   - **変更がある（中断からの再開）**: `deno task next <ID>` で作業中（`doing`）のタスクを確かめ、変更がそのタスクの分かを
     `git diff` で確かめる。そのタスクの分なら、続きを実装して手順2-5から進める。そうでなければ止まってユーザーに確認する。
4. `deno task gate` を一度実行し、**実装を始める前の時点の結果**を控えておく（再開の場合は省いてよい）。
   - 失敗しているものがあっても止まらない。自分の変更による失敗と区別するために控え、最後の報告に含める。
   - 品質ゲートが設定されていない（`commands` が空）場合も止まらない。`package.json` の scripts、`composer.json`、
     `pyproject.toml`、`Makefile` などからテストのコマンドを推定して使い、品質ゲートが未設定であることを報告に含める。

## 2. タスクを1件ずつ実装する

すべてのタスクが完了するまで、次を繰り返す。1件ごとに報告して止まることはしない。

### 2-1. 次のタスクを確かめる

```sh
deno task next <ID>
```

タスクの説明、実現する要件、関係するコンポーネント、エラー処理、検証する対象（受け入れ条件）、影響範囲が表示される。
必要に応じて `docs/sdd/architecture.ts`、`conventions.ts`、`design.ts` の該当箇所を読む。

### 2-2. 着手する

spec のそのタスクの `status` を `"doing"` にする。

### 2-3. 実装する

- タスクの説明と、表示された要件・受け入れ条件・インターフェースに従う。`conventions.ts` の規約と、既存コードの書き方に合わせる。
  特に、手で守る規約（`enforcedBy: "manual"`）は、design.ts（軽量モードは spec.ts）の `conventionsCompliance` に書いた守り方どおりにする。
- **テストのタスク**: 受け入れ条件の `when` を実際に実行し、`then` を観測するテストにする。
  ファイルに文字列があるかを調べるだけのテストにしない。品質ゲートでスキップされるテストにしない。
  - 再現テスト（バグの修正の最初のタスク）は、**修正前のコードで失敗すること**を実行して確かめる。
    失敗しなければ再現できていないので、原因の見直しが要る。spec の根本原因や受け入れ条件が誤っていたなら、止まる条件1に当たる。
  - 現状の振る舞いを固定するテストは、**変更前のコードで成功すること**を確かめる。
- **実装のタスク**: 関係するテストが通るようにする。

### 2-4. specの見直しが必要になったら

| 必要になったこと | 対応 |
|---|---|
| 影響範囲（impact）に無いファイルの変更 | AIが spec の impact（とコンポーネントの files）を直して続ける |
| 設計（コンポーネント、インターフェース、データモデル、方針）の見直し | AIが design.ts（軽量モードは approach）を直して続ける |
| タスクの分割・統合・追加 | AIが tasks を直して続ける（IDは振り直さず、追加は末尾の番号で） |
| 要件・受け入れ条件・変えてはいけない振る舞いの変更 | **止まる**（止まる条件1） |
| accepted の ADR と食い違う実装、ADR になる判断、規約からの逸脱 | **止まる**（止まる条件2） |
| 品質ゲートを緩める（除外の追加、レベルの引き下げ） | **止まる**（止まる条件3） |

AIが直した場合は、`docs/sdd/guides/review-feedback.md` の手順2（影響の洗い出し）と手順4（check、verify）を行い、
直した内容を控えて最後の報告に含める。impact を直した場合は `deno task conflicts --issue <ID>` も実行する。

### 2-5. 品質ゲートを通す

```sh
deno task gate
```

失敗したら直して、通るまで繰り返す。手順1で控えた「開始前から失敗していたもの」は、このタスクで悪化していなければよい。
同じ失敗を直せないまま何度も繰り返す場合は、原因を調べ、環境の問題なら止まる条件4に当たる。
品質ゲートを通すためにテストを除外する（スキップする、除外する設定を足す）ことはしない。

### 2-6. コミットする

1. spec のそのタスクの `status` を `"done"` にする。
2. コードの変更と spec の更新をまとめてコミットする。コミットメッセージは `<type>(<ID>): <タスクID> <タスクのタイトル>`（type はタスクの kind から決める）。
   pre-commit hook が spec を検査する。失敗したら直してからコミットし直す。
3. `git status --porcelain` で作業ツリーに変更が残っていないことを確かめてから、次のタスクに進む。

## 3. すべてのタスクが終わったら

1. `deno task scope <ID>` で、実際に変えたファイルと影響範囲を照合する。影響範囲の外の変更があれば spec を直す（手順2-4）。
2. `deno task gate --full`（E2E テストを含む）と `deno task verify <ID>` を実行し、通ることを確かめる。
   ビルドが失敗していたら、以前からの失敗でも直す（人の受け入れテストで同じ手順が失敗するため）。直せなければ止まる（止まる条件4）。
3. **受け入れテストの準備を、実行できる形で書く。** spec の `acceptanceGuide`（tasks.ts、軽量モードは spec.ts）に書く（型の説明に従う）。
   - `setup`: 準備のコマンド。**人の手元の環境（すでにセットアップ済みのDB）でも通るように**、マイグレーションを含める
   - `server`: アプリのサーバー（Docker で起動済みなら省く）
   - `accounts`: テスト用のアカウント（ID、パスワード、権限）。人に登録させない
   - `data`: 受け入れ条件ごとのデータを用意するコマンド（開発用のシーダーなど）と、実行後の状態（件数など）
   - `check`: 確かめる画面の URL と、表示されるべき文字列
4. **`deno task acceptance <ID>` を実行し、通るまで直す。** 準備のコマンドとデータのコマンドを実際に実行し、サーバーを起動して画面を確かめる。
   これが通らないまま、受け入れテストを頼まない。画面がある案件では、E2E のスクリーンショットを見て、表示の崩れが無いかも確かめる。
   通ったら `chore(<ID>): 受け入れテストの準備を追加` としてコミットする。
5. `deno task render <ID>` でHTMLを生成し直す。
6. push する（リモートが無ければ省く）。
7. ユーザーに報告し、**受け入れテストを依頼する**。
   - 実装したタスクとコミットの一覧（`deno task next <ID>` で確かめられる）
   - 品質ゲートの結果（開始前から失敗していたもの、未設定のものを含む）
   - AIが直した spec の内容（あれば）
   - `deno task acceptance <ID>` の結果と、自分で確かめた受け入れ条件・確かめられなかったもの
   - 受け入れテストの手順（起動の手順、アカウント、データ）と、生成したHTMLのパス。HTMLの「受け入れテスト」の章に、
     人が確かめる受け入れ条件の一覧と準備が載っている
   - 合格したら sdd-finish、不合格なら内容をチャットで伝えてもらうよう案内する

## 受け入れテストで不合格だったら

スキルが呼ばれていなくても（チャットで不具合を伝えられただけでも）、`docs/sdd/guides/review-feedback.md` の
「受け入れテストで不合格だった場合」の手順で対応する（タスクを追加 → テスト → 品質ゲート → コミット → `acceptance` → 再依頼）。

- 受け入れ条件どおりに動いていない: コードを直す。必要ならタスクを追加する（末尾の番号で）。品質ゲートを通してコミットし、受け入れテストをもう一度依頼する。
- 受け入れ条件そのものが違っていた: 要件を直す（ユーザーの確認が要る）。その後、影響を受ける設計・タスク・コードを直す。
- 受け入れ条件の範囲外の調整（見た目など）: review-feedback.md の「受け入れ条件の範囲外の調整」に従う。
