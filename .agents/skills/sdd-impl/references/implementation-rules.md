# 実装の進め方

## 目次

- 基本方針
- 1つのタスクの進め方
- テストの書き方
- 設計との線引き
- テストが通らないとき
- セルフレビューで必ず確認すること

## 基本方針

- tasks.md は実装の順番、design.md は作るものの中身を決めている。実装の中で新しい判断をしない。
- 1つのタスクで扱うのは、そのタスクのコンポーネントの `場所` と、`テストを書く` にあるテストファイルだけにする。
- テストを先に書き、失敗することを確かめてから実装する。
- 既存のコードの書き方（名前の付け方、エラーの返し方、フォルダの分け方）に合わせる。design.md の「既存コードの調査」と、`場所` の周りのファイルを読んで確かめる。

## 1つのタスクの進め方

1. 次を読む。
   - tasks.md のそのタスクのすべての項目。
   - design.md のそのコンポーネント（`場所`、`入出力`、`決めておく振る舞い`）。
   - `守る技術判断` にある `D-xx` の `決定`、`adr:<id>`、`decision:<id>` のファイル。
   - `実装する` に「データ」や「移行・リリース」の項目があれば、design.md のその項目。
   - `テストを書く` の根拠にある受け入れ条件の「前提」「操作」「結果」（requirements.md）。
   - `（変更）` のコンポーネントなら、`場所` の今のコードと、そのコードを使っている箇所。
2. `テストを書く` のテストを、すべて書く。
3. 書いたテストを実行し、失敗することを確かめる。失敗の理由が「まだ実装していないから」（関数やファイルがない、結果が違う）であることを出力で確かめる。テスト自体の誤り（書き間違い、前提の作り方の誤り）で失敗している場合は、テストを直す。
   - 実装する前からテストが通る場合は、テストが受け入れ条件の「結果」を本当に確かめているかを見直す。`（変更）` のコンポーネントで、既存のコードがすでにそう動いているなら、そのまま進め、報告に書く。
4. `実装する` のとおりに実装する。入出力の名前、型、エラーの種類と返し方は、design.md のとおりにする。
5. `完了条件` のコマンドを実行し、このタスクのテストと既存のテストがすべて通ることを確かめる。
6. `レビューで確かめる` があれば、実装したコードで1つずつ確かめる。確かめた箇所（ファイルと関数）を、仕上げの報告に書けるように控える。
7. tasks.md のそのタスクを `状態: done` にする。

## テストの書き方

- テストファイルは、`テストを書く` のパスに置く。1行の観点につき、テストを少なくとも1つ書く。
- テストの名前には、確かめること（受け入れ条件の結果や振る舞い）を書き、受け入れ条件IDを含める（例: `order-export.csv-download.ac2: 期間内に注文がないとき、見出し行だけのCSVが返る`）。
- 受け入れ条件のテストは、requirements.md の「前提」を作り、「操作」を行い、「結果」を確かめる。受け入れ条件にある具体的な値（件数、日付、入力値）をそのまま使う。
- 「結果」は、利用者から見える形のまま確かめる。E2Eなら画面の表示、結合テストなら応答を確かめ、内部の関数が呼ばれたことだけで済ませない。
- 前提の作り方（ログイン状態、テストデータ、現在時刻）は、design.md のテスト方針に書かれた方法だけを使う。
- 確かめたいものそのものを差し替え（モック）にしない。差し替えてよいのは、テスト方針に書かれたもの（外部サービス、現在時刻など）だけ。
- テストの中の重複をまとめる補助の関数（テストデータを作る関数など）は、テストのフォルダの中に置く。

## 設計との線引き

### 止まるもの

次に当たる場合は、実装で補わずに止まり、SKILL.md の「設計と合わないことが見つかったとき」に進む。

- 設計どおりの `入出力`（名前、引数、戻り値、エラーの種類と返し方）や `決めておく振る舞い` では、テストが通らない、または要件を満たせない。
- 設計にない入出力や振る舞いが必要になる（例: 呼ぶ側が必要とする情報を、設計の戻り値が含んでいない）。
- 設計にないライブラリ（依存関係の定義への追加）が必要になる。
- 設計の `場所` にない本番のファイルを作る必要がある。
- design.md の「データ」にない、テーブル、列、索引、制約の追加や変更が必要になる。
- design.md の「移行・リリース」にない、環境変数や設定が必要になる。
- 技術判断の `決定`、ADR、全体方針と合わない実装にしないと進めない。
- テストのためだけの仕組み（テスト用のデータ投入口、テスト用の設定）を、テスト方針にない形で本番のコードに置く必要がある。
- `テストを書く` のテストを、その検証方法で書けない（前提を作れない、結果を確かめられない）。
- 既存のテストが壊れ、それが design.md の「移行・リリース」に書かれた変更ではない。

### 止まらずに進めるもの

次は設計に書かれていなくても進め、仕上げの報告の「設計に書かれていない内部の工夫」に書く。

- `場所` のファイルの中だけで使う関数、定数、型（外から呼ばれないもの）を足す。
- `場所` のファイルの中の組み立て方（処理の分け方、内部の変数名）を決める。
- テストのフォルダの中に、テストの補助の関数やテストデータを置く。
- lintや型チェックの指摘を、振る舞いを変えずに直す。

迷う場合は、止まるものとして扱う。

## テストが通らないとき

- 失敗の出力を読み、原因を1つに絞ってから直す。当てずっぽうに書き換えない。
- 原因が実装の誤りなら、実装を直す。原因がテストの誤り（受け入れ条件の値の写し間違い、前提の作り方の誤り）なら、テストを直す。受け入れ条件の「結果」と合わなくなるような直し方はしない。
- 設計どおりでは通らないと分かったら、「止まるもの」として扱う。
- 同じテストで3回直しても通らない場合は止まり、試したことと出力をユーザーに報告する。
- 実行環境の問題（DBに接続できない、ブラウザが起動しない）は、実装で回避せずに止まり、ユーザーに伝える。

## セルフレビューで必ず確認すること

- すべてのタスクが `状態: done` になっているか。
- 各コンポーネントの入出力（名前、引数、戻り値、エラーの返し方）が、design.md と一致しているか。
- すべての `決めておく振る舞い` が実装され、テストか「レビューで確かめる」で確かめられているか。
- `守る技術判断` の決定、ADR、全体方針に反する実装がないか。
- design.md の「データ」と「移行・リリース」の項目が、すべて実装されているか（マイグレーション、環境変数の検査など）。
- 受け入れ条件のテストが、「結果」を利用者から見える形で確かめているか。受け入れ条件の値を使っているか。
- テストのためだけの仕組みが、テスト方針に書かれた形（本番で使えなくする仕組みを含む）になっているか。
- 設計にないライブラリ、本番のファイル、入出力を足していないか。足した内部の工夫は、すべて報告に書いたか。
- デバッグ用の出力、コメントアウトしたコード、飛ばしたテスト（`skip`、`only` など）が残っていないか。
