# 独立したレビューの依頼文

仕上げの確認で、実装した文脈を持たないレビュー役に差分を読ませる。
サブエージェントを起動できる環境では、次の依頼文の `<...>` を埋めて渡す。
サブエージェントを起動できない場合は、会話の経緯を使わず、ここに挙げたファイルと差分だけを読み直して、同じ観点で自分でレビューする。

## 依頼文

```text
あなたは実装レビューの担当です。次の実装を、PRを出す前に直すべき問題がないかという観点でレビューしてください。
ファイルは読むだけにし、編集しないでください。gitは読むだけの操作（status、diff、log、show）に限ります。

- 差分: `git merge-base HEAD <既定のブランチ（例: origin/main、main、master）>` で得たコミットと作業ツリーの差分（`git diff <そのコミット>`）と、`git status --short` の未追跡のファイル。docs/specs/ の下は除く。
- 設計: <docs/specs/<feature>/design.md のパス>
- タスク: <docs/specs/<feature>/tasks.md のパス>
- 要件: <docs/specs/<feature>/requirements.md のパス>（要件、受け入れ条件、制約・前提だけを読む）
- ADRと全体方針: <design.md の技術判断で参照している docs/adr/ と docs/decisions/ のファイルのパス。なければ「なし」>
- 実装のルール: <このスキルの references/implementation-rules.md のパス>

次の観点で、実際に問題になる具体的な入力や手順を挙げて指摘してください。一般論だけの指摘はしないでください。

1. 設計との食い違い: design.md の入出力（名前、引数、戻り値、エラーの返し方）、決めておく振る舞い、データ、移行・リリース、技術判断の決定と合わない実装。設計にない入出力、ライブラリ、本番のファイル。
2. 要件との食い違い: 受け入れ条件の前提と操作で、結果のとおりにならない場合。境界の値（上限ちょうど、上限+1、0件、空文字）での動き。
3. テストの質: 受け入れ条件の「結果」を利用者から見える形で確かめていないテスト、確かめたいものを差し替えたテスト、実装がなくても通るテスト、飛ばしたテスト。tasks.md の「テストを書く」の観点で、テストがないもの。
4. セキュリティ: 認証・権限の抜け、利用者が指定できる値の検証のすり抜け、応答の違いから分かってしまう情報、秘密の値のログ出力、テスト用の仕組みが本番で有効になる経路。
5. データ: マイグレーションとコードの食い違い、並びが1つに決まらない問い合わせ、同時に操作したときの重複や不整合、トランザクションの抜け。
6. 残りもの: デバッグ用の出力、コメントアウトしたコード、使われていないコード、既存の書き方と合わない名前や構成。

結果は次の形式で返してください。問題がない観点は「なし」と書いてください。

- <観点の番号> <重大度: 高 | 中 | 低> <ファイルと行、または tasks.md のタスク番号>: <問題> / <問題になる入力や手順の例> / <直し方の案>
```

## 指摘の扱い

- 指摘を1件ずつ確かめる。レビュー役の指摘が誤っている場合もあるので、コード、design.md、要件を読み直して判断する。
- 正しい指摘は、次のどれかで扱う。
  - 設計の範囲で直せる（implementation-rules.md の「止まらずに進めるもの」か、設計どおりに直すだけ）: コードかテストを直す。
  - 直すには設計を変える必要がある: SKILL.md の「設計と合わないことが見つかったとき」に進む。
- 誤りと判断した指摘は、理由を1文で添えて、仕上げの報告に載せる。
