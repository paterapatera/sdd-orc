# 実装PRの本文と後片付けの形式

## 目次

- 実装PRの本文
- 要件の取り込み
- 解釈の反映
- 用語の取り込み
- ディレクトリの削除

## 実装PRの本文

仕上げの確認のあとに、次の形で案を出力する。ユーザーがPRの本文に貼る。

```markdown
#42 の実装です。

## できるようになること
- 経理担当者が、注文履歴の画面で期間を指定し、注文をCSVでダウンロードできる。

## 要件の解釈（ご確認ください）
- order-export.csv-columns: 税込金額は、1円未満を切り捨てた整数で出力します。
（ない場合は「なし」）

## 手動確認
- [ ] auth.accounting-role.ac1: 経理ロールを持たない利用者で注文履歴画面を開き、期間の入力欄とダウンロードボタンがないこと
（ない場合は「なし」）

## テスト
- `npm test`: 通過（42件）
- `npm run test:e2e`: 通過（6件）

## マージの前に
- レビューが終わったら、要件を docs/capabilities/ に取り込み、docs/specs/42-order-csv-export/ を削除する変更をこのPRに追加します。
```

- 「できるようになること」は、requirements.md のユーザーストーリーと要件から、顧客に分かる言葉で1〜3行書く。APIやファイルの名前は書かない。
- 「要件の解釈」は、design.md の `種類: 要件の解釈` の技術判断ごとに、関係する要件IDと、決めた解釈を平易な日本語で1行ずつ書く。`決定者: 既存の慣習` のものも載せる。
- 「手動確認」は、tasks.md の `手動確認` をすべて載せる。

## 要件の取り込み

requirements.md の「既存仕様への影響」に従って、`docs/capabilities/<業務領域>.md` を直す。業務領域は、要件IDの `.` より前。

- 追加: その業務領域のファイルの末尾に、要件を足す。ファイルがなければ作る。
- 変更: 同じIDの要件を、requirements.md の要件で置き換える。位置は変えない。
- 削除: 同じIDの要件を消す。

要件は、requirements.md の本文と同じ形で書き写す。`根拠` だけは、質問ログが削除されるため、issue番号に置き換える。

```markdown
### order-export.period-limit 期間の上限
- 種別: 機能
- 要件: 指定期間が12ヶ月を超える場合、システムはエラーを表示し、出力しない。
- 根拠: #42
- 受け入れ条件:
  - order-export.period-limit.ac1 期間超過
    - 前提: 経理担当者としてログインしている。
    - 操作: 期間を13ヶ月にしてダウンロードする。
    - 結果: エラーが表示され、ファイルは出力されない。
```

- 見出し、`種別`、`要件`、受け入れ条件は、1文字も変えずに書き写す。
- `根拠` は `#<issue番号>` にする。変更した要件で、前の根拠が残っている場合は、`#12, #42` のように取り込んだ順に並べる。
- 新しくファイルを作るときは、1行目を `# <業務領域>: <説明>` にする。説明は `docs/capabilities/README.md` の一覧と同じにする。

## 解釈の反映

design.md の `種類: 要件の解釈` の技術判断を、関係する要件の `- 要件:` の次の行に `- 解釈:` として書く。

```markdown
- 要件: 指定期間が12ヶ月を超える場合、システムはエラーを表示し、出力しない。
- 解釈: 「12ヶ月」は、開始日の12ヶ月後の同じ日の前日までとする。
```

- 関係する要件は、design.md の `決めておく振る舞い` のうち、根拠にその `D-xx` と要件IDが並んでいるもの。
- 顧客が承認した要件の文は変えずに、解釈だけを足す。1つの解釈につき1行にする。
- 実装の言葉（関数名、ライブラリ名、型）ではなく、利用者から見える結果で書く（例: 「絵文字は1文字と数える」。「String.length で数える」とは書かない）。
- `D-xx` や design.md は書かない（削除されるため）。
- 同じ要件にすでに `- 解釈:` がある場合は、その下に足す。内容が食い違う場合は止まり、ユーザーに報告する。

## 用語の取り込み

requirements.md の「用語」で、末尾に「（新規）」が付いたものを、`docs/glossary.md` に足す。

- 形式は `- <用語>: <定義>`。「（新規）」は外す。
- `docs/glossary.md` がなければ、1行目を `# 用語集` にして作る。
- 同じ用語がすでにあり、定義が違う場合は止まり、ユーザーに報告する（他の機能が先に同じ用語を定義している）。

## ディレクトリの削除

- 後片付けの検証スクリプトでエラーがなくなってから、`docs/specs/<feature>/` をディレクトリごと削除する。
- 削除するのは、requirements.md、design.md、tasks.md を含むそのディレクトリだけ。`docs/adr/` と `docs/decisions/` は残す。
- 削除した内容は、実装PRのコミットの履歴に残る。
