# sdd-req: 要件定義

1件のissue（ユーザーストーリー）から `docs/specs/<feature>/requirements.md` を作り、ユーザーへの質問と顧客のPRレビューを繰り返して、要件を確定（`status: approved`）させる。

## やらないこと

- 書き込みを伴うgit操作（ブランチ作成、コミット、プッシュ、PR作成、マージ）。ユーザーが手動で行う。読み取りだけの `git fetch`、`git show` などは使ってよい。
- issueやPRの取得・作成。内容はユーザーがチャットに貼り付ける。
- 設計（API、DB、画面構成、変更するコンポーネント）。ステップ3（design）で扱う。
- issueや回答に書かれていない内容を推測で書くこと。不明点は必ず質問にする。
- 他のissueの requirements.md や、他のissueが作った全体方針（`docs/decisions/`）の編集。影響があればユーザーに報告する。例外は「全体方針の変更」で古い全体方針を `superseded` にする場合だけ。

## 参照ファイル

- テンプレート: [templates/requirements.md](templates/requirements.md)、全体方針: [templates/decision.md](templates/decision.md)、業務領域の一覧: [templates/capabilities-readme.md](templates/capabilities-readme.md)
- 記入ルール（状態、ID、EARS、根拠、質問ログ、全体方針）: [references/writing-rules.md](references/writing-rules.md)
- 質問の観点と優先順: [references/clarification-checklist.md](references/clarification-checklist.md)
- 記入例: [references/example.md](references/example.md)
- 共有情報の一覧: `python3 <このスキルのディレクトリ>/scripts/context.py <リポジトリのルート> [--exclude-feature <feature>]`
- 検証スクリプト: `python3 <このスキルのディレクトリ>/scripts/validate_requirements.py <requirements.md> [--target in_review|approved]`

作業を始める前に、テンプレートと記入ルールを必ず読む。

## 共通の準備

複数人が並行して要件定義を進める前提で、作業のたびに（再開したときも）最初に次を行う。

1. `git fetch --prune` を実行し、リモートブランチを最新にする。失敗した場合（gitリポジトリでない、ネットワークに接続できないなど）は、その旨をユーザーに伝えて続ける。
2. `context.py` を実行し、業務領域の一覧、全体方針、他の要件定義（mainにあるものと、作業中のブランチにあるもの）を確認する。自分の feature は `--exclude-feature` で除く。
3. `docs/glossary.md` があれば読む。
4. `docs/capabilities/README.md` がない場合は、テンプレートから作成してよいかユーザーに確認する。

作業中のブランチにある内容は、まだ顧客の承認を得ていない。根拠にせず、衝突や重複に気づくための参考にだけ使う。

## 手順

### 対象の決定

1回の実行で扱う feature は1つだけにする。複数の requirements.md をまとめて作ったり、進めたりしない。質問は1問ずつ行い、要件PRも feature ごとに分かれるため。

1. issueが貼り付けられた場合は、そのissueを対象にする。複数のissueが貼り付けられた場合は、どれから扱うかを選択肢形式でユーザーに選んでもらう。
2. ユーザーが feature（ディレクトリ名、issue番号、ファイル）を指定していれば、それを対象にする。
3. どちらでもなければ、`docs/specs/*/requirements.md` のうち `approved` でないものを、feature 名と status の一覧にする。一覧から1つを、選択肢形式でユーザーに選んでもらう。候補が1つだけでも、推測で決めずに選んでもらう。候補がなければ、その旨を伝え、issueの貼り付けを依頼する。
4. 対象の feature を「0. 状況の判定」に進める。

### 0. 状況の判定

- issueが貼り付けられ、対応する requirements.md がない → 「1. 新規作成」
- `status: drafting` または `clarifying` → 「2. 質問」
- `status: in_review` で、顧客のPRコメントや確認結果が伝えられた → 「5. 顧客フィードバックの反映」
- `status: in_review` で、確認事項がすべてチェック済みになり、ユーザーが承認を依頼した → 「6. 承認」
- `status: approved` で、設計（sdd-design）から要件の問題が報告された → 「承認後の要件変更」
- 承認済みの全体方針を変えたいと依頼された → 「全体方針の変更」
- どれにも当てはまらない → ユーザーに何をしたいか確認する。

### 1. 新規作成

1. 貼り付けられたissueのタイトル、本文、コメントを読む。issue番号が分からない場合は、ファイルを作る前に止まってユーザーに聞く。仮の番号で進めない。
2. feature名を `{issue番号}-{英語の短い名前}`（小文字、ハイフン区切り、2〜4語）で決める。
3. 影響する業務領域を `docs/capabilities/README.md` の一覧から選ぶ。
   - 当てはまるものがない場合は、新しい業務領域の名前と説明を選択肢にしてユーザーに質問する。承認されたら、README.md の一覧に1行追加する。
   - 作業中のブランチで同じ意味の業務領域が追加されていれば、その名前を推奨の選択肢にする。
4. 影響する業務領域の `docs/capabilities/<業務領域>.md` と、`depends_on` の依存先のうち承認済みでまだ実装されていないものの requirements.md を読む。既存の要件を変更する場合は既存のIDをそのまま使い、変更前の要件文を「現行」として控える。
5. 他の要件定義との関係を確認する。
   - 他のissueの機能がないと普通の流れが成り立たない場合（本当の依存）は、その issue 番号を `depends_on` に書く。その機能がないうちは発動しないだけの要件（条件付きの前提、例: 「ログイン済みなら拒否する」）は `depends_on` に書かず、制約・前提に機能を提供する順番を書く。判断できない場合はユーザーに質問する。
   - 必要な機能のissueがまだない場合は、そのissueの下書き（タイトル、ユーザーストーリー、スコープ）をチャットに出力し、ユーザーにissueを作って番号を教えてもらう。「番号は決まり次第追記する」のまま先に進めない。
   - 同じ要件を変更しようとしている要件定義があれば、ユーザーに伝える。
6. テンプレートをもとに `docs/specs/<feature>/requirements.md` を作る（`status: drafting`）。
   - issueから読み取れる内容だけを書く。
   - 質問の観点に沿って不明点を洗い出し、該当箇所に `[要確認: Q-xx]` を置き、質問ログに `状態: open` で登録する。
   - `accepted` の全体方針で決まっていることは質問にせず、そのまま本文に反映して、根拠に `decision:<id>` と書く。
7. 「分割判定」を行う。
8. `status: clarifying` にして「2. 質問」へ進む。

### 2. 質問（1回に1問）

1. `open` の質問から、質問の観点の優先順に従って1問選ぶ。
2. 選択肢形式で質問する。選択肢形式の質問ツールがあれば使い、なければ番号付きの選択肢をテキストで示す。
   - 選択肢は2〜4個に、必ず「顧客に確認」を加える。推奨する選択肢を先頭に置き「（推奨）」と付ける。
   - 質問文には、なぜそれを決める必要があるかを1文添える。
   - 作業中のブランチに同じ論点の全体方針（`proposed`）があれば、その内容を選択肢の1つにし、「〇〇（#番号で検討中の方針に合わせる）」のように出典を添える。
3. 回答を反映する。
   - ユーザーが答えた場合: `状態: answered_by_user`、`回答者: ユーザー`。本文に反映し、顧客への確認事項に未チェックで追加する。
   - 「顧客に確認」が選ばれた場合: `状態: needs_customer`。推奨の選択肢を暫定の扱いとして本文に反映し、顧客への確認事項に未チェックで追加する。ユーザーが別の暫定の扱いを指定した場合はそれに従う。
   - どちらの場合も、本文の `[要確認: Q-xx]` を消し、反映した要件の根拠に `Q-xx` を書く。
   - 回答がこの機能だけでなく他の機能にも当てはまる内容（例: 「全画面でログイン必須」「日付はすべて日本時間」）なら、全体方針として登録するかをユーザーに質問する。登録する場合は、テンプレートから `docs/decisions/<id>.md` を `status: proposed` で作り、関係する要件の根拠に `decision:<id>` を加え、顧客への確認事項の該当行の末尾に「（全体方針 decision:<id> として登録）」と付ける。
4. 回答と既存の要件・回答済みの質問との組み合わせを見直す。
   - 矛盾や、組み合わせたときに決まっていないケース（例: 「著者は任意」と「タイトルと著者で重複判定」）があれば、質問ログに `open` で追加する。
   - 新しい回答によって意味がなくなった質問（例: 項目の変更でなくなった「著者」についての質問、スコープ外になった機能についての質問）は、`状態: withdrawn` にして `理由` を書き、顧客への確認事項と要件の根拠から外す。
   - 前提が変わって決め直す必要がある論点は、新しい質問を作らず、既存の質問を `open` に戻して聞き直す。見出しの文言も最新の用語に直す。
5. スコープについての回答を反映した直後と、要件が増えたときに「分割判定」を行う。詳細の質問に進む前に分割を決める。
6. `open` が残っていれば 2-1 に戻る。なくなれば「3. セルフレビュー」へ進む。

ユーザーが途中で中断しても、状態はファイルに残る。次回は「0. 状況の判定」から再開する。

### 3. セルフレビュー

顧客に見せる前に、抜けがないかを自分で確認する。

1. 質問の観点を上から順にすべて見直し、観点ごとに「本文のどこで扱ったか」を確認する。本文で扱っていない観点は、質問ログに `open` で追加する。「扱わなくてよい」と判断した観点も自分だけで決めず、その判断を選択肢の1つにした質問として追加する。
2. 質問の観点の「セルフレビューで必ず確認すること」を1つずつ確かめる。
3. 要件ごとに、根拠との突き合わせを行う。要件と受け入れ条件の文を「条件」と「結果」に分け、それぞれが根拠に書いた issue や回答の中に書かれているかを確かめる。書かれていない部分（例: 根拠の回答は「ログイン必須」だけなのに、要件に「エラーを表示する」とある）は、質問ログに `open` で追加する。
4. 入力項目ごとに、質問の観点の「入力項目ごとに決めること」の5点が決まっているかを確かめる。決まっていない点は、質問ログに `open` で追加する。
5. `open` を追加した場合は「2. 質問」に戻る。
6. 確認結果を、次の形式でユーザーに報告する。省略しない。

```markdown
#### 観点ごとの確認
| 観点 | 本文での扱い |
|---|---|
| スコープ | ... |
（質問の観点の8項目すべて）

#### 入力項目ごとの確認
| 入力項目 | 必須 | 形式 | 上限 | 空白 | 値の範囲 |
|---|---|---|---|---|---|
| 本のタイトル | 必須 | ... | 100文字 | ... | 当てはまらない（自由入力のため） |

#### 根拠との突き合わせ
- 根拠のない振る舞い: なし（見つかった場合は、要件IDと追加した質問ID）
```

### 4. レビュー準備

1. 「共通の準備」の1と2を行ったうえで、`--target in_review` で検証スクリプトを実行し、エラーがなくなるまで直す。
   - 警告は内容を確認し、必要なら直す。
   - 他の要件定義との重なり（同じ要件の変更、同じ用語の別定義、同じIDの全体方針）の警告は、自分で相手の内容に合わせず、ユーザーに報告して、担当者と調整してもらう。
2. `status: in_review` にする。
3. ユーザーに次を伝える。
   - 要件PRを作成してほしいこと。
   - PR本文の案。顧客向けに、変更の概要（3行程度）と「確認してほしいこと」（顧客への確認事項をそのまま転記）を平易な日本語で書く。
   - 顧客のコメントが届いたら、チャットに貼り付けてほしいこと。

### 5. 顧客フィードバックの反映

1. 貼り付けられたコメントや確認結果を1件ずつ読み、次のように対応する。「ほかは問題なし」と伝えられた項目は承認として扱う。
   - 本文に反映する前に、コメントの解釈を1文で書き出す（例: 「『0埋めはしない』は、0埋めしない入力も受け付けるという意味」）。解釈が1つに決まらない場合は、考えられる解釈を選択肢にしてユーザーに質問する（「顧客に確認」も選択肢に入れる）。特に、形式や範囲についての短いコメントと、「どちら」「それ」のように指す対象が曖昧な言葉に注意する。
   - 書き出した解釈は、反映結果の報告でユーザーに示す。
   - 確認事項への承認: 該当項目を `[x]` にし、質問を `answered_by_customer` に更新して `顧客確認日` を書く。`回答者` と `回答日` は書き換えない。`needs_customer` だった質問は、暫定の扱いを回答として記録し、`回答者: 顧客` とする。全体方針として登録した項目なら、その全体方針を `status: accepted` にして `顧客確認日` を書く。
   - 暫定の扱いと異なる回答や、修正の依頼: 既存の質問なら回答を書き換えて `回答者: 顧客` とし、新しい話題なら質問を追加する（`状態: answered_by_customer`）。本文に反映し、確認事項に `[x]` で載せる。
   - 意図が読み取れないコメント: 推測せず、「2. 質問」と同じ形式でユーザーに1問ずつ聞く。
   - `回答` 欄には、顧客が実際に言った内容だけを書く。AIの解釈、補足、据え置きの判断は書かない。
2. 顧客の回答で本文を変えた場合は、その回答が影響する範囲を洗い出す。対象は、変更前の内容を前提にしていた質問、要件、スコープ、目的・成功の基準。特に次を確認する。
   - 各要件が扱うデータの範囲（例: ログイン必須になったなら、重複判定や表示の対象は自分の分か、全員の分か）。
   - 目的と各ルールが矛盾しないか（例: 目的が「当時の読書を見返す」なのに、同じ本を読み直しても登録できない）。
   - 意味がなくなった質問がないか（あれば 2-4 と同じく `withdrawn` にする）。
3. 洗い出した結果に応じて、次のどちらかで進める。
   - 派生する変更がある場合: 顧客が直接言っていない変更（要件の追加、振る舞いの変更、「変えずに据え置く」という判断を含む）は、AIが決めない。質問ログに `open` で追加する。変更前の前提のもとで承認された質問は、`[x]` を `[ ]` に戻し、状態を `answered_by_user` に戻して `顧客確認日` を消し、確認事項の末尾に「（前提が変わったため再確認）」と付ける。そのうえで `status: clarifying` に戻し、「2. 質問」「3. セルフレビュー」「4. レビュー準備」を経て `in_review` に戻る。
   - 派生する変更がない場合: `in_review` のまま進める。「派生する変更はない」と判断したことと、その理由をユーザーに報告する。
   - 「派生する変更がない」と言えるのは、顧客の言葉を本文の該当箇所に書き写すだけで済む場合に限る。要件、受け入れ条件、ルールを1つでも追加・削除する場合や、顧客が触れていない部分（例: 「必須→任意」の変更に伴う「今日以前のみ」のルール）の扱いが変わる場合は、派生する変更があるものとして扱う。
4. 未チェックの確認事項が残っている場合は、ユーザーに、修正をPRに反映して残りの確認事項について顧客の確認を取ってほしいと伝え、残りの項目を一覧で示す。
5. 確認事項がすべてチェック済みなら「6. 承認」へ進む。

### 6. 承認

レビュー中の1〜4週間に、他のissueの承認で main が進んでいる可能性がある。承認の前に、最新の main との整合を必ず確かめる。

1. ユーザーに、最新の main を作業ブランチに取り込んでもらう。取り込みが済んだことを確認してから次へ進む。
2. 「共通の準備」の1と2を行ったうえで、`--target approved` で検証スクリプトを実行する。
3. エラーと警告を次のように扱う。
   - 「現行」の不一致、IDや用語の重複、置き換え済みの全体方針の参照など、要件の内容に関わるもの: 本文を直す前に、ユーザーに報告する。直すことで要件の意味が変わる場合は、顧客の確認が必要な修正として「5. 顧客フィードバックの反映」に戻る。
   - 書式だけのもの: 直して再実行する。
4. この機能が本当に依存する他のissueの機能（普通の流れに必要なもの）が、既存の機能でも `depends_on` の依存先でもない場合は、承認に進まずユーザーに確認する。条件付きの前提は、制約・前提に順番が書かれていればよい。
5. エラーがなくなったら `status: approved` にする。このissueで作った全体方針が、すべて `accepted` になっていることを確かめる。
6. ユーザーに、この変更をPRに含めたうえでマージしてほしいこと、次はステップ3（design）であることを伝える。`depends_on` の依存先がまだ approved でない場合は、依存先が approved になるまで design に進めないことも伝える。「対象の決定」の3と同じ条件で残りの feature を調べ、進められる feature があれば一覧で伝える。

## 承認後の要件変更

設計で、承認済みの要件の矛盾、実現できない要件、要件にない業務ルール、複数の意味に分かれる言葉、`depends_on` に載っていない依存が見つかった場合に使う。
sdd-design から複数の問題がまとめて報告された場合は、すべてを質問ログに登録し、顧客の確認を1回で済ませる。

1. 報告された問題を、質問ログに `open` で追加する。既存の質問と同じ論点なら、その質問を `open` に戻す。
2. `status: clarifying` に戻し、「2. 質問」「3. セルフレビュー」「4. レビュー準備」を経て `in_review` に戻る。
3. ユーザーに、要件の変更について顧客の確認を取ってほしいと伝える。要件PRがマージ済みの場合は、変更だけを含むPRを新しく作ってもらう。
4. 顧客が承認したら「6. 承認」を行い、ユーザーに sdd-design を再開してよいことを伝える。

## 全体方針の変更

承認済み（`accepted`）の全体方針を変えたい場合は、既存のファイルを書き換えず、置き換える。

1. 変更の内容を、今扱っている requirements.md の質問として記録し、顧客の確認を取る。
2. 新しい全体方針を別のIDで作り、古い全体方針を `status: superseded`、`superseded_by: <新しいID>` にする。
3. リポジトリ全体と作業中のブランチから `decision:<古いID>` を参照している requirements.md を探し、ユーザーに一覧で報告する。他のissueのファイルは編集しない。
4. 取り込み済みの `docs/capabilities/` の要件が影響を受ける場合は、今扱っている requirements.md の「既存仕様への影響（変更）」に載せる。

## 分割判定

主な基準は、スコープの対象に「単独で顧客に価値を届けられる項目」が複数あるかどうか。例: 「登録する」と「共有リンクで他の人が閲覧する」は、それぞれ単独で価値があるので分割の候補になる。
補助の目安として、要件が5件を超える場合と、影響する業務領域が3つ以上ある場合も、分割を検討する。

- スコープの対象が2項目以上ある場合は、AIが「セットで価値がある」と判断したときも含めて、必ず分割するかどうかをユーザーに質問する。選択肢には「分割する」「分割しない」の両方を入れる。
- 補助の目安に当てはまる場合も、必ずユーザーに分割を提案する。提案せずに先へ進まない。
- 分割の警告を消す目的で、要件を統合したり、書き方を変えたりしない。
- ユーザーが分割しないと判断した場合は、その旨をチャットで確認したうえで進める。

提案するときは、分割後の各issueの下書き（タイトル、ユーザーストーリー、スコープの対象と対象外）を出力し、ユーザーの判断を待つ。issueの作成はユーザーが行う。
分割する場合は、次のように進める。

- 元のissueは分割後の1つに絞って続行し、切り出した内容はスコープの対象外に「別issueで扱う」（番号が決まっていれば `#番号`）と書く。
- 切り出した側に関係する質問と回答は、issueの下書きの「決定済み事項」としてチャットに出力する。そのうえで、このファイルでは `withdrawn`（理由: 別issueへ移動）にする。このディレクトリは実装後に削除されるため、切り出した側の決定をここに残さない。
- 切り出した側に関係する要件、受け入れ条件、用語は、このファイルから削除する。
