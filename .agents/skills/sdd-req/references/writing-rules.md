## 基本方針

- 顧客がPRの差分画面で読み、行ごとにコメントする前提で書く。
- 1行に1文。表は使わない。
- 平易な日本語で書き、専門用語は「用語」で定義する。
- 「何を実現するか」だけを書く。API、DB、画面構成、変更するコンポーネントは書かない。
- 本文は質問ログを読まなくても完結させる。回答は必ず本文に反映する。
- 本文で `Q-xx` を参照するのは、要件の「根拠」だけにする。「Q-09の規則による」のように本文から質問ログを参照せず、内容を本文に書く。
- 回答に書かれていないことまで広げて書かない。例: 「比較するときは空白を除く」という回答から、「空白を除いて保存する」を導かない。広げる必要があれば質問にする。

## YAML front matter

```yaml
issue: 42                                # issue番号（数字のみ）
feature: 42-order-csv-export             # {issue番号}-{英語の短い名前}。ディレクトリ名と一致させる
status: clarifying                       # drafting | clarifying | in_review | approved
capabilities: [order-export, auth]       # 影響する業務領域。docs/capabilities/README.md の一覧から選ぶ
depends_on: []                           # 先に承認されている必要があるissueの番号（例: [12, 15]）。なければ []
```

| status | 意味 | 次に進む条件 |
|---|---|---|
| drafting | 初稿の作成中 | 初稿を書き終えた |
| clarifying | ユーザーへの質問中 | `open` の質問が0件で、`--target in_review` の検証を通過した |
| in_review | 顧客がPRでレビュー中 | 確認事項がすべてチェック済みで、`--target approved` の検証を通過した |
| approved | 顧客の承認済み | ステップ3（design）に進める |

## 見出し（後続スキルとの約束）

次のH2見出しを、この順番で必ず置く。中身がない場合は `- なし` と書く。

1. 顧客への確認事項
2. ユーザーストーリー
3. 目的・成功の基準
4. スコープ（H3で「対象」「対象外」）
5. 用語
6. 要件
7. 制約・前提
8. 既存仕様への影響（H3で「追加」「変更」「削除」）
9. 質問ログ

見出しの名前を変えたり、見出しを追加したりしない。

## 要件ID

- 形式: `<業務領域>.<英語の短い名前>`（例: `order-export.csv-download`）
- 使える文字は小文字の英数字とハイフン。
- 業務領域は front matter の `capabilities` に含まれるものに限る。
- `docs/capabilities/` に取り込み済みの要件のIDは変えない。見出しの文言や内容を変えても、既存のIDをそのまま使う。
- この requirements.md で新しく作る要件のIDは、`approved` になるまでは内容に合わせて直してよい。項目の変更などで古い用語がIDに残った場合（例: 著者がなくなったのに `duplicate-title-author`）は直す。直したときは、根拠、質問の反映先、既存仕様への影響、受け入れ条件のIDもあわせて直す。
- 削除された要件のIDは再利用しない。

## 要件の書き方

要件は1つずつH3見出しにする。

```markdown
### order-export.period-limit 期間の上限
- 種別: 機能
- 要件: 指定期間が12ヶ月を超える場合、システムはエラーを表示し、出力しない。
- 根拠: Q-01
- 受け入れ条件:
  - order-export.period-limit.ac1 期間超過
    - 前提: 経理担当者としてログインしている。
    - 操作: 期間を13ヶ月にしてダウンロードする。
    - 結果: エラーが表示され、ファイルは出力されない。
```

- 種別は `機能` か `非機能`（性能、セキュリティ、監査、可用性など）。
- 「要件」は次のEARS記法のいずれかで、1文に1つの要件だけを書く。

| 型 | 書き方 |
|---|---|
| 常時 | システムは〜する。 |
| イベント | 〜したとき、システムは〜する。 |
| 状態 | 〜の間、システムは〜する。 |
| 異常 | 〜の場合、システムは〜する。 |
| オプション | 〜の機能を有効にしている場合、システムは〜する。 |

- 「目的・成功の基準」は、達成したかどうかを判定できる形で書く。可能なら数値にする。
- 「速く」「適切に」「など」のような曖昧な言葉を使わない。数値、具体的な条件、具体的な値で書く。
- 決まっていない箇所は推測で埋めず、`[要確認: Q-xx]` を置く。

## 受け入れ条件

- IDは `<要件ID>.ac<連番>`。
- 「前提」「操作」「結果」の3行をすべて書く。
- テストにそのまま使えるよう、具体的な値（件数、日付、入力値）を入れる。
- 「結果」は、利用者または検証する人から見える形で書く（例: 「完了メッセージが表示され、一覧に1件追加される」）。「記録される」「保存される」のような、システム内部の出来事だけで終わらせない。
- 1つの要件には、見出しが表す振る舞いの受け入れ条件だけを入れる。別の振る舞いは別の要件にする。
- 種別が `機能` の要件には、受け入れ条件を1つ以上付ける。`非機能` も、測定できるものは付ける。

## 根拠

要件がどこから来たかを、カンマ区切りで書く。
要件と受け入れ条件の条件・結果は、すべて根拠に書いた issue や回答の中に書かれている必要がある。根拠の回答に書かれていない振る舞い（例: 回答は「ログイン必須」だけなのに「エラーを表示する」と書く）は要件に書かず、質問にする。

- `issue`: issueの記述から読み取った。
- `Q-xx`: 質問ログの回答から決まった。
- `既存仕様`: `docs/capabilities/` の既存の要件を引き継いだ。
- `decision:<id>`: 全体方針 `docs/decisions/<id>.md` から決まった（例: `根拠: issue, decision:login-required`）。main にある全体方針か、このissueで作った全体方針に限る。作業中の他のブランチにしかない全体方針や、`superseded` の全体方針は根拠にしない。

## 用語

- この機能で使う用語を定義する。
- `docs/glossary.md` にない新しい用語には、末尾に「（新規）」と付ける。実装完了時に glossary へ取り込む目印になる。
- glossary にある用語は、glossary と同じ定義で書き、「（新規）」を付けない。
- 作業中の他の要件定義が同じ用語を新しく定義している場合は、定義をそろえる。そろえられない場合はユーザーに報告する。

## 既存仕様への影響

実装完了時に `docs/capabilities/` へ取り込む差分。

```markdown
### 追加
- order-export.csv-download
- order-export.period-limit

### 変更
- auth.accounting-role: 経理ロールの権限に「注文履歴のCSV出力」を追加する。
  - 現行: システムは、経理ロールを持つ利用者にのみ、請求書の閲覧を許可する。

### 削除
- なし
```

- 本文の要件は、すべて「追加」か「変更」のどちらかに載せる。
- 「追加」のIDは、`docs/capabilities/` にまだないIDにする。
- 「変更」と「削除」のIDは、`docs/capabilities/` にあるIDにする。`depends_on` の依存先が承認済みでまだ実装されていない（`docs/capabilities/` に取り込まれていない）場合は、その依存先の requirements.md にあるIDも使える。
- 「変更」には、何を変えるかを1文で添える。変更後の内容は本文の要件に全文を書く。
- 「変更」には、次の行に `  - 現行: ` として、`docs/capabilities/`（未実装の依存先なら、その requirements.md）にある変更前の要件文をそのまま書き写す。承認の直前に、他のissueが先に同じ要件を変えていないかを、この行で検出する。一致しなくなった場合は、最新の要件文を確認して変更内容を見直す。
- 「削除」には、削除する既存の要件IDと理由を書く。削除する要件は本文に書かない。

## 質問ログ

```markdown
### Q-01 指定できる期間の上限は？
- 状態: answered_by_customer
- 回答: 12ヶ月
- 回答者: ユーザー
- 回答日: 2026-09-28
- 顧客確認日: 2026-09-30
- 反映先: order-export.period-limit

### Q-02 キャンセルされた注文の金額はどう出力するか？
- 状態: needs_customer
- 暫定の扱い: 0円で出力する
- 反映先: order-export.csv-columns
```

| 状態 | 意味 | 必須項目 |
|---|---|---|
| open | 未回答 | なし |
| answered_by_user | ユーザーが回答した（顧客の確認が必要） | 回答、回答者（ユーザー）、回答日、反映先 |
| needs_customer | 顧客にしか分からない（暫定の扱いで進める） | 暫定の扱い、反映先 |
| answered_by_customer | 顧客が回答・承認した | 回答、回答者、回答日、顧客確認日、反映先 |
| withdrawn | 後の回答や分割で意味がなくなった | 理由 |

- 質問IDは `Q-01` からの連番。
- `回答` 欄には、回答者が実際に言った内容だけを書く。AIの解釈や補足は書かない。
- `approved` の時点では、すべての質問が `answered_by_customer` か `withdrawn` になっている必要がある。
- `withdrawn` は、項目の変更やスコープの変更で質問自体が意味を失った場合と、分割で別issueへ移した場合に使う。回答を変えただけなら取り下げず、回答を書き換える。
- 1つの論点につき質問は1つにする。前提が変わって決め直すときも、新しい質問を作らずに既存の質問を更新し、見出しも最新の用語に直す。
- `withdrawn` の質問は、顧客への確認事項に載せず、要件の根拠にも書かない。`理由` には、取り下げの原因になった質問IDか「別issueへ移動」を書く（例: `理由: Q-04 で登録項目から著者がなくなったため`）。
- `回答者` は `ユーザー` か `顧客`。ユーザーの回答を顧客が承認した場合は、`回答者: ユーザー` と `回答日` を残したまま `顧客確認日` を追加する。顧客が直接答えた、または回答を修正した場合は `回答者: 顧客` とする。
- 反映先は要件IDのほか、`スコープ`、`用語`、`制約・前提` なども書ける。
- 顧客のPRコメントで新しい話題が出た場合も、質問として記録する（`answered_by_customer`）。

## 顧客への確認事項

顧客がPRで最初に目にする場所。顧客に判断してほしいことだけを、平易な日本語で書く。

```markdown
## 顧客への確認事項
- [ ] Q-02: キャンセルされた注文の金額を0円として出力してよいか（関連: order-export.csv-columns）
- [x] Q-01: 指定できる期間を最大12ヶ月とした（関連: order-export.period-limit）
```

- `answered_by_user` と `needs_customer` の質問は、必ずここに載せる。
- 顧客の承認を得たら `[x]` にする。
- `approved` にするには、すべての項目が `[x]` である必要がある。
- 全体方針として登録した回答は、該当行の末尾に「（全体方針 decision:<id> として登録）」と付ける。

## 業務領域の一覧と docs/capabilities

`docs/capabilities/README.md` に、業務領域を1行ずつ登録する。

```markdown
## 一覧

- order-export: 注文データの出力
- auth: ログインと権限
```

- 名前は小文字の英数字とハイフン。登録済みの名前は変えない。
- 新しい業務領域は、ユーザーの承認を得てから、その要件PRで1行追加する。
- `docs/capabilities/<業務領域>.md` には、取り込み済みの要件を requirements.md と同じ形（`### <要件ID> タイトル` と `- 要件:` 以下）で書く。`根拠` は issue番号（`#42`）に置き換え、設計で決めた要件の解釈を `- 解釈:` の行で足す。取り込みは実装PRで sdd-impl が行い、このスキルでは編集しない。

## 全体方針（docs/decisions）

複数の機能にまたがる決定（例: 「全画面でログイン必須」）を、1件1ファイルで `docs/decisions/<id>.md` に残す。
requirements.md の中身は実装後に削除されるが、全体方針は他のissueの要件定義が参照するため、例外として要件PRで作り、承認と同時に main に残す。

```markdown
---
id: login-required
status: accepted
feature: 1-register-read-book
superseded_by:
---

# 全画面でログインを必須にする

- 決定: システムは、すべての画面でログインを必須にする。
- 理由: 利用者ごとにデータを分けるため。
- 適用範囲: すべての業務領域
- 決定日: 2026-09-28
- 顧客確認日: 2026-10-05
```

| status | 意味 |
|---|---|
| proposed | 要件PRで提案中（顧客の確認待ち） |
| accepted | 顧客が承認した |
| superseded | 別の全体方針に置き換えられた（`superseded_by` に置き換え先のIDを書く） |

- IDは小文字の英数字とハイフンで、内容を表す名前にする。ファイル名と `id` を一致させる。
- `feature` には、その全体方針を作った requirements.md の feature 名を書く。
- `決定`、`理由`、`適用範囲`、`決定日` は必須。`accepted` にしたら `顧客確認日` を書く。
- requirements.md を `approved` にするには、そのissueで作った全体方針がすべて `accepted` である必要がある。
- `accepted` の全体方針は書き換えない。変えるときは新しいIDで作り、古いほうを `superseded` にする。

## 後続スキルが読む範囲

ステップ3（design）以降は、`status: approved` の requirements.md から次だけを読む。

- front matter（`status`、`capabilities`、`depends_on`）
- スコープ、用語、要件、受け入れ条件、制約・前提、既存仕様への影響

顧客への確認事項と質問ログは経緯の記録なので、後続スキルは読まない。ユーザーストーリーと目的は、背景の理解にだけ使う。
