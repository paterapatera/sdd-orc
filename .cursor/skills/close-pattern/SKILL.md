# close-pattern

`eval/wiki/patterns/` の未対策を1件、採用された対策まで進める。ここはスキルの開発元であり、対象リポジトリではない。`sdd-*` をこのリポジトリに対して実行しない。

閉じたときの状態は「道具で検出」「手順で対策」「解決」のどれかである。一覧の状態名に「対策済み」は無い。原因がスキルで、道具（verify、doctor、finish-report、gate など）とテストに落とせたら「道具で検出」。手順の文章だけなら「手順で対策」。原因が検証か試験場で、そこを直して同じ失敗が残っていなければ「解決」。解決のときはスキルを変えない。

スキルを呼び出したこと（`/close-pattern`）は、確認ポイントへの回答ではない。

## 確認ポイント

ユーザーの回答を待つのは次だけである。それ以外は止まらずに進める。質問は1件ずつにする。

1. 未対策が2件以上あり、ユーザーが ID を指定していない。どれをやるかを1件だけ聞く。
2. 直しの根拠が val の記録にしか無い。読むと、その問題は train に移し、その点数は汎化の証拠にしない。読む前に、読むかを聞く。
3. 下の「着手してよいか」で、測っても却下になる見込みである。ユーザーが測ると明示するまで、スキルを変えず、`eval:auto` を始めない。
4. コミット、`git revert`、push は、ユーザーが指示するまで実行しない。却下のときは、戻すと伝えて指示を待つ。

## 守ること（試行で崩れた点）

失敗の回にだけ出る語をスキルの手順へ足すと、その回には効いても別の問題では合格が減る。P-007 で日時のタイムゾーンを別の1問として足した変更は、VAL-001 の合格が 3/3 から 1/3 に減り、却下された。

直す前に、失敗を一段上の原則にする。原則は、その回にだけ出る語を消しても残る1文である。今のスキルの文が許した振る舞いと、その文を動かす方向を勾配として書く。同じ原則の候補を2件か3件比べ、落ちた回と通った回に当てたうえで1件だけ実装する。スキルのファイルを変えるのは、この観測のあとである。却下されたら、その語を足して出さず、原則か勾配からやり直す。

この順は、具体へ戻る前の抽象化、文への勾配と候補の比較、思考と行動の交互、に合わせてある。文章だけの決まりは守られないので、`deno task eval:propose` が同じ条件を落とす。

## 手順

### 1. 対象を1件決める

`eval/wiki/index.md` と、状態が未対策の `eval/wiki/patterns/P-*.md` を読む。未対策が無ければ、変更を出さずに終わる。

`eval/wiki/skill-impact.md` で、そのパターンの却下済みの案を読む。同じ案は出さない。

### 2. 根拠は train の記録だけ

パターンに書いてある train の実行（採点の `passed`、落ちた check の id と label、transcript）を読む。val の transcripts、`persona.jsonl`、隠したテスト、`repo.bundle`、val のログは読まない。採点の `passed` と check の id・label だけは、val でも見てよい。

原因をスキル、検証、試験場のどれかに分ける。検証か試験場が原因のときは、スキルの案を出さず、`.agents/skills/` も変えない。`eval:auto` にも進まない。

- 検証: その問題の採点（`eval/scenarios/<ID>/scenario.ts`、`eval/grade.ts`）と隠したテストを読んで直す。隠したテストは、issue と人役の回答表に書いた約束だけを確かめる。検証を直すときだけ、隠したテストを読んでよい。val の transcripts は読まない。読んだ内容は、スキルの変更の根拠にしない。
- 試験場: `eval/` の準備・採点・集計と、試験場リポジトリの環境を直す。

すでに直してあり、そのあとの train の記録に同じ失敗が残っていなければ、直さずに状態だけを「解決」にする。直したあとは、採点のやり直しまたは `deno task test` で同じ失敗が残っていないことを確かめ、パターンと `eval/wiki/index.md` の状態を「解決」にして `logs.md` に残して終わる。

原因がスキルのときだけ、次へ進む。これは訓練の完了ではない。val の合格が 0 のあいだは、未知の問題で通ったことにはしない。

### 3. 考えてから、選ばれた1件だけを直す

1回の変更で直すパターンは1つ。`.agents/skills/` と、対象リポジトリへコピーされる道具は、`deno task eval:propose --pattern <P-00>` が成功してから変える。

パターンのファイルに `## 改善案` を、次の順で書く。思考が終わる前に、スキルのファイルは変えない。

1. 思考。その失敗の回にだけ出て、別の問題では消える語を `固有` に書く。語は `、` で区切り、2文字以上にする。「なし」にはしない。`原則` は、その語を消しても残る1文にする。
2. 思考。`勾配` に、今のスキルのどの振る舞いに従ったかを左、その文をどの方向へ動かすかを右に、`→` でつなぐ。右辺には、失敗した出力を貼らない。
3. 行動。同じ原則の候補を2件か3件、表にする。種類は `道具`、`ひな形`、`手順`。内容に固有の語は書かない。`skill-impact.md` で却下済みの案は書かない。
4. 観測。各候補の `落ちた回` に、その候補が拾える train の実行 ID を書く。拾えないときは `なし`。`ひな形` と `手順` は、すでに正しくできていた train の実行 ID を `通った回` に1件以上書く。正しくできていた回が無い候補は選ばない。`道具` は、当てる通った回が無ければ `通った回` を `なし` にしてよい。落ちた回と通った回に同じ実行 ID は書かない。実行 ID は `eval/runs/` にあるものだけを書く。
5. 思考。ミニバッチを通った候補のうち、種類が最も強いもの（道具、ひな形、手順の順）を選ぶ。同じ種類が複数通るときは、落ちた回の数が多い方の番号を `選ぶ` に書く。数が同じなら、通った回の振る舞いを壊さない方を書く。どれも通らなければ `出さない`。
6. 観測。`deno task eval:propose --pattern <P-00>` を実行する。失敗したら改善案を直し、成功するまでスキルは変えない。成功しても `選ぶ` が `出さない` なら、スキルは変えず、調べた結果を `logs.md` に残して終わる。

実装してよいのは、`選ぶ` の1件だけである。手順の文章を足すのは、道具でもひな形でも落ちた回を拾えないときだけである。道具で検出する候補には、検出する場合としない場合のテストも足す。

### 4. 着手してよいか

`deno task eval:summary` で、今の val の合格回数を見る。採否は `eval/wiki/skill-impact.md` の条件で、`deno task eval:impact` が判定する。

val が1問で変更前の合格が 0 のとき、変更後に1回以上合格しなければ却下され、スキルは戻すことになる。その失敗が、いま直す train の問題と同じ種類だと記録から言えないなら、確認ポイント3で止まる。

変更前の同じ実行のしかたで、各 val が3回未満なら、先に変更前を測る。手と自動は混ぜない。いまの val の記録が自動なら `--driver auto` に揃える。

### 5. 直す

原因がスキルのときだけ、選ばれた1件の範囲で、`.agents/skills/` と、対象リポジトリへコピーされる道具を変える。実装で増やす行に、固有の語は書かない。変えたあと、コミットの前に次がすべて通ることを確かめる。

```sh
deno task eval:propose --pattern <P-00>
deno task test
deno fmt
deno lint
```

`eval:propose` は、改善案に加えて、未コミットの `.agents` の追加行に固有の語が無いかを見る。ここで失敗したら、その未コミットの差分を戻し、測るには進まない。

コミットの1行目は日本語で、何をなぜ変えたかを書く。1つのスキルだけなら `sdd-init: ...` のようにスキル名を先頭に付ける。型定義の版を上げたら、1行目の最後に `（型定義 x.y.z）` と書く。Conventional Commits は使わない。

### 6. 測る

変更の前と後で、すべての val を同じ実行のしかたで3回以上回す。モデルは `composer-2.5` のままにする。`eval/sdk/driver.ts` が Fast を切る。`--model` で Fast や別のモデルに変えない。

```sh
deno task eval:prepare <問題のID> --force
deno task eval:auto
```

`eval:prepare` は試験場を tag に戻し、ほかのブランチと未追跡のファイルを消す。origin があれば、リモートの既定ブランチへ強制 push する。`eval:auto` が失敗しても採点は残る。`eval/runs/` は追記だけで、書き換えない。

実行する AI に、wiki、人役の回答表、隠したテストを見せない。

### 7. 採否

`--change` の値が `-` で始まるときは `--change=...` と書く。

```sh
deno task eval:impact --pattern <P-00> --target <狙った問題> --before <変更前のコミット> --after <変更後のコミット> --change "<要約>" --driver auto --write
```

採用なら、パターンと `eval/wiki/index.md` の状態を「道具で検出」か「手順で対策」にし、`eval/wiki/logs.md` に何が分かったかを追記する。

却下なら、戻すとユーザーに伝えて指示を待つ。wiki と `eval/runs/` は戻さない。指示があって戻したあとは、同じ候補を出さない。次の案は、原則か勾配を変えた新しい改善案にし、手順3からやり直す。固有の語を足して出し直さない。

### 8. 状態の更新

パターンの先頭の「状態」と、一覧の同じ行を揃える。根拠の実行 ID を足す。採用前に「対策中」とは書かない。「解決」のときも、パターンと一覧を揃える。
