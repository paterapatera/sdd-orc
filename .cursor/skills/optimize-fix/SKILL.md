# optimize-fix

`.agents/skills/` のスキルと、対象リポジトリへコピーされる道具（`.agents/skills/sdd-init/assets/sdd/`）を、1件の依頼につき1件の変更で直す。ここは対象リポジトリではない。`sdd-*` をこのリポジトリに対して実行しない。

経路は2つある。

- 依頼の経路: ユーザーが「〇〇機能も追加したい」「〇〇が出ないから出るようにして」のように頼んだとき。依頼を `eval/wiki/requests/R-<3桁>.md` に書き、変えたスキルで事例を流し直して採否を決める。
- 訓練の経路: `close-pattern` の手順3から呼ばれたとき。対象のパターンが決まっているので、確認ポイント1と2は飛ばす。改善案はパターンに書き、採否は `close-pattern` の手順4以降（val の合格）で決める。

スキルを呼び出したこと（`/optimize-fix`）は、確認ポイントへの回答ではない。

## 確認ポイント

ユーザーの回答を待つのは次だけである。それ以外は止まらずに進める。質問は1件ずつにする（回答によって次の質問が変わるため）。

1. 対象のスキルか、依頼の中身が決まらない。どのスキルの、どの場面の振る舞いかを、1件ずつ聞く。
2. 事例の表（場面と期待）ができた。期待は依頼を言い換えたものなので、AI の判断では決めない。出してはいけない場面も含めて見せ、合っているかを聞く。違えば、違う点を1件ずつ聞いて直す。表を見せる前に、依頼から1つに決まらない点（どこに出すか、どの形か、どの場面では出さないか）があれば、それを1件ずつ聞く。
3. 依頼を実現すると、AGENTS.md の「守ること」とぶつかる（人のコードレビューを前提にする手順、特定のツールの hook に頼る、外部のパッケージを使う、など）。ぶつかる点を示して、どうするかを聞く。
4. 訓練の経路で、直しの根拠が val の記録にしか無い。読むと、その問題は train に移し、その点数は汎化の証拠にしない。読む前に、読むかを聞く。
5. コミット、`git revert`、`git restore`、push は、ユーザーが指示するまで実行しない。却下のときは、戻すと伝えて指示を待つ。

## 守ること（試行で崩れた点）

- 依頼の言葉や、失敗した場面にだけ出る語を、そのまま手順へ足さない。その場面には効いても、別の場面では悪くなる。P-007 で日時のタイムゾーンを別の1問として足した変更は、VAL-001 の合格が 3/3 から 1/3 に減り、却下された。依頼は、同じ原則が当てはまる場面の1つとして扱う。
- 出してはいけない場面も事例にする。出したい場面だけで確かめると、ほかの場面でも出るようになったことに気づかない。
- `固有` に書くのは、事例の場面にだけ出る語（その案件の名前、ファイル名、値、例の文面）である。依頼された機能の名前は、実装に要るので `固有` にしない。
- 依頼の経路の採否は、事例を流し直して決める。val の点数は使わず、val の記録も読まない。val の合格が減っていないかは、次の訓練の `deno task eval:summary` で見る。

直す前に、`固有` の語を消しても残る原則にする。今の文が許した振る舞いと、文を動かす方向を勾配として書く。同じ原則の候補を2件か3件比べ、事例に当ててから1件に絞る。ファイルを変えるのは、その観測のあとである。却下されたら、語を足して出し直さず、原則か勾配からやり直す。

この順は、次に合わせてある。具体へ戻る前の抽象化（Zheng et al., 2023, “Take a Step Back: Evoking Reasoning via Abstraction in Large Language Models”）。候補を作って点で選ぶこと（Zhou et al., 2022, “Large Language Models Are Human-Level Prompt Engineers”）。文への勾配と候補の比較（Prasad et al., 2023, “Automatic Prompt Optimization with Gradient Descent and Beam Search”）。思考と行動の交互（Yao et al., 2022, “ReAct: Synergizing Reasoning and Acting in Language Models”）。文章だけの決まりは守られないので、`deno task eval:propose` が同じ条件を落とし、採否も判定する。

## 手順

### 1. 今の振る舞いを読んで確かめる

対象のスキルの `SKILL.md` と、関係する `assets/`、`references/`、`docs/sdd/guides/` の手引き、道具を読む。依頼の振る舞いが今どの文か道具から来ているか、または、どこにも無いかを確かめる。推測で書かない。

`eval/wiki/index.md` に、同じ失敗の未対策のパターンがあれば、訓練の経路にする。train の実行（`eval/runs/`）に同じ場面があれば、根拠に足す。val の記録は読まない。

原因がスキルの外（対象リポジトリの設定、呼び出し方の誤り）なら、スキルは変えない。記録の状態を「スキル以外」にし、何が原因かを伝えて終わる。

依頼の経路では、`eval/wiki/requests/` に同じ依頼で状態が「未対応」のものがあれば、それを続ける。無ければ次の番号で作る。ひな形は `eval/wiki/index.md` にある。

### 2. 事例を書いて、人に確かめる

`## 事例` の表に、ID（`E-1` から順）、今（`落ちた` か `通った`）、場面、期待を書く。

- 落ちた: 依頼した振る舞いが、今のスキルでは出ない場面。依頼の場面と、同じ原則が当てはまる別の場面を、それぞれ1件以上書く。
- 通った: 今のスキルで正しく、変えてはいけない場面。依頼した振る舞いを出してはいけない場面を1件以上含める。
- 場面には、どのスキルの、どの工程で、何が起きているか（spec の中身、人の答え）を書く。期待には、外から見て確かめられる形で書く（何が、どこに、どの形で出るか、出ないか）。

確認ポイント2で人に確かめる。確かめるまで、手順3へ進まない。

### 3. 改善案を書いて、観測してから1件に絞る

この手順が終わるまで、`.agents/skills/` は変えない。改善案は、依頼の経路では依頼の記録に、訓練の経路ではパターンのファイルに、`## 改善案` として次の順で書く。

1. 思考。事例の場面にだけ出る語を `固有` に書く。語は `、` で区切り、2文字以上にする。「なし」にはしない。`原則` は、その語を消しても残る1文にする。依頼はどんな振る舞いの1つの例かを書く。
2. 思考。`勾配` に、今のスキルのどの文や道具がその振る舞いを生んでいるか（無いなら、どこが黙っているか）を左、それをどの方向へ動かすかを右に、`→` でつなぐ。
3. 行動。同じ原則の候補を2件か3件、表にする。種類は `道具`（verify、doctor、finish-report、gate、render などで、機械的に出すか検出する。`tests/` にテストも足す）、`ひな形`（`assets/` のひな形、型定義）、`手順`（`SKILL.md`、`references/`、手引きの文章。description も含む）。内容に固有の語は書かない。却下済みの候補は書かない。
4. 観測。各候補の `落ちた回` に、その候補で期待どおりになる落ちた事例の ID を書く。どれも直らないときは `なし`。`ひな形` と `手順` は、変えても期待どおりのまま残る通った事例の ID を `通った回` に1件以上書く。`道具` は、当てる通った事例が無ければ `通った回` を `なし` にしてよい。訓練の経路では、事例の ID は train の実行 ID で、`eval/runs/` にあるものだけを書く。
5. 思考。ミニバッチを通った候補のうち、種類が最も強いもの（道具、ひな形、手順の順）を選ぶ。同じ種類が複数通るときは、落ちた回の数が多い方の番号を `選ぶ` に書く。数が同じなら、通った事例の振る舞いを壊さない方を書く。どれも通らなければ `出さない`。
6. 観測。改善案を確かめる。失敗したら改善案を直し、成功するまでスキルは変えない。成功しても `選ぶ` が `出さない` なら、スキルは変えず、調べた結果を `## 試した対策`（訓練の経路では `logs.md`）に残して終わる。

```sh
deno task eval:propose --file eval/wiki/requests/<R-ID>.md   # 依頼の経路
deno task eval:propose --pattern <P-00>                       # 訓練の経路
```

### 4. 1件だけ実装する

訓練の経路では、ここで実装しない。`.cursor/skills/close-pattern/SKILL.md` の手順4（着手してよいか）から続け、手順5で `選ぶ` の1件だけを実装する。

依頼の経路では、`選ぶ` の1件だけを実装する。AGENTS.md の決まり（道具のコード、型定義の版、SKILL.md の書き方）に従う。実装で増やす行に、固有の語は書かない。道具の候補には、落ちた事例の場面で出ることと、通った事例の場面で変わらないことの両方をテストする。実装のあと、手順3の6と同じコマンドを実行する。未コミットの `.agents` の追加行に固有の語があれば失敗するので、その差分を直してからやり直す。`deno task test`、`deno fmt`、`deno lint` も通す。

### 5. 変えたスキルで、事例を流し直す（依頼の経路）

- 道具とひな形で決まる事例: `tests/` のテストで、その場面を作って確かめる。決まった結果になるので、1回でよい。
- 手順の文章で決まる事例: 試験場を、場面に近い train の問題で準備する（`deno task eval:prepare <問題のID> --force`）。Task のサブエージェントで、モデルは `composer-2.5` にし、試験場でその場面をやり直させる。渡すのは、試験場のパス、呼び出すスキル、場面の依頼の文面、その場面で人が答える内容だけである。原則、勾配、候補、期待、依頼の記録は渡さない。答えを知っていると、スキルの効き目ではなく答えに合わせて動くからである。出力はぶれるので、同じ事例を3回流し、3回とも期待どおりのときだけ `通った` にする。
- 流せない事例は `再現できない` にする。

流し終わってから、`## 結果` の表（ID、後）にすべての事例を書く。

### 6. 採否（依頼の経路）

手順3の6と同じコマンドを実行する。`## 結果` があると、採否を判定する。

- 採用: 選んだ候補の落ちた事例がすべて期待どおりになり、通っていた事例が1件も崩れていない。状態を「採用」にし、`## 試した対策` に候補と結果を書く。ユーザーには、事例ごとに前と後の振る舞いを示す。これが受け入れテストになる。
- 却下: 選んだ候補の落ちた事例が残ったか、通っていた事例が崩れた。戻すと伝えて指示を待つ。`## 試した対策` に却下した候補を書き、状態を「未対応」に戻す。次の案は、原則か勾配を変えて手順3からやり直す。
- 保留: 流していない事例か、再現できない事例がある。どの事例かを伝える。採用とは書かない。

訓練の経路の採否は、`close-pattern` の手順7（`deno task eval:impact`）で決める。
