# optimize-fix

このリポジトリのスキルと、対象リポジトリへコピーされる道具を、失敗の記録から1件だけ直す。ここは対象リポジトリではない。`sdd-*` をこのリポジトリに対して実行しない。

未対策のパターンを選ぶところから採否まで進める依頼は `close-pattern` である。このスキルは、その直し方である。`close-pattern` の手順3から呼ばれたときは、対象のパターンが決まっている。確認ポイント1は飛ばす。

スキルを呼び出したこと（`/optimize-fix`）は、確認ポイントへの回答ではない。

## 確認ポイント

ユーザーの回答を待つのは次だけである。それ以外は止まらずに進める。質問は1件ずつにする。

1. 直す対象が無い。パターン ID も、スキル名と失敗の様子も無い。どれを1件だけ聞く。
2. 直しの根拠が val の記録にしか無い。読むと、その問題は train に移し、その点数は汎化の証拠にしない。読む前に、読むかを聞く。
3. コミット、`git revert`、push は、ユーザーが指示するまで実行しない。

## 守ること（試行で崩れた点）

失敗の回にだけ出る語を手順へ足すと、その回には効いても別の問題では合格が減る。P-007 で日時のタイムゾーンを別の1問として足した変更は、VAL-001 の合格が 3/3 から 1/3 に減り、却下された。

直す前に、その語を消しても残る原則にする。今の文が許した振る舞いと、文を動かす方向を勾配として書く。同じ原則の候補を2件か3件比べ、落ちた回と通った回に当ててから1件に絞る。ファイルを変えるのは、その観測のあとである。却下されたら、その語を足して出さず、原則か勾配からやり直す。

この順は、次に合わせてある。具体へ戻る前の抽象化（Zheng et al., 2023, “Take a Step Back: Evoking Reasoning via Abstraction in Large Language Models”）。候補を作って点で選ぶこと（Zhou et al., 2022, “Large Language Models Are Human-Level Prompt Engineers”）。文への勾配と候補の比較（Prasad et al., 2023, “Automatic Prompt Optimization with Gradient Descent and Beam Search”）。思考と行動の交互（Yao et al., 2022, “ReAct: Synergizing Reasoning and Acting in Language Models”）。文章だけの決まりは守られないので、`deno task eval:propose` が同じ条件を落とす。

## 手順

### 1. 対象を1件決める

パターン ID があるとき、または `close-pattern` から来たときは、そのパターンを使う。聞き直さない。

スキル名と失敗の様子だけがあるときは、`eval/wiki/index.md` の未対策から、そのスキルに関係するものを見る。1件ならそれを使う。2件以上なら、どれかを1件だけ聞く。0件なら、train の記録が無いのでスキルは変えない。

`eval/wiki/skill-impact.md` の、そのパターンの却下済みの案は候補にしない。

### 2. 根拠は train の記録だけ

`close-pattern` の手順2に従う。val の transcripts、`persona.jsonl`、隠したテスト、`repo.bundle`、val のログは読まない。採点の `passed` と check の id・label だけは、val でも見てよい。

原因が検証か試験場のときは、スキルの案を出さず、`.agents/skills/` も変えない。`close-pattern` の手順2の残り（採点か試験場を直して「解決」にする）に戻る。

原因がスキルのときだけ、次へ進む。

### 3. 改善案を書いて、観測してから1件に絞る

`.agents/skills/` と、対象リポジトリへコピーされる道具は、この手順が終わるまで変えない。パターンのファイルに `## 改善案` を、次の順で書く。

1. 思考。その失敗の回にだけ出て、別の問題では消える語を `固有` に書く。語は `、` で区切り、2文字以上にする。「なし」にはしない。`原則` は、その語を消しても残る1文にする。
2. 思考。`勾配` に、今のスキルのどの振る舞いに従ったかを左、その文をどの方向へ動かすかを右に、`→` でつなぐ。右辺には、失敗した出力を貼らない。
3. 行動。同じ原則の候補を2件か3件、表にする。種類は `道具`、`ひな形`、`手順`。内容に固有の語は書かない。
4. 観測。各候補の `落ちた回` に、その候補が拾える train の実行 ID を書く。拾えないときは `なし`。`ひな形` と `手順` は、すでに正しくできていた train の実行 ID を `通った回` に1件以上書く。正しくできていた回が無い候補は選ばない。`道具` は、当てる通った回が無ければ `通った回` を `なし` にしてよい。落ちた回と通った回に同じ実行 ID は書かない。実行 ID は `eval/runs/` にあるものだけを書く。
5. 思考。ミニバッチを通った候補のうち、種類が最も強いもの（道具、ひな形、手順の順）を選ぶ。同じ種類が複数通るときは、落ちた回の数が多い方の番号を `選ぶ` に書く。数が同じなら、通った回の振る舞いを壊さない方を書く。どれも通らなければ `出さない`。
6. 観測。`deno task eval:propose --pattern <P-00>` を実行する。失敗したら改善案を直し、成功するまでスキルは変えない。成功しても `選ぶ` が `出さない` なら、スキルは変えず、調べた結果を `logs.md` に残して終わる。

手順の文章を選ぶのは、道具でもひな形でも落ちた回を拾えないときだけである。道具で検出する候補には、検出する場合としない場合のテストも、実装のときに足す。

### 4. 実装は、測ってよいかを見てから

改善案が通ったあと、実装はまだしない。`.cursor/skills/close-pattern/SKILL.md` の手順4（着手してよいか）から続ける。手順5で、`選ぶ` の1件だけを実装する。実装で増やす行に、固有の語は書かない。実装のあと、測る前に `deno task eval:propose --pattern <P-00>` をもう一度実行する。
