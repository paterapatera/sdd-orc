# R-003 sdd-impl / sdd-finish: 実装完了で PR/MR を出し、合格後の finish でマージする

- 状態: 採用
- 対象: `.agents/skills/sdd-impl/`、`.agents/skills/sdd-finish/`（手順の案内が同じ流れを指す `sdd-req` の報告と `README.md` の流れの説明を含む）
- 依頼: 「実装後に人が動作確認してから `/sdd-finish` で MR を出す流れになっている。理想は、実装完了後に MR を出して、人が動作確認して、OK だったら `/sdd-finish` でドキュメント整理後にマージする」
- 動作確認: このリポジトリの受け入れテスト（HTML の「受け入れテスト」の章）と同じものとして書く。違えば直す

## 今の振る舞い（読んで確かめたこと）

- `sdd-impl/SKILL.md` の手順3は、タスク完了後に受け入れテストの準備、`acceptance.ts`、HTML の再生成、push まで行い、受け入れテストを依頼して止まる。PR/MR は作らない。合格したら sdd-finish、と案内する。
- `sdd-finish/SKILL.md` は、受け入れテストの合格後に恒久ドキュメントへ反映し、spec を削除してから PR/MR を作る。確認ポイントで「PR/MR を作成してよいか」を聞き、言及が無い「OK」は作成の了承にしない（P-005）。マージはユーザーに頼まれた場合だけ行う。
- `sdd-finish/assets/pr-body.md` は、本文を「人が受け入れテストで確かめたもの（合格済み）」として書く。
- `sdd-req/SKILL.md` の報告は「PR/MR はこの時点では作らない（sdd-finish で作る）」。
- `README.md` の流れは、受け入れテストのあと `/sdd-finish` で PR/MR を作り、その後に squash マージ、である。
- `review-feedback.md` の「PR/MR を作った後に変更が入った場合」は、sdd-finish の後（spec を削除した後）を前提にしている。

## 改善案

- 原則: 人が振る舞いを確かめる前に、作業の結果を見せる提案を開き、合格のあと長く残す知識を反映してからその提案を取り込む。
- 固有: 合格済み、作業ツリー、main、HTML、導入
- 勾配: 実装の完了は提案を開かず、完了の手順が人が確かめたあとで提案を作り、取り込みは別の依頼があるときだけ行う → 実装が終わった時点で提案を開き、合格のあとの完了は長く残す知識を反映してからその提案を取り込む。実装より前、確認が済む前、提案の置き場が無いときは開かず取り込まない
- 選ぶ: 1

| # | 種類 | 内容 | 落ちた回 | 通った回 |
|---|---|---|---|---|
| 1 | 手順 | 実装が終わった報告で提案を開き、完了ではその提案を長く残す知識の反映と要約の更新のあとに取り込む。実装より前、確認が済む前、置き場が無いとき、保存していない変更の確認、不合格のあと同じ提案への追加は残す | E-1、E-2 | E-3、E-4、E-5、E-6、E-7、E-8 |
| 2 | 手順 | 実装が終わった報告で提案を開くことだけを足し、完了は人が確かめたあとで提案を作る手順のままにする | E-1 | E-3、E-4、E-7、E-8 |

## 試した対策

- 候補1（手順）を実装した。`sdd-impl` は実装の完了で PR/MR を開き、`sdd-finish` は合格の確認のあと、恒久ドキュメントの反映と本文の更新と spec の削除をしてから、開いている PR/MR を squash マージする。`bun run fmt`、`bun run lint`、`bun run test`、`bun eval/propose.ts --file eval/wiki/requests/R-003.md` は通った。
- 人が、`gh pr edit` の失敗は試験場の GitHub CLI 2.45.0 の問題であり、ここまでの検査は合格だと判断した。状態を採用にする。E-5、E-7、E-8 は個別には流していない。
- 1回目（QUICK-001、20261016-145147）。実装完了で PR #10 を開き、本文は「これから確かめること」で、マージも spec の削除もしていない。`OK /sdd-finish` のあと、本文を「確かめて合格したもの」に更新し、spec を削除して squash マージした（`7648d2eb`）。新しい PR は作らず、了承も重ねて聞いていない。恒久ドキュメントは変えていない。本文の更新は `gh pr edit` が失敗し、`gh api` で行われた。
- 2回目（QUICK-001、20261016-151437）。実装完了で PR #11 を開き、本文は受け入れる前のままで、マージも spec の削除もしていない。`OK /sdd-finish` のあと squash マージし、spec は main に残っていない。本文の更新は再び `gh pr edit` が終了コード 1 で失敗し、`gh api` で行われた。標準エラーは `projectCards`（Projects classic の廃止）。試験場の `gh` は 2.45.0 で、2.73.0 以降で直る不具合。`~/.local/bin/gh` を 2.102.0 にし、マージ済みの PR #11 で `gh pr edit --body-file` が終了コード 0 になることを確かめた。スキルは変えていない。
