# R-002 sdd-design: 恒久ドキュメントで決まっていない構成の判断を、AI が決めてしまう

- 状態: 未対応
- 対象: `.agents/skills/sdd-design/`（「質問はありません」の前の確認、手順3）と、道具の設計の検査（`.agents/skills/sdd-init/assets/sdd/scripts/lib/rules.ts`）
- 依頼:「このなかで人が決めておかないと大きな手戻りが発生しそうなものはありますか？」への答え（構成の判断）を受けて「どのスキルを直せばいいですか？」。選んだ案は「P-008 を記録し、sdd-design の検査（新しいモジュールに adr: true を必須にする）の候補を eval:propose にかける」

## 今の振る舞い（読んで確かめたこと）

## 改善案

7回目の案（1回目から6回目の候補1は却下。「試した対策」を参照）。

- 原則: 構成の判断（新しい部品の置き場所と、前例の無いつなぎ方）の根拠は、恒久ドキュメントの記述の全体、根拠のある部品に仕える前例どおりの細部、人が答えたと書き手が道具に申告して記録した回答のどれかである。細部が仕えてよい部品は、architecture.ts の依存の向きで決まる（細部のモジュールが、その部品のモジュールと同じか、そのモジュールに依存する）。
- 固有: お知らせ、ダッシュボード、Announcements、プロフィール、管理画面、Admin、laravel-modules、Deptrac
- 勾配: 前例を「変更する既存の部品と依存でつながる」で決めると、何にでもつながれる入口の部品（ルートの定義）を経由して新しい機能の部品が前例になり、新しい部品にだけつながる細部は前例にならない。また、道具が未回答として一覧に出したあとなら、書き手が人に聞かずに answer を書いても通る → 前例の根拠にできる部品を、変更する既存の部品か、恒久ドキュメントか回答を根拠にした新しい部品に広げ、細部のモジュールがその部品のモジュールと同じか、architecture.ts でそのモジュールに依存する場合に限る。answer は、書き手が verify に「ユーザーが答えた」と ID を申告して記録したものだけを認める
- 選ぶ: 1

6回目で、前例の条件は、既存の画面に足す設計の細部（変更する部品につながるスキーマの変更と UI の部品）の質問を消した（E-4）。崩れたのは、変更する入口の部品（ルートの定義）を経由して新しい機能の部品が前例になった回（E-1）、新しい部品にだけつながる細部が前例にならず聞いた回（E-6、E-7）、一覧に出たあとに書き手が自分で answer を書いた回（E-2）である。
候補1は、細部が仕える向きを architecture.ts のモジュールの依存で決める。入口の部品のモジュールにほかのモジュールは依存しないので、新しい機能のモデルやコントローラが入口の部品を経由して前例になる形は消え、機能の置き場所の質問が残る（E-1、E-3）。スキーマの変更は、スキーマのモジュールがモデルのモジュールに依存するので、変更する既存のモデルにつながっても（E-4、E-7）、恒久ドキュメントを根拠にした新しいモデルにつながっても（E-6）前例として通る。UI の部品は、変更する画面と同じモジュールなので通る（E-4）。(b) は、人に聞かずに answer を書くには「ユーザーが答えた」と申告する必要があるので、一覧に出したあとの自動の記載が止まる（E-2）。ADR と architecture.ts の記述で決まる設計（E-5、E-6）、answers の無い spec（E-9）、質問の形（E-8）は変わらない。
候補2は、依存を問わないので、同じモジュールの既存の部品を変える設計では、新しい機能の部品が前例として通り、機能の置き場所の質問が出ない（E-1 が運のまま）。
候補3は、6回目の E-2 の崩れ（一覧に出たあとに書き手が answer を書く）が残る（E-2 が通らない）。
流し直しでは、5回目と同じく、確認ポイントで人の役が一覧を見て、答えていない項目を指摘したあと、書き手がその項目を1件で聞き、最後の design.ts の根拠が人の答えた回答だけになれば、その回は期待どおりとする。
