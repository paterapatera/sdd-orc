- 状態: 採用
- 対象: `.agents/skills/sdd-req/`（手順5の点検）と、共有の手引き `.agents/skills/sdd-init/assets/sdd/guides/writing-requirements.md`
- 依頼:「確認ポイントを最適化して」「たとえば、バリデーションのパターンが少なすぎる。https://readouble.com/laravel/13.x/ja/validation.html#available-validation-rules にあるようなルールが網羅されていない。そんなかんじで、具体的なチェックをしているのに網羅されていない部分が他にもありそう」
- 範囲: 入力の検証だけでなく、外から見える値の点検の全体（人に確かめた）

## 今の振る舞い（読んで確かめたこと）

- `sdd-req/SKILL.md` の手順5は「点検で、次の値が受け入れ条件にあるかを1つずつ確かめる」とし、入力の上限と必須、表示の形、日時のタイムゾーン、件数、文言の5項目を挙げる。一覧が例か全部かを書いていない。
- 手引き `writing-requirements.md` の十分性のチェックリストは、`inputValidation` の点検を「必須、形式、長さ、範囲」の4語にしている。`schema/requirements.ts` の表示名も同じ4語。
- 「分からないことは推測で埋めない」の例（文言、並び順、遷移先、既存の画面、不正な入力）も閉じた列挙である。
- train の FULL-001 の6回（20261011-171027 から 194523）で、人役に聞いた質問は、一覧に載った観点（上限、件数、並び順、0件の文言、page の不正な値、日付の形、閲覧の権限）だけだった。一覧に無い観点（空白だけの値を空とみなすか、同じタイトルの重複、本文の改行の見せ方、登録日時が同じものの並び）は6回とも聞いていない。
- 点検の単位が「観点の一覧」で、issue に出てくる入力や表示を1つずつ取り出す手順が無い。観点の出どころ（フレームワークの検証規則の一覧など）も書いていない。

## 改善案

5回目の案（1回目の候補3、2回目から4回目の候補1は却下。「試した対策」を参照）。

- 原則: 決まっていないことは、関係しない理由にならない。観点の扱いを決められるのは issue、既存のコード、人の回答だけで、書き手の判断は扱いを決めない。書き手の判断で外せる扱いが残る限り、決めていない観点はそこへ流れる。
- 固有: お知らせ、タイトル、本文、ダッシュボード、登録日時、開始日、終了日、備考、添付ファイル、プロフィール、announcement、readouble
- 勾配: 関係しない扱いは、出どころが issue の任意の文でも通るので、書き手が「issue に無い」を理由に観点を外せる → 関係しない扱いは人の回答だけを出どころにし、回答は requirements.ts の answers に ID 付きで残す。出どころの回答は answers の ID を指し、無い ID は型と verify がエラーにする。それ以外の決まらない観点は未確定のまま質問する
- 選ぶ: 1
