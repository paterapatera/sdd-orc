# 訓練の wiki

試験場での実行から分かったことを溜める場所。スキルを直す側だけが読む（試験場にはコピーしない。実行する AI にも見せない）。

| ファイル | 中身 | 書く人 |
|---|---|---|
| `patterns/<ID>.md` | 失敗のしかたを1件ずつ | 実行の記録を読んだ AI と人 |
| `strategies/<ID>.md` | 合格した実行でうまくいったやり方を1件ずつ | 同上 |
| `logs.md` | 実行のたびの要約（何を回し、何が分かったか） | 同上 |
| `skill-impact.md` | スキルの変更の提案と、採点の結果、採否 | `bun eval/impact.ts --write`（それより前は手で書いた） |
| `requests/<ID>.md` | `.agents/skills` のスキルへの依頼（機能の追加、出ない振る舞いを出す）の記録。事例、改善案、流し直した結果 | optimize-fix |

## うまくいったやり方の一覧

合格した実行から取り出したやり方。スキルの文章を直すときに、何を書くかの根拠にする。

| ID | 概要 | 関係するパターン |
|---|---|---|
| [S-001](strategies/S-001.md) | 回答が質問の一部にしか答えていなければ、残りを推奨で埋めずに次の質問で聞き直す | P-007 |
| [S-002](strategies/S-002.md) | 外から見える値は、1つの質問に1点だけにする（日時の形とタイムゾーンを分ける） | P-007 |
| [S-003](strategies/S-003.md) | 完了時の短い了承は受け入れテストの結果としてだけ受け取り、PR を作るかは別に聞く | P-005 |
| [S-004](strategies/S-004.md) | 品質ゲートが既存のコードで落ちたら、直さずに止まって聞く | P-001、P-003 |

状態は「未対策」「対策中」「道具で検出」「手順で対策」「解決」のどれか。未対策は、原因がスキルで、まだ閉じていないものだけである。スキルが原因なら、道具（verify、doctor など）とテストに落とし込めたら「道具で検出」、手順の文章だけなら「手順で対策」。検証か試験場が原因で、そこを直して同じ失敗が残っていなければ「解決」。解決のときはスキルを変えない。

## パターンのひな形

```md
# P-001 <短い名前>

- 状態: 未対策
- 原因: スキル
- 起きた工程: sdd-init の手順4（品質ゲートの登録）
- 根拠: 20261010-120000-INIT-001（transcripts/xxx.jsonl の◯行目付近）、…

原因は「スキル」「検証」「試験場」のどれか。検証と試験場は、そこを直して「解決」にする。スキルの案は出さない。

## 何が起きたか

## なぜ起きたか（推測は推測と書く）

## 対策の案

原因がスキルのときだけの見立て。道具で検出できるか → ひな形・型で防げるか → 手順の文章、の順に考える。スキルを変える直前の正式な案は「改善案」である。

## 改善案

close-pattern が、スキルを変える前に書く。`bun eval/propose.ts --pattern <ID>` が通るまでスキルは変えない。

- 原則: （固有の語を消しても残る1文）
- 固有: （この失敗の回にだけ出る語。`、` で区切る）
- 勾配: （今の文が許した振る舞い） → （文を動かす方向）
- 選ぶ: （候補の番号、または「出さない」）

| # | 種類 | 内容 | 落ちた回 | 通った回 |
|---|---|---|---|---|
| 1 | 道具 |  |  |  |
| 2 | 手順 |  |  |  |

## 試した対策（skill-impact.md の行）
```

## 依頼の記録のひな形

optimize-fix の依頼の経路で使う。番号は `R-001` から順。状態は「未対応」「採用」「保留」「スキル以外」のどれか。却下したら、候補を「試した対策」に残して「未対応」に戻す。

```md
# R-001 <対象のスキル>: <依頼の短い名前>

- 状態: 未対応
- 対象: `.agents/skills/sdd-finish/`
- 依頼: （ユーザーの言葉のまま。例:「受け入れテストの手順に、確かめる URL も出るようにして」）

## 今の振る舞い（読んで確かめたこと）

（どの文か道具が、今の振る舞いを生んでいるか。どこにも無いなら、どこが黙っているか）
```
