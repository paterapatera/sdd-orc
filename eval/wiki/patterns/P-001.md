# P-001 品質ゲートのコマンドを、動くか試さずに登録する

- 状態: 道具で検出（2026-10-10 採用）
- 起きた工程: sdd-init の「ツールの選定と品質ゲート（config.ts の commands）」
- 根拠: 20261010-113010-INIT-001、20261010-114316-INIT-001、20261010-115030-INIT-001（3/3 回。composer-2.5、スキル cc870e8）

## 何が起きたか

3回とも、`commands` に `composer check:php`、`php artisan test` など、ホストで実行する形のコマンドを登録した。
試験場ではホストの PHP が 8.4、`composer.json` が `^8.5`、テストの DB が Sail の `pgsql` なので、`gate --full` は format から e2e まですべて落ちる。

- 3回とも、Sail（`./vendor/bin/sail`）を一度も実行していない（Shell の記録に無い）。
- 3回とも、登録したコマンドを一度も実行せずにコミットした。
- `doctor` は通る（コマンドが登録されているかだけを見ており、動くかは見ていない）。
- 1回は e2e に `npx playwright install chromium` を含めた。

## なぜ起きたか（推測を含む）

- 確かめた事実: sdd-init の手順には、登録したコマンドを実行して確かめる手順が無い。`doctor` も実行しない。
- 推測: `composer.json` の scripts と CI（`composer ci:check`）をそのまま写しており、CI はホストに PHP 8.5 を入れて動かすので、ローカルの実行環境の違いに気づく材料が無かった。
  `compose.yaml`、`phpunit.xml` の `DB_HOST=pgsql` は手がかりになるが、読んでいない。

## 対策の案

1. 道具: 導入時（または `config.ts` の `commands` を変えたとき）に、登録したコマンドが基準のコードで通ることを機械的に確かめる。
   例: `config.ts` の `commands` を変えたコミットでは、pre-commit hook が `gate` を流す。`doctor --gate` で実行できるようにする。
2. 手順: sdd-init の手順6（コミットの前）で `gate --full` を実行し、通らなければ原因を調べてコマンドを直す。通らないままコミットしない。

## 試した対策（skill-impact.md の行）

- 2026-10-10: pre-commit hook が、config.ts のコミットで `gate --if-changed` を流す。
  INIT-001 の gate の項目は 0/3 → 3/3。3回とも Sail を調べ、コマンドを Sail 経由に直した。
  ただし基準のコードが品質ゲートを通らないため、アプリのコードを直して通すようになった（P-003）。
